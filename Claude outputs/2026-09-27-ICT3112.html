The Seven ISTQB Principles

ISTQB has seven core testing principles. Exam questions often ask you to spot which one applies to a scenario.

  • Testing shows presence of defects — a passing test means no defects were found yet, not that none exist.
  • Exhaustive testing is impossible — you can't test every input, so use risk analysis to focus effort.
  • Early testing saves cost — find bugs early (shift left), before they get expensive to fix.
  • Defect clustering — about 80% of bugs live in about 20% of modules. Focus testing there.
  • Pesticide paradox — running the same tests over and over stops finding new bugs. Refresh your test cases.
  • Testing is context-dependent — a banking app and a games app need different testing approaches.
  • Absence-of-errors fallacy — zero bugs doesn't mean the software is useful, if it solves the wrong problem.
Watch out: pesticide paradox is about a stale test suite; defect clustering is about where bugs hide. Don't mix them up.

Mnemonic: Teach Every Eager Developer Proper Testing Approaches (T-E-E-D-P-T-A).

Boundary Value Analysis (BVA)

BVA tests the edges of a range, since bugs love to hide at boundaries (off-by-one errors).

For a valid range of 0–100:

  • Basic BVA: test 0, 100 (valid edges) and −1, 101 (just outside).
  • Extended BVA: also test 1 and 99 (just inside).

For strings (e.g. 1–10 capital letters), test length boundaries and character-range boundaries separately — mixing them hides which one actually broke.

Four general rules:

  1. Test both ends of a range, plus one step beyond each.
  2. No range given? Test the domain's min/max, plus one below/above.
  3. For sets or files, test every value plus the first/last item.
  4. Test extreme outputs, not just inputs.
Watch out: rule 4 catches people who only think about inputs. BVA complements Equivalence Partitioning — it doesn't replace it.

Basic Musa Reliability Model

This model assumes each bug you fix cuts the failure rate by the same fixed amount — exponential decay.

Two formulas:

  • λ(τ) = λ₀ × e^(−λ₀τ/ν₀) → failure rate at time τ
  • μ(τ) = ν₀ × [1 − e^(−λ₀τ/ν₀)] → total failures expected by time τ

Where λ₀ = starting failure rate, ν₀ = total failures expected over the software's life.

Example: λ₀=2, ν₀=10, τ=5 → exponent = −1 → λ(5) ≈ 0.74, μ(5) ≈ 6.32.

Best for stable, mature software. The Logarithmic Musa model is the alternative, used when early bugs are far worse than later ones.

Watch out: ν₀ is a fixed total count; λ(τ) is a rate that keeps dropping. Don't confuse the two.

Mnemonic: ν₀ = total "volume" of bugs ever expected; λ = the "live" rate right now.
