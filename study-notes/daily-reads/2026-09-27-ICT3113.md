## Response Time, Percentiles and the Tail

Response time splits into `R = W + S`:
- **S (service time)** = time the server is actively working on YOUR request.
- **W (wait time)** = everything else — queuing, waiting, distraction.

**Polyclinic example:** 25 min queue + 10 min doctor + 15 min waiting for results + 5 min follow-up = 55 min total. Only 15 min is service — 73% is just waiting.

**Key insight:** shaving a few minutes off service time saves more than just those minutes — everyone queued behind also starts earlier.

For a spread of response times, percentiles matter more than the average:
- The mean gets dragged up by rare slow outliers.
- p95/p99 show what the **tail** looks like — that's why SLOs are set on them.

Rough perception thresholds: 0.1 s = instant, 1 s = noticeable delay, 10 s = need a loading spinner.

> [!warning] Watch out
> SLI = the metric measured. SLO = the target for it. SLA = the contract around it. Don't swap SLI and SLO.

## Multi-Server Queues (M/M/c)

M/M/c is M/M/1 with c servers sharing one queue (e.g. 3 API servers behind a load balancer).

**Stability:** ρ = λ/(c×μ) must be less than 1.

Surprising fact: one super-fast server beats c slower servers of the same total capacity — but real systems still use many servers, because:
- No single machine scales forever.
- If one of c servers fails, you only lose 1/c of capacity, not everything.

**Example:** λ=8 tps, S=148 ms, c=3 → normal wait ≈ 7 ms. Lose one server (c=2) → wait jumps to ≈ 58 ms (8× worse).

> [!warning] Watch out
> "More servers = better latency" is false. The real reason for many servers is fault tolerance, not speed.

## Operational Laws — Forced Flow and Service Demand

These laws connect throughput, visits, and utilisation, using only measurable numbers.

**Forced Flow Law:** `X_k = V_k × X`
→ Each transaction makes 4 DB queries (V=4), system throughput X=25 tps → DB handles 4×25 = 100 queries/sec.

**Service Demand:** `D_k = V_k × S_k`
→ V=4 queries × S=5 ms each = D=20 ms total DB time per transaction.

**Service Demand Law:** `U_k = X × D_k`, rearranged: `D_k = U_k / X`
→ Lets you calculate demand from monitoring data alone — no need to trace every transaction.

**Diagnostic case:** API, DB, and storage all show *moderate* utilisation, yet p95 latency = 3.5 s. If capacity and demand look fine, the problem is **variability** (see the Kingman formula).

> [!warning] Watch out
> Exam questions love chaining these — find V_k, then D_k, then U_k or X_k, in that order.
