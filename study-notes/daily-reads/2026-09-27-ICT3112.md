## The Seven ISTQB Principles

Testing is never a random activity — ISTQB codifies seven guiding principles that shape how a professional test strategy is built, and exam questions love to test whether you can tell them apart.

The two easiest to confuse are the pesticide paradox and defect clustering. The pesticide paradox says that running an unchanged regression suite repeatedly eventually stops finding new defects — the bugs that suite is capable of catching have all been caught, so the suite needs to be revised and extended, not simply re-run. Defect clustering is a different claim: defects are not spread evenly across a codebase — roughly 80% of defects cluster in about 20% of modules (a Pareto distribution), so risk-based testing should deliberately weight effort towards those hotspots rather than spreading it evenly.

Two more principles sit either side of what testing can prove. "Testing shows presence of defects" means a passing suite tells you defects exist somewhere it happened to look — it can never prove their absence. The "absence-of-errors fallacy" goes further: even a system with zero known defects can still fail if it does not do what the user actually needs — correctness is not the same as usefulness. "Exhaustive testing is impossible" is the principle behind risk-based prioritisation: since every input combination cannot be tested, effort must be focused using risk analysis. "Early testing saves cost" reflects the shift-left philosophy — finding defects before they become embedded and expensive to fix. "Testing is context-dependent" means a safety-critical medical device and a marketing website warrant very different testing strategies.

> [!warning] Watch out
> Exam questions often describe a scenario ("the same suite has run for six months without finding a bug") and ask you to name the principle at play — that is the **pesticide paradox**, not defect clustering.

**Mnemonic:** Teach Every Eager Developer Proper Testing Approaches — T-E-E-D-P-T-A walks through all seven in order.

## Boundary Value Analysis (BVA)

Where Equivalence Partitioning (EP) picks one representative value from inside each partition, Boundary Value Analysis targets the edges of those partitions directly — defects statistically cluster at boundaries (off-by-one errors, wrong comparison operators, and so on).

For a valid numeric range such as 0–100, basic BVA tests the two boundary values themselves (0 and 100) plus the two values just outside the valid range (−1 and 101). Extended BVA adds one more layer: the values just inside each boundary (1 and 99), giving six test values across the range.

The same idea carries over to strings and sets. For a "1–10 capital letters" field, boundaries exist on two independent dimensions — string length (1 and 10 characters, e.g. "G" and "BORDERNAME") and character range (ASCII 'A' to 'Z', with "@" just below 'A' as an invalid boundary) — and these must be tested in **separate** test cases. If a single test combines an out-of-range length with an out-of-range character and it fails, you cannot tell which boundary actually caused the failure.

Four general rules extend BVA beyond simple numeric ranges: (1) for any specified range, test both ends plus one step beyond each; (2) when no range is specified, test the min and max of the domain plus one value below and one above; (3) for sets of values, test each value and the set's size limits — for files, test the first and last records; (4) test any extreme input or output condition you can identify, even if not explicitly specified.

> [!warning] Watch out
> Rule 4 exists precisely to catch students who only think about **input** ranges — output boundaries need testing too. BVA is explicitly described as complementary to Equivalence Partitioning, not a replacement for it.

## Basic Musa Reliability Model

The Basic Musa model treats software reliability growth as an exponential decay process: every fault fixed reduces the failure intensity by the same fixed amount, because faults are assumed to be roughly uniform in how often they trigger and how severely they affect failure rate.

Two equations matter. Failure intensity at execution time τ is λ(τ) = λ₀ × e^(−λ₀τ/ν₀), and expected cumulative failures by time τ is μ(τ) = ν₀ × [1 − e^(−λ₀τ/ν₀)], where λ₀ is the initial failure intensity and ν₀ is the total number of failures expected over the software's life if testing continued indefinitely.

**Worked check:** with λ₀ = 2, ν₀ = 10, τ = 5, the exponent is −λ₀τ/ν₀ = −(2×5)/10 = −1. That gives λ(5) = 2 × e⁻¹ ≈ 0.736 failures/time unit, and μ(5) = 10 × (1 − e⁻¹) ≈ 6.32 expected cumulative failures.

The Basic model suits stable, mature releases where the assumption of evenly distributed fault severity roughly holds. It contrasts with the Logarithmic Musa model, which assumes early faults are far more severe than later ones, so failure intensity decreases logarithmically instead of at a constant rate.

> [!warning] Watch out
> Don't confuse ν₀ (a fixed total count) with λ(τ) (a rate that keeps falling over time) — mixing them up is the single most common Musa-model exam error.

**Mnemonic:** ν₀ is the "volume" of failures ever expected; λ is the "live" rate right now.
