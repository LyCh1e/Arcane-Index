## ICT3112 — Software Verification and Validation

### Cyclomatic Complexity

Cyclomatic complexity, introduced by Thomas McCabe in 1976, gives you a single number that represents the minimum number of independent paths through a module — and therefore the minimum number of test cases needed to guarantee at least branch coverage.

**Formula:**

$$C = E - N + 2$$

where **E** is the number of edges in the Control Flow Graph (CFG) and **N** is the number of nodes.

**Worked Example — Factorial Function:**
The factorial CFG has 12 edges and 11 nodes, so:

$$C = 12 - 11 + 2 = 3$$

This means there are three independent (basis) paths, and you need at least three test cases:
- Path 1: `num < 0` → prints "nope"
- Path 2: `num = 0` → loop is skipped entirely
- Path 3: `num > 0` → loop runs at least once

**Why it matters for exams:** The complexity value tells you *both* the test case count *and* the risk level of the code.

| C Range | Risk Assessment |
|---------|----------------|
| 1–4 | Simple, low risk |
| 5–10 | Marginal, low risk |
| 11–20 | Moderate risk |
| 21–50 | High risk |
| > 50 | Untestable, very high risk |

> [!warning] Watch Out
> The back-edge in a loop (e.g. node 9 → node 6 in the factorial example) **is an edge and must be counted**. Students who forget the back-edge will under-count E by one and compute C = 2 instead of 3. Always trace every arrow in the CFG, including those pointing backwards.

**Memory hook:** "Edges minus Nodes plus 2 = paths to pursue."

### Decision / Branch Coverage

Decision coverage (also called branch coverage) requires every **decision outcome** — both the True branch and the False branch of every `if`, `while`, `for`, or `switch` statement — to be executed at least once. It is stronger than statement coverage because it is possible to achieve 100% statement coverage while leaving one branch of a decision untested.

**Formula:**

$$\text{Coverage \%} = \frac{\text{decision outcomes executed}}{\text{total decision outcomes}} \times 100$$

**Worked Example:**
Consider code with two decisions: an `if (num < 0)` and a `while (i <= num)`. Each decision has a True and a False outcome → 4 outcomes in total.

| Test Case | Input | if → True/False | while → True/False |
|-----------|-------|-----------------|-------------------|
| TC1 | num = −1 | **True** ✓ | **False** ✓ (loop skipped) |
| TC2 | num = 3 | **False** ✓ | **True** ✓ (loop runs) |

Two test cases cover all four decision outcomes → 100% decision coverage.

**Key property:** Decision coverage **subsumes** statement coverage — achieving decision coverage automatically gives you statement coverage. The reverse is not true.

> [!warning] Watch Out
> Do not confuse decision coverage with condition coverage. Decision coverage asks "did both outcomes of the entire decision fire?" Condition coverage asks "did each individual sub-condition take both True and False?" — and critically, condition coverage does **not** subsume decision coverage. It is entirely possible to achieve 100% condition coverage while never executing one branch of a compound decision. This distinction is a favourite exam question.

**Memory hook:** "Decision coverage = both branches walked; condition coverage = each sub-flag flipped."

### Equivalence Partitioning

Equivalence partitioning (EP) is a blackbox technique designed to minimise the number of test cases whilst maintaining broad input coverage. The fundamental insight is that if the system behaves identically for all values within a group (a *partition*), testing one representative value from that group tells you just as much as testing them all.

**Mechanism:**
1. Divide the input domain into partitions where every value produces the same result.
2. Identify both **valid** and **invalid** partitions — both must be tested.
3. Select **one representative value** from each partition.

**Worked Example — Integer input, valid range 0–100:**

```
◄──────────────────────────────────────►
   Invalid 1   |      Valid       | Invalid 2
    x < 0      |   0 ≤ x ≤ 100   |  x > 100
───────────────────────────────────────────
    e.g. −10          e.g. 50       e.g. 110
```

Minimum test set: **3 test cases** (one per partition). You do not need to test −9, −8, −7 … because they all represent the same invalid case.

EP can also be applied to **output** partitions, not only inputs.

> [!warning] Watch Out
> A very common mistake is to omit the invalid partitions entirely, testing only the valid range. Exam questions often ask for the "complete minimum test set" — this always includes representatives from invalid partitions as well. A test set that only tests valid inputs is incomplete by definition.

**Memory hook:** "One per partition — valid and invalid both count."

## ICT3113 — Performance Optimisation and Design

### Little's Law and the M/M/1 Queue

**Little's Law** is the single most important result in queueing theory. It states:

$$N = X \times R$$

where **N** is the average number of items in the system, **X** is the throughput (completions per unit time), and **R** is the average time each item spends in the system (response time). It holds for any stable system, regardless of arrival distribution, service distribution, or number of servers.

You can also apply it to the queue alone:

$$N_{queue} = X \times W$$

where **W** is the wait time (time spent in queue before service begins).

**Worked Example:**
An API server processes requests at a throughput of 10 requests per second. Each request spends an average of 0.4 seconds in the system. How many requests are in the system on average?

$$N = 10 \times 0.4 = 4 \text{ requests}$$

**The M/M/1 Queue** is the simplest analytical model: Markov (Poisson) arrivals at rate λ, Markov (exponential) service at rate μ, single server. The stability condition is ρ = λ/μ < 1.

Key results:

| Metric | Formula |
|--------|---------|
| Traffic intensity | ρ = λ/μ = λ × S |
| Wait in queue | W = ρ/(1−ρ) × S |
| Response time | R = S / (1−ρ) |

As ρ approaches 1, R grows without bound — the system becomes unstable and queues form indefinitely. This is why real systems are deliberately run below 70–80% utilisation: the relationship between utilisation and response time is highly non-linear, and small increases in load near saturation cause disproportionately large increases in wait time.

> [!warning] Watch Out
> In a short finite observation window, the mean of observed inter-arrival gaps does **not** equal 1/λ. Always compute λ as (number of arrivals) ÷ (total window length). Dividing by the mean gap will give you the wrong answer. This distinction is explicitly tested in exams.

**Memory hook:** "N = XR — jobs in system equals rate times residence."

### The Kingman Formula

Whilst the M/M/1 model assumes both arrivals and service times follow exponential distributions (coefficient of variation = 1 for both), real systems have variable service times — mixed workloads, long reports alongside fast lookups, bursty arrival patterns. The **Kingman formula** quantifies how variability inflates wait time:

$$W \approx \underbrace{\frac{\rho}{1-\rho}}_{\text{utilisation term}} \times \underbrace{\frac{C_a^2 + C_s^2}{2}}_{\text{variability term}} \times \underbrace{S}_{\text{service time}}$$

- **ρ/(1−ρ)** is the same utilisation-driven term as M/M/1
- **(Cₐ² + Cₛ²)/2** scales the wait up or down depending on variability
- **Cₐ** = coefficient of variation of inter-arrival times; **Cₛ** = coefficient of variation of service times
- When Cₐ = Cₛ = 1 (both exponential), the formula reduces exactly to the M/M/1 result

**Worked Example (ρ = 0.8, S = 100 ms):**

| Scenario | Cₐ² | Cₛ² | Variability term | W |
|----------|-----|-----|-----------------|---|
| Deterministic (regular) | 0 | 0 | 0 | ≈ 0 ms |
| M/M/1 (Poisson/Exp) | 1 | 1 | 1 | 4 × 1 × 100 = **400 ms** |
| Mixed workload | 1 | 4 | 2.5 | 4 × 2.5 × 100 = **1,000 ms** |

The utilisation term at ρ = 0.8 is 0.8/0.2 = **4**. The mixed workload has 2.5× the wait of M/M/1 — with *identical* hardware, load, and mean service time. The extra 600 ms comes purely from variance.

**Practical implication:** If your system shows high tail latency at moderate utilisation, variability — not capacity — is almost certainly the root cause. The fix is to separate heavy and light workloads into distinct queues to reduce Cₛ.

> [!warning] Watch Out
> Kingman applies to a **single server (G/G/1)**. For multiple servers, use Sakasegawa's approximation (which modifies the utilisation term). Do not apply the G/G/1 formula directly to a multi-server system.

**Memory hook:** "Kingman = utilisation × variability × service time — all three must be tamed."

## INF2005 — Cyber Security Fundamentals

### RSA Key Generation

RSA is an asymmetric encryption algorithm whose security rests on the practical impossibility of factoring the product of two large prime numbers. You must know the six-step key generation procedure for the exam.

**Six Steps:**

1. Pick two large distinct primes, **p** and **q**
2. Compute the modulus: **n = p × q**
3. Compute Euler's totient: **φ(n) = (p−1)(q−1)**
4. Choose public exponent **e** such that 1 < e < φ(n) and gcd(e, φ(n)) = 1 (i.e. e and φ(n) are coprime)
5. Compute private exponent **d** such that **d × e ≡ 1 mod φ(n)** (i.e. d is the modular multiplicative inverse of e)
6. **Public key = (e, n)** · **Private key = (d, n)**

**Encryption and Decryption:**
- Encrypt: C = Mᵉ mod n
- Decrypt: M = Cᵈ mod n

**Worked Example (small primes for illustration):**
- p = 5, q = 11 → n = 55, φ(n) = 4 × 10 = 40
- Choose e = 3 (gcd(3, 40) = 1 ✓)
- Find d: 3d ≡ 1 mod 40 → d = 27 (since 3 × 27 = 81 = 2×40 + 1)
- Public key = (3, 55) · Private key = (27, 55)

**Why it is secure:** An attacker knows e and n (both public), but cannot compute d without knowing φ(n), which in turn requires factoring n back into p and q — computationally infeasible for large n.

> [!warning] Watch Out
> Key generation uses modulus **φ(n)** — not n. Encryption and decryption use modulus **n** — not φ(n). These are different values. Mixing them up in an exam answer will cost marks. Also remember: the RSA private key is (d, n), **not** just d.

**Memory hook:** "Generation uses φ(n); encryption uses n — phi for private-key craft, n for message transform."

### LSB Steganography

Steganography hides the *existence* of a message, whereas cryptography hides its *content*. LSB (Least Significant Bit) steganography exploits the fact that altering only the rightmost bit of a pixel byte causes a value change of at most 1 out of 255 — visually imperceptible to the human eye.

**Core idea:** Replace (or adjust) the LSB of each pixel byte with one bit of the secret payload. A 1024×1024 RGB image has 3,145,728 pixel channels, giving a raw capacity of ~393 KB of hidden data.

**Two Variants:**

| Variant | How it works | Detectability |
|---------|-------------|---------------|
| **LSB Replacement** | Directly set the LSB to the payload bit | Higher — creates statistical asymmetry in pixel-value distribution |
| **LSB Matching** | If LSB ≠ payload bit, randomly add or subtract 1 from the pixel value | Lower — avoids the detectable hard-flip pattern |

LSB Matching is more resistant to statistical steganalysis because it avoids the signature left by pure replacement.

**Critical format constraint:** LSB steganography works only in **lossless image formats** — PNG, TIFF, BMP. JPEG uses lossy compression, which discards small bit-level changes during encoding, destroying any embedded payload.

**Bit plane insight:** Every colour channel can be decomposed into 8 bit planes (bit 0 = LSB, bit 7 = MSB). The LSB plane (bit 0) naturally resembles random noise even in unmodified images, which explains why embedding data there is visually imperceptible.

**Steganalysis:** To detect LSB Replacement, apply a visual attack — map even pixel values to black and odd pixel values to white. Hidden messages create structured patterns in this view, whereas a clean image appears as true random noise.

> [!warning] Watch Out
> JPEG will destroy your hidden data. Students regularly confuse image formats in exam questions. PNG is lossless and safe for LSB; JPEG is lossy and will corrupt the payload. Also note: LSB Replacement changes approximately 50% of LSBs on average (not 100%), because half the cover pixels already carry the correct bit value.

**Memory hook:** "LSB lives in lossless — PNG yes, JPEG no."
