# HCI Study Notes 01 - Introduction, History & User-Centered Design

## 1. Introduction to Human-Computer Interaction

### What is HCI?
- **Definition**: The study of how humans interact with computers and the design of computer interfaces that are usable and accessible
- **Key Distinction**: UI (User Interface) vs UX (User Experience) - "Same same, but different"
  - UI focuses on visual design and interface elements
  - UX encompasses the entire user experience and how it "feels" to use

### Why HCI is Important

#### Real-World Consequences of Poor Design
- **Air Inter Flight 148 (1992)**: 87 fatalities due to confusing cockpit interface
  - Pilot confusion between Flight Path Angle Mode vs. Vertical Speed Mode
  - Advanced digital instruments with poor usability
- **Anton Yelchin Incident (2016)**: Death caused by confusing E-Shifter design in Jeep
  - Vehicle rolled backwards due to unclear gear position feedback
- **Hawaii Missile Alert (2018)**: False missile warning sent to entire state
  - Poor dropdown menu design with obscure names and close placement

#### Daily User Frustrations
- Complex devices: TV remotes, smart watches, washing machines, microwaves
- Most users don't know how to use all features of their devices
- Poor design costs money, time, and potentially lives

### Good Design Principles
- **Easy, Efficient, and Enjoyable**: Not just visual appeal (UI) but overall experience (UX)
- Follows iterative process: Design → Implementation → Evaluation

## 2. History of HCI

### Early Foundations (1940s-1960s)

#### Visionary Concepts
- **Vannevar Bush - "As We May Think" (1945)**
  - Proposed the "Memex" - conceptual device for information storage/retrieval
  - Precursor to personal computers and hypertext systems
  - Connection to Oppenheimer era innovation

- **Ted Nelson - Hypertext**
  - Created the term "hypertext"
  - Project Xanadu - early vision of interconnected information

- **Tim Berners-Lee - World Wide Web**
  - Realized the hypertext vision globally

#### Early Computing Hardware
- **ENIAC**: First general-purpose, fully electronic digital computer
- **Mainframes**: Large, centralized computing systems

### Interface Evolution (1960s-1980s)

#### Input Innovations
- **Douglas Engelbart - The Mouse (1965)**
  - Revolutionary pointing device that changed human-computer interaction

#### Graphical Interface Development
- **Ivan Sutherland - Sketchpad (1963)**
  - First graphical user interface system
- **NLS Workstation (1968)**
  - Early demonstration of GUI concepts
- **Alan Kay - Dynabook & Smalltalk (1972)**
  - Vision of personal, portable computing
- **Xerox Star (1981)**
  - First commercial GUI workstation

### WIMP Paradigm
- **Windows, Icons, Menus, Pointing device**
- Became the dominant interface metaphor
- Foundation for modern desktop interfaces

### Direct Manipulation Interfaces
**Key Principles:**
- Continuous visibility of objects and actions
- Rapid, reversible, incremental actions with immediate feedback
- Replace command language with direct object manipulation
- Physical actions replace text commands

### Touch Interface Evolution
- **E.A. Johnson (1965)**: First finger-driven touchscreen
- **PLATO IV (1971)**: Infrared touchscreen terminal
- **HP-150 (1983)**: Early commercial touchscreen
- **Apple Newton (1993)**: First mainstream handheld with touch
- **Palm Pilot (1996)**: Successful PDA implementation

### Modern Computing Paradigms

#### Ubiquitous Computing (Mark Weiser, 1991)
- **Definition**: Computation embedded everywhere in our environment
- **Goal**: Make technology "transparent" and seamless
- **Vision**: "Computer for the 21st Century"
- Foundation for IoT and smart environments

#### Extended Reality (XR)
- **Milgram's Reality-Virtuality Continuum (1994)**
  - Real Environment ↔ Virtual Environment
  - Includes Augmented Reality (AR) and Mixed Reality (MR)
- **Modern XR**: VR, AR, MR technologies

### Current Trends in HCI
- **AI-Augmented Interfaces**: ChatGPT and conversational AI
- **Extended Reality**: AR, MR, VR applications
- **Multimodal Interaction**: Apple Vision Pro and beyond
- **Ethical HCI**: Responsible design considerations

## 3. User-Centered Design (UCD)

### What is UCD?
**ISO 13407 Definition**: "Human-centered design is characterized by: active involvement of users and clear understanding of user and task requirements; appropriate allocation of function between users and technology; iteration of design solutions; multi-disciplinary design."

### The Reality of Software Projects
Common disconnect between:
- What user described
- What project manager heard  
- What got designed
- What got implemented
- What user really wanted

### Core UCD Principles

#### 1. Early Focus on Users and Tasks
- Structured, systematic information gathering
- Approach users early and frequently
- Define clear tasks and user personas
- Understand user needs before designing solutions

#### 2. Empirical Measurement and Testing
- Focus on ease of learning and ease of use
- Test prototypes with actual users
- Make decisions based on data, not assumptions
- Measure usability objectively

#### 3. Iterative Design
- Product designed, modified, and tested repeatedly
- Early testing of conceptual models and design ideas
- Allow for complete design overhaul based on early feedback
- Continuous improvement throughout development

### UCD Process: Design → Implementation → Evaluation → (Repeat)

### Usability Activities by Development Stage

#### Concept Stage
- Define usability goals and objectives
- Create user profiles and personas
- Conduct interviews, field studies, task analysis

#### Design Stage  
- Create low-fidelity paper prototypes
- Perform heuristic evaluations
- Run focus groups and user interviews

#### Development Stage
- Plan and execute pre-release evaluations
- Conduct usability testing with prototypes
- Refine based on user feedback

#### Release Stage
- Formal usability testing with final product
- User surveys and interviews for feedback
- Site visits and post-deployment evaluation

### Key UCD Tools

#### Personas
- **Definition**: Fictional characters representing key user segments
- **Based on**: Real data and research, not assumptions
- **Purpose**: Represent different user types and build usage scenarios
- **Components**: Name, age, background, likes/dislikes, hobbies, goals

#### Paper Prototypes
- Low-cost, rapid way to test design concepts
- Allow early user feedback before development
- Easy to modify based on user input

#### Usability Testing
- Direct observation of users interacting with product
- Identifies real usability problems
- Provides concrete data for design decisions

### Benefits of UCD
- Reduces development costs through early problem identification
- Improves user satisfaction and adoption
- Creates products that truly meet user needs
- Minimizes post-launch redesign and support costs

## 4. Needfinding

### What is Needfinding?
**Definition**: The process of uncovering user needs that people may or may not be aware of, to guide innovation efforts and design decisions.

### Core Questions for Needfinding
1. **What do people do now?** - Current behaviors and workflows
2. **What values and goals do people have?** - Motivations and objectives  
3. **How are activities embedded in larger ecology?** - Context and environment
4. **What are similarities and differences across people?** - User diversity
5. **What other contexts matter?** - Time of day, location, social factors

### Why Needfinding is Critical
- **Uncover hidden needs**: Find needs users may not articulate or be aware of
- **Guide innovation**: Direct development efforts toward real problems
- **Define target users**: Identify specific user groups to design for
- **Understand emotions**: Discover emotional drivers behind behaviors

### Requirements Definition Process
1. **Understand user experience** by learning about their lives
2. **Define detailed requirements** for the system being developed
3. **Gather data** about what users need to do or accomplish
4. **Analyze and represent** collected data
5. **Interpret results** and use in design decisions
6. **Iterate** - continuous refinement throughout process

---

## Data Gathering Techniques for Needfinding

### 1. Observation
**Purpose**: Watch users do what they do in natural or controlled settings

#### Direct Observation
**Controlled (Lab) Setting:**
- **Advantages**: Controlled environment, consistent conditions, easier data collection
- **Disadvantages**: Artificial environment, may not reflect real usage patterns

**Field Setting:**
- **Advantages**: Natural environment, authentic behavior, rich contextual data
- **Disadvantages**: Less control, potential distractions, harder data collection

**Best Practices:**
- Take extensive photos, notes, and sketches
- Focus on specific task-relevant behaviors
- Video recording for later analysis and transcription
- Convert observations to abstract subtasks

#### Indirect Observation
- **Method**: Rely on reported observations from others or self-observations
- **Focus**: Effects or results of behavior rather than behavior itself
- **Examples**: Food diaries, app usage logs, activity trackers

#### Hawthorne Effect
- **Problem**: People perform differently when they know they're being observed
- **Impact**: Users may become nervous or alter natural behavior
- **Mitigation**: Longer observation periods, unobtrusive methods, building rapport

### 2. Ethnography
- **Origin**: Techniques from sociology and anthropology
- **Approach**: Deeply contextual inquiry - "live among" the users
- **Philosophy**: "Wallow in the data" to understand full behavioral complexity
- **Goal**: Understanding behavior in complete social context
- **Time Investment**: Extensive, long-term engagement

### 3. Surveys & Questionnaires
**Strengths**: Quantitative data, large sample sizes, standardized responses
**Weaknesses**: Limited depth, potential response bias, low response rates

#### Question Types
**Objective Questions:**
- Quantifiable and countable
- Multiple choice, checkboxes, yes/no, true/false

**Subjective Questions:**
- Open-ended responses in sentences
- Opinion and experience questions

#### Rating Scales
**Semantic Differential Scale:**
- Bipolar adjectives (e.g., Easy ←→ Difficult)
- Numerical scale between extremes

**Likert Scale:**
- Agree Strongly → Disagree Strongly
- Standard 5-point agreement scale

#### Survey Best Practices
- **Keep it short**: Fewer but better questions
- **Ensure anonymity**: Encourage honest responses  
- **Clear motivation**: Explain why survey matters
- **Start with research goals**: Align questions with objectives
- **Online tools**: SurveyMonkey, Google Forms for easier distribution and analysis

#### Common Survey Issues
- **Targeting**: Reaching the right users
- **Low response rates**: May not represent full user base
- **Response bias**: Self-selection effects
- **Ambiguous questions**: Misinterpretation of intent
- **Dishonest responses**: Social desirability bias

### 4. Interviews
**Purpose**: Rich, contextual data directly from users through face-to-face engagement

#### Interview Types
**Structured Interviews:**
- **Method**: Set script of questions
- **Advantages**: Efficient, consistent data
- **Disadvantages**: Limited flexibility, requires training

**Unstructured Interviews:**
- **Method**: No predetermined script
- **Advantages**: Natural conversation, unexpected insights
- **Disadvantages**: Difficult to manage, inefficient, hard to compare

**Semi-Structured Interviews:**
- **Method**: Script with flexibility to explore interesting answers
- **Advantages**: Good balance of efficiency and depth
- **Most Common**: Often the best choice for user research

#### Interview Process
**1. Introduction**
- Set context and expectations
- Establish rapport and trust

**2. Warm-up**
- Easy, comfortable questions
- Get participant talking

**3. Interview "Proper"**
- Core research questions
- Deep dive into specific topics

**4. Cool-down**
- Lighter questions
- Transition to closing

**5. Summary and Wrap-up**
- Recap key points
- Next steps and thank you

#### Effective Interview Questions
- "How do you perform task X?"
- "Why do you perform task X?"
- "What information do you need to...?"
- "Who do you need to communicate with to...?"
- "What do you use to...?"
- "What happens after you...?"
- "What is the result or consequence of NOT...?"

#### Interviewing Best Practices
- **Manage conversation flow** - stay focused but flexible
- **Listen more, talk less** - let participants share their stories
- **Use specific examples** - but don't dominate with your own stories
- **Create safe environment** - build trust before tough questions
- **Meta-monitor** - constantly assess how the interview is going

### 5. Focus Groups
**Structure**: Organized discussion with 3-10 participants representing different perspectives

**Advantages:**
- **Group dynamics**: Participants build on each other's ideas
- **Cost-effective**: Gather multiple perspectives efficiently
- **Quick insights**: Rapid way to understand preferences and views

**Challenges:**
- **Dominant participants**: Some may overshadow others
- **Group think**: Pressure to conform to group opinion
- **Facilitation**: Requires skilled moderator to manage dynamics

**Best Practices:**
- Use multiple groups with different roles/perspectives
- Audio/video record with permission
- Focus on preferences and views, not task performance
- Actively manage participation to ensure all voices heard

## Analyzing & Reporting Needfinding Data

### Data Analysis Process
1. **Digest and organize** collected data
2. **Identify patterns** and themes across data sources
3. **Infer insights** from collected information
4. **Create representations** using figures, charts, statistics, and descriptions
5. **Generate design recommendations** based on findings

### Key Outputs
- **User needs summary** - prioritized list of identified needs
- **User personas** - representative user archetypes
- **Use cases and scenarios** - how users accomplish goals
- **Design requirements** - specific system requirements
- **Opportunity areas** - gaps and innovation possibilities

### Reporting Best Practices
- **Visual representation**: Use charts, diagrams, and infographics
- **Specific examples**: Include quotes and real user stories  
- **Actionable insights**: Connect findings to design implications
- **Evidence-based**: Support conclusions with data
- **Stakeholder-focused**: Present in way that guides decision-making

## 5. Task Analysis

### What is Task Analysis?
**Definition**: The study of the way people perform their jobs and achieve their intended goals.

### Purpose of Task Analysis
**Primary Goals:**
- Determine **what people do** in their current workflows
- Identify **what tools and resources** they use
- Understand **what knowledge** they must possess
- Better understand user needs and identify tasks the application must support

### Two Types of Knowledge
**Declarative Knowledge:**
- **Definition**: Objects and relationships
- **Example**: "A scooter has a handle and a brake"
- **Focus**: What things are and how they relate

**Procedural Knowledge:**
- **Definition**: Task sequences, goals, subgoals, dependencies, constraints
- **Example**: "Press the brake with right foot to stop the scooter to avoid an obstacle"
- **Focus**: How things are done and in what order

### Task Analysis vs. Other Approaches
**Task Analysis Focus:**
- Users and existing tasks (not desired system)
- Observable behavior and whole job (not internal mental states)
- Complete workflows (not isolated unit tasks)

**Systems Analysis Focus:**
- Desired system functionality
- Technical requirements and constraints

**Cognitive Models Focus:**
- Internal mental processes
- Individual cognitive actions

### Key Questions Task Analysis Answers
- What are users' goals and what are they trying to achieve?
- What do users actually do to achieve those goals?
- What experiences (personal, social, cultural) do users bring?
- How does physical environment influence users?
- How do users' previous knowledge and experience influence:
  - How they think about their work
  - The workflow they follow

---

## Task Analysis Approaches

### 1. Task Decomposition
**Goal**: Break down complex tasks into manageable subtasks
**Most Common Method**: Hierarchical Task Analysis (HTA)

#### Hierarchical Task Analysis (HTA)
**Process:**
1. **Get list of tasks** from observation/interviews
2. **Group tasks** into higher-level categories
3. **Decompose** lowest-level tasks further as needed

**Stopping Rules:**
- **Purpose-driven**: Expand only tasks relevant to design goals
- **Motor actions**: Stop at lowest sensible level of physical actions
- **Simplicity**: Don't over-decompose obvious actions

#### HTA Example: Booking Doctor's Appointment Online
```
Hierarchical Description:
0. Book an appointment
  1. Choose doctor  
  2. Select date/time
  3. Confirm details
  4. Receive confirmation

Plans:
Plan 0: Do 1, 2, 3, 4 in order
```

#### HTA Example: Cleaning Home
```
Hierarchy Description:
0. Clean the house
  1. Get the vacuum cleaner out
  2. Get the appropriate attachment  
  3. Clean the rooms
    3.1 Clean the living room
    3.2 Clean the kitchen
    3.3 Clean the bedrooms
  4. Empty the dust bag
  5. Put vacuum cleaner and attachments away

Plans:
Plan 0: Do 1, 2, 3, 5 in order; when dust bag full, do 4
Plan 3: Do 3.1, 3.2, 3.3 in any order, as needed
```

#### HTA Refinement Heuristics
- **Paired actions**: Look for missing complementary actions (e.g., "turn on" needs "turn off")
- **Restructure**: Group related subtasks into higher-level tasks
- **Balance**: Ensure subtasks are at similar levels of complexity
- **Generalize**: Consider variations (one cup vs. multiple cups of tea)

### 2. Knowledge-Based Analysis
**Goal**: Understand knowledge required for task performance

#### Applications
- **Training materials**: What users need to learn
- **Documentation**: How-to manuals and guides  
- **Knowledge transfer**: Leverage common knowledge across tasks

#### Focus Areas
- **Objects**: Tools, materials, information used in tasks
- **Actions**: Operations performed on objects
- **Relationships**: How objects and actions connect

#### Taxonomies for Organization
**Purpose**: Represent different levels of abstraction and grouping
**Organization**: Depends on intended use and user mental models

#### Car Control Taxonomy Example
```
Motor Controls
├── Steering: steering wheel, indicators
├── Engine/Speed: ignition, accelerator, foot brake  
├── Gearing: clutch, gear stick
├── Lights
│   ├── External: headlights, hazard lights
│   └── Internal: cabin light
├── Wash/Wipe
│   ├── Wipers: front wipers, rear wipers
│   └── Washers: front washers, rear washers
├── Heating: temperature control, air direction, fan
└── Parking: hand brake, door lock
```

### 3. Task Descriptive Hierarchy (TDH)
**Method**: Task Analysis for Knowledge Description (TAKD)

#### Three Types of Branches
**XOR (Exclusive OR):**
- **Rule**: Object in exactly one branch
- **Example**: Shape is either dished OR flat (not both)

**AND:**
- **Rule**: Object must be in both branches  
- **Example**: Kitchen item has both shape AND function

**OR (Inclusive OR):**
- **Rule**: Can be in one, many, or none
- **Example**: Item can have multiple functions

#### TDH Example: Kitchen Items
```
Kitchen Item (AND)
├── Shape (XOR)
│   ├── Dished: mixing bowl, casserole, saucepan, soup bowl, glass
│   └── Flat: plate, chopping board, frying pan
└── Function (OR)
    ├── Preparation: mixing bowl, plate, chopping board
    ├── Cooking: frying pan, casserole, saucepan  
    └── Dining (XOR)
        ├── For food: plate, soup bowl, casserole
        └── For drink: glass
```

#### TDH Example: Flight Booking
```
0. Complete flight booking
├── 1. Choose travel type (XOR)
│   ├── 1.1 One-way
│   └── 1.2 Round-trip  
├── 2. Add optional services (OR)
│   ├── 2.1 Extra baggage
│   ├── 2.2 In-flight meals
│   └── 2.3 Seat selection
└── 3. Confirm passenger info (AND)
    ├── 3.1 Name matches ID
    └── 3.2 Contact details complete
```

### 4. Entity-Relationship Techniques
**Focus**: Objects, actions, and their relationships in the domain
**Emphasis**: Domain understanding rather than implementation details
**Scope**: Includes non-computer entities and relationships

**Example**: "Gardener digs soil using spade"
- **Entity**: Gardener (person)
- **Action**: Digs (process)  
- **Entity**: Soil (object)
- **Tool**: Spade (instrument)

## Task Analysis Summary

### Key Benefits
- **Understanding current workflows**: How work actually gets done
- **Identifying user needs**: What system must support
- **Training and documentation**: What users need to know
- **Design guidance**: How to structure interfaces and interactions

### Process Overview
1. **Determine data needed** to describe current tasks
2. **Gather data** using appropriate observation and interview methods
3. **Represent tasks** using hierarchies, taxonomies, or diagrams
4. **Apply insights** to improve system design

### Choosing the Right Approach
- **Task Decomposition (HTA)**: When you need to understand workflow sequences
- **Knowledge-Based Analysis**: When creating training or documentation
- **Entity-Relationship**: When understanding domain complexity and relationships

### Integration with Design Process
Task analysis findings directly inform:
- **User interface structure**: How to organize features and navigation
- **Interaction design**: What actions users need to perform
- **Information architecture**: How to present and organize content
- **User testing scenarios**: Realistic tasks for usability evaluation

- **User needs summary** - prioritized list of identified needs
- **User personas** - representative user archetypes
- **Use cases and scenarios** - how users accomplish goals
- **Design requirements** - specific system requirements
- **Opportunity areas** - gaps and innovation possibilities

### Reporting Best Practices
- **Visual representation**: Use charts, diagrams, and infographics
- **Specific examples**: Include quotes and real user stories  
- **Actionable insights**: Connect findings to design implications
- **Evidence-based**: Support conclusions with data
- **Stakeholder-focused**: Present in way that guides decision-making

---

## 2. Task Analysis

### What is Task Analysis?
**Definition**: The study of the way people perform their jobs and achieve their intended goals.

### Purpose of Task Analysis
**Primary Goals:**
- Determine **what people do** in their current workflows
- Identify **what tools and resources** they use
- Understand **what knowledge** they must possess
- Better understand user needs and identify tasks the application must support

### Two Types of Knowledge
**Declarative Knowledge:**
- **Definition**: Objects and relationships
- **Example**: "A scooter has a handle and a brake"
- **Focus**: What things are and how they relate

**Procedural Knowledge:**
- **Definition**: Task sequences, goals, subgoals, dependencies, constraints
- **Example**: "Press the brake with right foot to stop the scooter to avoid an obstacle"
- **Focus**: How things are done and in what order

### Task Analysis vs. Other Approaches
**Task Analysis Focus:**
- Users and existing tasks (not desired system)
- Observable behavior and whole job (not internal mental states)
- Complete workflows (not isolated unit tasks)

**Systems Analysis Focus:**
- Desired system functionality
- Technical requirements and constraints

**Cognitive Models Focus:**
- Internal mental processes
- Individual cognitive actions

### Key Questions Task Analysis Answers
- What are users' goals and what are they trying to achieve?
- What do users actually do to achieve those goals?
- What experiences (personal, social, cultural) do users bring?
- How does physical environment influence users?
- How do users' previous knowledge and experience influence:
  - How they think about their work
  - The workflow they follow

---

## Task Analysis Approaches

### 1. Task Decomposition
**Goal**: Break down complex tasks into manageable subtasks
**Most Common Method**: Hierarchical Task Analysis (HTA)

#### Hierarchical Task Analysis (HTA)
**Process:**
1. **Get list of tasks** from observation/interviews
2. **Group tasks** into higher-level categories
3. **Decompose** lowest-level tasks further as needed

**Stopping Rules:**
- **Purpose-driven**: Expand only tasks relevant to design goals
- **Motor actions**: Stop at lowest sensible level of physical actions
- **Simplicity**: Don't over-decompose obvious actions

#### HTA Example: Booking Doctor's Appointment Online
```
Hierarchical Description:
0. Book an appointment
  1. Choose doctor  
  2. Select date/time
  3. Confirm details
  4. Receive confirmation

Plans:
Plan 0: Do 1, 2, 3, 4 in order
```

#### HTA Example: Cleaning Home
```
Hierarchy Description:
0. Clean the house
  1. Get the vacuum cleaner out
  2. Get the appropriate attachment  
  3. Clean the rooms
    3.1 Clean the living room
    3.2 Clean the kitchen
    3.3 Clean the bedrooms
  4. Empty the dust bag
  5. Put vacuum cleaner and attachments away

Plans:
Plan 0: Do 1, 2, 3, 5 in order; when dust bag full, do 4
Plan 3: Do 3.1, 3.2, 3.3 in any order, as needed
```

#### HTA Refinement Heuristics
- **Paired actions**: Look for missing complementary actions (e.g., "turn on" needs "turn off")
- **Restructure**: Group related subtasks into higher-level tasks
- **Balance**: Ensure subtasks are at similar levels of complexity
- **Generalize**: Consider variations (one cup vs. multiple cups of tea)

### 2. Knowledge-Based Analysis
**Goal**: Understand knowledge required for task performance

#### Applications
- **Training materials**: What users need to learn
- **Documentation**: How-to manuals and guides  
- **Knowledge transfer**: Leverage common knowledge across tasks

#### Focus Areas
- **Objects**: Tools, materials, information used in tasks
- **Actions**: Operations performed on objects
- **Relationships**: How objects and actions connect

#### Taxonomies for Organization
**Purpose**: Represent different levels of abstraction and grouping
**Organization**: Depends on intended use and user mental models

#### Car Control Taxonomy Example
```
Motor Controls
├── Steering: steering wheel, indicators
├── Engine/Speed: ignition, accelerator, foot brake  
├── Gearing: clutch, gear stick
├── Lights
│   ├── External: headlights, hazard lights
│   └── Internal: cabin light
├── Wash/Wipe
│   ├── Wipers: front wipers, rear wipers
│   └── Washers: front washers, rear washers
├── Heating: temperature control, air direction, fan
└── Parking: hand brake, door lock
```

### 3. Task Descriptive Hierarchy (TDH)
**Method**: Task Analysis for Knowledge Description (TAKD)

#### Three Types of Branches
**XOR (Exclusive OR):**
- **Rule**: Object in exactly one branch
- **Example**: Shape is either dished OR flat (not both)

**AND:**
- **Rule**: Object must be in both branches  
- **Example**: Kitchen item has both shape AND function

**OR (Inclusive OR):**
- **Rule**: Can be in one, many, or none
- **Example**: Item can have multiple functions

#### TDH Example: Kitchen Items
```
Kitchen Item (AND)
├── Shape (XOR)
│   ├── Dished: mixing bowl, casserole, saucepan, soup bowl, glass
│   └── Flat: plate, chopping board, frying pan
└── Function (OR)
    ├── Preparation: mixing bowl, plate, chopping board
    ├── Cooking: frying pan, casserole, saucepan  
    └── Dining (XOR)
        ├── For food: plate, soup bowl, casserole
        └── For drink: glass
```

#### TDH Example: Flight Booking
```
0. Complete flight booking
├── 1. Choose travel type (XOR)
│   ├── 1.1 One-way
│   └── 1.2 Round-trip  
├── 2. Add optional services (OR)
│   ├── 2.1 Extra baggage
│   ├── 2.2 In-flight meals
│   └── 2.3 Seat selection
└── 3. Confirm passenger info (AND)
    ├── 3.1 Name matches ID
    └── 3.2 Contact details complete
```

### 4. Entity-Relationship Techniques
**Focus**: Objects, actions, and their relationships in the domain
**Emphasis**: Domain understanding rather than implementation details
**Scope**: Includes non-computer entities and relationships

**Example**: "Gardener digs soil using spade"
- **Entity**: Gardener (person)
- **Action**: Digs (process)  
- **Entity**: Soil (object)
- **Tool**: Spade (instrument)

---

## Task Analysis Summary

### Key Benefits
- **Understanding current workflows**: How work actually gets done
- **Identifying user needs**: What system must support
- **Training and documentation**: What users need to know
- **Design guidance**: How to structure interfaces and interactions

### Process Overview
1. **Determine data needed** to describe current tasks
2. **Gather data** using appropriate observation and interview methods
3. **Represent tasks** using hierarchies, taxonomies, or diagrams
4. **Apply insights** to improve system design

### Choosing the Right Approach
- **Task Decomposition (HTA)**: When you need to understand workflow sequences
- **Knowledge-Based Analysis**: When creating training or documentation
- **Entity-Relationship**: When understanding domain complexity and relationships

### Integration with Design Process
Task analysis findings directly inform:
- **User interface structure**: How to organize features and navigation
- **Interaction design**: What actions users need to perform
- **Information architecture**: How to present and organize content
- **User testing scenarios**: Realistic tasks for usability evaluation

# HCI Study Notes 03 - Ethics and Usability Principles

## 1. Ethics in HCI

### What is Ethics?
**Definition**: Principles of right and wrong that individuals, acting as free moral agents, use to make choices to guide their behaviors.

**Purpose**: A process that guides decision-making in situations with conflicting goals by:
- Making informed, justified decisions
- Applying values to practice

### Why Ethics Matters in HCI
**Human Involvement**: HCI requires participation of human subjects, which creates ethical responsibilities because:
- Human behavior is examined
- Personal information is collected
- Results or products of human behavior are examined

### Historical Context - Unethical Research

#### Nazi Medical Experiments (Early 1940s)
- Medical experiments conducted on concentration camp prisoners
- No consent, extreme harm, scientific misconduct
- Led to Nuremberg Code establishing research ethics

#### Tuskegee Syphilis Experiment (1932-1972)
- U.S. Public Health Service study on untreated syphilis
- African American men deceived about receiving treatment
- Continued even after penicillin was discovered as cure
- Major breach of informed consent and beneficence

#### Milgram Experiment (1963)
- Studied obedience to authority figures
- Participants believed they were administering painful electric shocks
- Psychological distress without proper informed consent
- Raised questions about deception in research

---

## Ethical Principles and Frameworks

### Classical Ethical Guidelines

#### Golden Rule
**Principle**: "Do unto others as you would have them do unto you"
**Application**: Design and research decisions should consider how you would want to be treated

#### Immanuel Kant's Categorical Imperative
**Principle**: "If an action is not right for everyone to take, it is not right for anyone"
**Application**: Universal applicability test for ethical decisions

#### Descartes' Rule of Change
**Principle**: "If an action cannot be taken repeatedly, it is not right to take at all"
**Application**: Consider long-term sustainability of actions

### Modern Ethical Principles

#### 1. Utilitarian Principle
**Definition**: Take the action that achieves the higher or greater value
**HCI Examples:**
- Simplifying app interface for broader accessibility, even if sacrificing advanced features
- Developing pandemic tracking app despite privacy concerns for collective benefit

#### 2. Risk Aversion Principle
**Definition**: Take the action that produces the least harm or potential cost
**HCI Examples:**
- Designing confirmation prompts before deleting important data
- Choosing end-to-end encryption despite slightly complicating user experience

#### 3. Ethical "No Free Lunch" Rule
**Definition**: Assume all tangible and intangible objects are owned by someone unless specifically declared otherwise
**HCI Example:**
- Not using user-uploaded content for AI training without informed consent

---

## The Belmont Report (1979) - Core Principles

### 1. Respect for Persons
**Requirements:**
- Protect freedom and capacity of participants
- Protect vulnerable people
- **Informed consent is essential**

### 2. Beneficence
**Requirements:**
- Secure well-being of participants
- **Minimize possible harm**
- Maximize benefits

### 3. Justice
**Requirements:**
- **Fairness in distribution** of risks and benefits
- Equitable selection of participants
- Avoid exploitation of vulnerable populations

---

## General Ethical Responsibilities in HCI

### Safety
**Requirements:**
- Do not cause physical or psychological harm
- Inform participants about what will happen
- **Participants must be able to stop at any point**
- Provide clear exit procedures

### Informed Consent
**Information to Provide:**
- Explain goals and procedures clearly
- Specify what information will be recorded
- Describe how results will be used
- Outline potential risks and benefits

**Requirements:**
- Participants must understand and agree voluntarily
- Consent must be ongoing (can be withdrawn)
- Special protections for vulnerable populations

### Privacy Protection
**Data Management:**
- Prevent unauthorized access to information
- **Don't collect unnecessary data**
- Use data only for consented purposes
- **Destroy data when no longer needed**
- Ensure anonymity and confidentiality

**Implementation Methods:**
- Data anonymization techniques
- Secure storage and transmission
- Access controls and audit trails
- Clear data retention policies

### Institutional Review Board (IRB)
**Purpose**: Administrative body to protect rights and welfare of human research subjects
**Responsibilities:**
- Review all research involving human participants
- Ensure compliance with laws and regulations
- Ongoing monitoring of approved research

**Singapore Context:**

#### Human Biomedical Research Act 2015 (HBRA)
**Authority**: Ministry of Health

**Focus**: Medical and health-related research

## Real-World Ethical Failures

**Issue**: Unauthorized harvesting of personal data for political advertising
**Lessons**: Consent, data use limitations, third-party access controls

### Google Photos Tagging Incident (2015)
**Issue**: AI system tagged Black people as "gorillas"

### TikTok Content Moderation Bias

## 2. Usability Principles

### Definition of Usability
**ISO 9241-11**: "The extent to which a product can be used by specified users to achieve specified goals with effectiveness, efficiency and satisfaction in a specified context of use."

**Key Characteristics of Usable Systems:**
- Easy to learn
- Easy to memorize
- Efficient to use
- Visually appealing
- Fast recovery from errors

### Design Principles & Heuristics
**Purpose**: Broad usability statements that guide design efforts
**Function**: "Rules of thumb" describing features of usable systems
**Derivation**: From evaluating common design problems across many systems
**Goals**: Avoid common design pitfalls and inspect interfaces for usability problems

---

## Norman's Usability Principles

### 1. Affordance
**Definition**: Perceived and actual properties of an object that suggest how it can be used
**Key Concept**: "Much of everyday knowledge resides in the world, not in the head"

**Examples:**
- Door handles suggest pushing or pulling
- Chair affords sitting
- Ball affords throwing
- Teapot handles afford grasping

**Design Implication**: Object form should suggest its function

### 2. Signifiers
**Definition**: Signals or indications that communicate how to use an object
**Norman's Quote**: "Any physically perceivable cue, whether incidental or deliberate"

**Function**: Bridge between affordances and user understanding
**Examples:**
- Push/pull signs on doors
- Icons indicating clickable elements
- Visual cues showing interactive areas

### 3. Visibility
**Definition**: How easily features or capabilities can be seen and understood

**Key Principle**: Users shouldn't need instructions for basic operations
**Examples:**
- Hotel bathroom controls should be intuitive
- Shower diverters should be obvious
- Important functions should be prominently displayed

**Common Problem**: Hidden or unclear interface elements

### 4. Feedback
**Definition**: Information sent back about what action has been performed

**Types of Feedback:**
- **Audio**: Beeps, clicks, sounds
- **Visual**: Changes in appearance, progress indicators
- **Verbal**: Spoken confirmations or instructions
- **Tactile**: Vibrations, resistance, texture changes

**Examples:**
- Progress bars showing completion percentage
- Button state changes when pressed
- Cursor changes indicating different modes
- Loading indicators for longer operations

### 5. Mapping
**Definition**: Relationship between controls and their actions or results

**Good Mapping**: Clear, logical relationship between cause and effect
**Poor Mapping**: Confusing or arbitrary relationships

**Examples:**
- **Good**: Steering wheel rotation maps to car direction
- **Poor**: Climate control layouts where button placement doesn't match air vent locations
- **Complex**: Modern car climate controls vs. traditional knobs

### 6. Constraints
**Definition**: Limits to the perceived operation of a device

#### Types of Constraints:

**Physical Constraints:**
- Shape prevents incorrect assembly
- Size limitations guide proper use
- Physical barriers prevent wrong actions

**Semantic Constraints:**
- Meaning-based limitations
- Cultural understanding of symbols
- Logical relationships between function and form

**Cultural Constraints:**
- Social conventions and expectations
- Learned behaviors from cultural context
- Shared understanding of symbols and meanings

**Logical Constraints:**
- Reasoning-based limitations
- Natural relationships between controls and functions
- Cause-and-effect relationships

---

## Conceptual vs. Mental Models

### Conceptual Model
**Definition**: Simplified explanation or framework for understanding how something works
**Characteristics**: Formal, structured, logical
**Source**: Designer's intended model

### Mental Model  
**Definition**: Models people have of themselves, others, environment, and interactive objects
**Characteristics**: Informal, incomplete, sometimes erroneous
**Source**: User's understanding and experience

### System Image
**Definition**: Information conveyed by the product itself
**Function**: Bridge between designer's conceptual model and user's mental model
**Importance**: Primary means of communicating design intent

### Design Challenge
**Goal**: Align user's mental model with designer's conceptual model through clear system image
**Problem**: Gaps between intended design and user understanding
**Solution**: Clear signifiers, feedback, and consistent interaction patterns

---

## Gulf of Execution and Evaluation

### Gulf of Execution
**Question**: "How do I know what I can do?"
**Definition**: Effort required to tell the system what to do

#### Stages of Action:
1. **Forming the Goal**
   - Something to be achieved
   - Example: "Want to eat noodles"

2. **Forming the Intention**
   - Specifics of what to do to satisfy goal
   - Example: "Reheat instant noodles in microwave"

3. **Specifying Sequence of Actions**
   - Precise sequence for the system
   - Example: "Open door, place noodles, press buttons..."

4. **Execution of Action Sequence**
   - Actually performing the actions

### Gulf of Evaluation
**Question**: "How do I know what happened?"
**Definition**: Effort required to interpret the system's response

#### Stages of Evaluation:
1. **Perceiving State of World**
   - Experience what actually happened
   - Example: Hear beep, feel warmth, smell food

2. **Interpreting Perceived State**
   - Making sense of perceptions
   - Example: "Beep from microwave, smell from noodles"

3. **Evaluation of Interpretations**
   - Compare what happened with what was wanted
   - Example: "Noodles are heated, goal achieved"

### Design Goal: Bridge the Gulfs
**Reduce Gulf of Execution**: Make actions obvious and easy to perform
**Reduce Gulf of Evaluation**: Provide clear feedback about system state and results

---

## Norman's 7 Design Principles

1. **Use both knowledge in the world and knowledge in the head**
   - Don't rely solely on user memory
   - Provide environmental cues and reminders

2. **Simplify the structure of tasks**
   - Break complex tasks into simple steps
   - Reduce cognitive load

3. **Make things visible: bridge the gulfs of Execution and Evaluation**
   - Show possible actions clearly
   - Provide obvious feedback

4. **Get the mappings right**
   - Ensure controls relate logically to their functions
   - Use spatial and temporal relationships

5. **Exploit the power of constraints, both natural and artificial**
   - Use constraints to guide correct actions
   - Prevent errors through design

6. **Design for error**
   - Assume users will make mistakes
   - Make errors reversible and recoverable

7. **When all else fails, standardize**
   - Follow established conventions
   - Use familiar patterns when clarity isn't achievable

---

## Nielsen's 10 Usability Principles (Heuristics)

1. **Visibility of System Status**
   - Keep users informed about what's happening
   - Provide appropriate feedback within reasonable time

2. **Match Between System and Real World**
   - Use familiar language, concepts, and conventions
   - Follow real-world metaphors and logic

3. **User Control and Freedom**
   - Provide "emergency exits" for unwanted actions
   - Support undo and redo functions

4. **Consistency and Standards**
   - Follow platform conventions
   - Maintain internal consistency

5. **Help Users Recognize, Diagnose and Recover from Errors**
   - Use plain language for error messages
   - Precisely indicate problems and suggest solutions

6. **Error Prevention**
   - Prevent problems from occurring
   - Use confirmations for irreversible actions

7. **Recognition Rather Than Recall**
   - Make objects, actions, and options visible
   - Minimize memory load

8. **Flexibility and Efficiency of Use**
   - Provide shortcuts for experienced users
   - Allow customization and personalization

9. **Aesthetic and Minimalist Design**
   - Remove irrelevant information
   - Focus on essential elements

10. **Help and Documentation**
    - Provide searchable, contextual help
    - Focus on user tasks and be concise

---

## Interface Metaphors

### Definition
**Metaphor**: Figure of speech applying familiar concepts to new domains
**UI Metaphor**: Transfer of relationships between objects to different interaction domains
**Purpose**: Give users instant knowledge about interface interaction

### Common UI Metaphors

#### Desktop Metaphor
**Elements**: Files, folders, trash/recycle bin, desktop surface
**Benefit**: Leverages familiar office environment concepts
**Limitation**: Some digital concepts don't map well to physical world

#### Examples of Metaphor Usage
- **Folders**: Organize and contain files
- **Files**: Individual documents or applications  
- **Desktop**: Primary workspace area
- **Trash/Recycle Bin**: Temporary holding for deleted items

### Design Considerations
**Strengths**: Immediate familiarity, reduced learning curve
**Weaknesses**: May limit innovation, not all functions map well to physical metaphors
**Balance**: Use metaphors where helpful, break them when digital capabilities exceed physical limitations

---

## Summary - Key Takeaways

### Ethics in HCI
- Human involvement requires ethical responsibility
- Follow established principles: respect for persons, beneficence, justice
- Obtain proper informed consent and protect privacy
- Consider long-term implications of design decisions
- Use institutional review processes appropriately

### Usability Principles  
- Design should bridge gaps between user understanding and system functionality
- Apply Norman's principles: affordance, signifiers, visibility, feedback, mapping, constraints
- Reduce gulfs of execution and evaluation through clear design
- Follow established heuristics (Nielsen's 10 principles) for systematic evaluation
- Use metaphors appropriately to leverage user knowledge
- Test designs with real users to identify usability problems

# HCI Study Notes 04 - Prototyping

## 1. What is a Prototype?

### Definition
**Prototype**: A rapid approximation of a design idea used to visualize, simulate, and evaluate how users might interact with a design.

**Purpose**: Concrete representation of abstract concepts before full development begins.

### Rights of a Prototype
**Fundamental Characteristics**:
- Should not be required to be complete
- Should be easy to change
- Gets to retire (can be discarded after serving its purpose)

### Why Prototype?

#### Core Benefits
- **Interactive exploration** with envisioned product
- **Clarifies vague requirements** through concrete communication between stakeholders  
- **Answers questions and supports design decisions** with forced reflection
- **Tests feasibility & compatibility**
- **Sells product ideas** to stakeholders
- **Inspires innovation**

#### Key Insight
**Fundamental Truth**: People cannot describe what they want, but they are quick to recognize what they do not like!

**Historical Example**: Palm Pilot wooden model by Jeff Hawkins (1995) - tested design with wooden model using chopstick as stylus, counting steps for common tasks in real meetings.

---

## 2. What Do Prototypes Prototype?

### Three Dimensions of Prototyping

#### 1. Feel
**Focus**: What might it look like?
**Explores**: Visual design, aesthetics, appearance

#### 2. Implementation  
**Focus**: What might it work like?
**Explores**: Technical functionality, system behavior

#### 3. Role
**Focus**: What might the experience be like?
**Explores**: User experience, workflow, interaction patterns

---

## 3. Conceptual Design

### Definition
**Conceptual Design**: A description of the proposed system in terms of integrated ideas and concepts about what it should do, behave, and look like, that will be understandable by users in the intended manner.

### Requirements for Early Design Expression
**Essential Characteristics**:
- Allow lots of flexibility for radically different designs
- No coding involved (yet)
- Must be fast and cheap
- Simulate the design in low-cost manner
- Promote valuable feedback
- Facilitate iterative design and evaluation

---

## 4. Storyboards

### Definition and Purpose
**Storyboard**: A pencil and paper simulation or walkthrough of system look and functionality.

**Structure**: Sequence of diagrams or drawings showing user progression through a task flow or use case.

**Key Point**: Not simply pretty pictures; a means of communicating ideas.

### Essential Elements Storyboards Should Convey

#### 1. Setting
- **People involved** in the interaction
- **Environment** where interaction takes place  
- **Task being accomplished**

#### 2. Sequence
- **What steps are involved** in the process?
- **What leads someone to use** the app?
- **What specific task** is being illustrated?

#### 3. Satisfaction
- **What motivates people** to use this system?
- **What does it enable people** to accomplish?
- **What need** does the system fill?

### Benefits of Storyboarding
- **Holistic focus** on complete user experience
- **Understand workflow** of proposed system
- **Emphasizes how interface accomplishes tasks**
- **Avoids commitment** to particular UI elements (no buttons yet)
- **Aligns stakeholders** on common goals
- **Enables early feedback** collection

### Relationship with Scenarios
**Scenarios**: Hypothetical or fictional situations of use that:
- Involve specific people, events, situations, and environments
- Provide context of operation
- Can be narrative, sketches, or videos
- Approach problems from another person's perspective
- Include social and interpersonal aspects
- Can be futuristic and creative
- Facilitate feedback and opinions

---

## 5. Prototype Fidelity

### Fidelity Progression Strategy
**Key Principle**: Prototypes should shift from Low-Fi to Hi-Fi as project progresses.

### Low-Fidelity Prototypes

#### Characteristics
- **Cheap to produce**
- **Does not realistically simulate** the final product
- **Focus on conceptual design**
- Uses medium unlike final product (e.g., paper, cardboard)
- Quick, cheap, and easy to modify
- Important early on to encourage creative flexibility

#### Types and Examples

**Paper Prototypes**:
- Hand-drawn interfaces on paper
- Physical mockups using cardboard, sticky notes
- Sketched user interfaces and workflows

**Wireframes**:
- Basic structural blueprints of pages/screens
- Focus on layout and functionality, not visual design
- Show content hierarchy and navigation structure

#### Benefits
- Encourages exploration of ideas during conceptual design
- Low investment allows for radical changes
- Focuses attention on functionality rather than aesthetics
- Promotes creative flexibility and experimentation

### High-Fidelity Prototypes

#### Characteristics
- **Increased similarity to final product**
- Possibly even using the same "parts"
- **Focus on physical design**
- Uses similar materials as final product
- "Looks like" the final product
- May include "real" code to demonstrate functions

#### Common High-Fidelity Tools
- **Justinmind**: http://www.justinmind.com/download
- **Axure**: http://www.axure.com/
- **Balsamiq**: https://balsamiq.com/
- **Visual Paradigm**: http://www.visual-paradigm.com/features/wireframing/
- **Dreamweaver**: For web-based prototypes

#### Benefits
- **Simulation or demo of final product** to address feasibility
- Addresses physical design issues
- Provides realistic user experience
- Better for testing specific interactions
- More convincing for stakeholder presentations

#### Issues and Drawbacks
- **Costlier to develop** and maintain
- **Can confuse boundary** between prototype and real product
- **Users confuse demo promise with real product** - sets high expectations
- **Software prototypes may have** slow performance, bugs, etc.
- **"Invisible" compromises** - hacked code, sloppy engineering
- **Pressure to recycle sloppy code** when creating final "quality" product

---

## 6. Horizontal vs. Vertical Prototypes

### Horizontal Prototypes
**Definition**: Wide range with little detail
**Characteristics**:
- Cover many features superficially
- Good for overall system architecture understanding
- Show breadth of functionality
- Useful for getting overview of complete system

### Vertical Prototypes  
**Definition**: Much detail for few functions
**Characteristics**:
- Deep dive into specific features
- Good for testing particular workflows
- Show depth of functionality
- Useful for exploring complex interactions in detail

### Visual Example Context
**System Components** (like e-commerce system):
- Product Search, Content Management, Full-Text Search
- Credit Card Authorization, Item Checkout
- A.I. Ranking & Scoring, Product Recommendations
- User Reviews, Product Catalog DB, Purchasing, Tracking Data

**Horizontal**: Touch all components lightly
**Vertical**: Deep implementation of few components (e.g., just search and checkout)

---

## 7. Video Prototyping

### Definition and Purpose
**Video Prototyping**: Used to illustrate how users will interact with a new system through video storytelling.

### Key Characteristics
- Often used to quickly represent **design concepts involving complex relationships**
- Requires **high level of technology** to implement
- Like a storyboard but in video format
- Shows the **whole task, including motivation and success**
- Uses establishing shots and narrative structure
- Draws on tasks observed during needfinding
- Illustrates important tasks the system enables
- Can help **scope a minimum-viable product**

### Benefits of Video Prototyping
- **Cheap and fast** to produce
- **Great communication tools** - easy to share and understand
- **Portable and self-explanatory**
- **Helps convey ideas to others** effectively
- **Ties interface designs to tasks** - shows context of use
- **Aligns and orients interface choices** with real-world usage
- **Ensures complete interface** (and identifies unnecessary elements)
- **May serve as specification** for developers

---

## 8. Wizard-of-Oz Prototyping

### Definition and Core Concept
**Wizard-of-Oz Prototyping**: Simulate machine behavior with human operators instead of actual system functionality.

**Key Mechanism**: User thinks they are interacting with a computer, but a human (the "wizard") is responding to the input behind the scenes.

**Goal**: Create interactive application without (much) code.

### System Architecture
**Components**:
- **Front end interface** - what user sees and interacts with
- **Remote wizard** (hidden human) controls user interface responses
- **Must be faster, cheaper, and easier** than building the real thing
- **Done early in design** to understand user requirements

### Implementation Process

#### Setup Phase: How to Make a Wizard-Powered Prototype

**1. Map out scenarios and system flow**
- Define what should happen in response to user behavior
- Plan system responses and state changes

**2. Put together interface "skeletons" (framework)**  
- Create basic interface structure
- Design visual elements user will see

**3. Develop "hooks" (places in system) for wizard input**
- **Where and how wizard will provide input**:
  - Selecting the next screen
  - Entering text responses
  - Triggering system events
  - Recognizing speech input
  - Processing user gestures

**4. Remember replacement requirement**
- This part will need to be replaced with computer functionality
- Design with eventual automation in mind

**5. Rehearse the wizard role with a friend**
- Practice responses and timing
- Test system flow and identify issues

#### Execution Phase: How to Run a Wizard-Powered Prototype

**1. Practice Phase**
- Practice with a friend first before real users
- Refine wizard responses and timing

**2. User Recruitment**
- Recruit actual "users" for testing sessions

**3. Role Assignment - Two roles required:**

**Facilitator Role**:
- Provides tasks (usually on paper)
- Takes notes during session
- Manages user interaction
- Conducts debriefing

**Wizard Role**:
- Operates interface (preferably hidden or remote)
- Responds to user inputs in real-time
- Simulates system behavior
- Remains invisible to user

#### User Feedback Collection Methods

**Think Aloud Protocol**:
- User speaks freely while performing tasks
- Provides real-time insight into thought process

**Retrospective Feedback**:
- Best when think aloud distracts from task
- Post-session discussion of experience

**Heuristic Evaluation**:
- Works with expert users too
- Structured evaluation of interface

**User Debriefing**:
- Reveal wizard if needed for complete feedback
- Discuss overall experience and suggestions

### Benefits of Wizard-of-Oz Prototyping
- **Faster, cheaper, and more iterative** prototypes
- **Creating multiple variations is easy**
- **More realistic than paper prototyping**
- **Identifies bugs and problems** with current design
- **Places user at center** of development process
- **Can envision challenging-to-build applications**
- **Designers and developers learn** by playing wizard role

### Disadvantages of Wizard-of-Oz Prototyping
- **May misrepresent imperfect technology** - creates unrealistic expectations
- **May simulate technologies that don't exist** (and may never exist)
- **Wizards require training** and can be inconsistent in responses
- **Playing wizard can be exhausting** - requires sustained attention
- **Some features difficult/impossible to simulate** effectively
- **May be inappropriate in some venues** (e.g., home settings, public spaces)

---

## 9. Testing Prototypes

### Best Practices for Prototype Testing
- **Test on multiple users** and other stakeholders
- **Test multiple prototypes simultaneously** to get most comparative value
- **Emphasize conversation** and dialogue with users
- **Use "think aloud" protocols** to understand user reasoning
- **Test iteratively with users early** in the process
- Focus on learning and iteration rather than validation

### Testing Goals
- Gather feedback for design improvement
- Identify usability issues early
- Validate design concepts with real users
- Understand user mental models and expectations

---

## 10. Design Process Flow

### Recommended Progression
**Needfinding → Storyboards → Lo-Fidelity Prototypes → Hi-Fidelity Prototypes**

#### Stage Purposes
**Needfinding**: Understand user problems and context
**Storyboards**: Visualize user scenarios and task flows  
**Lo-Fidelity Prototypes**: Explore concepts and gather early feedback
**Hi-Fidelity Prototypes**: Refine design and test specific interactions

### Iterative Nature
**Key Principle**: Each stage should inform and improve the next
**Feedback Integration**: Continuously incorporate user feedback throughout process
**Flexibility**: Be prepared to return to earlier stages based on learning

---

## Summary - Key Takeaways

### Fundamental Prototyping Concepts
- **Prototypes are rapid approximations** of design ideas used to gather feedback
- **Prototypes should be cheap, fast to create**, and easily modifiable
- **People recognize what they don't like** better than describing what they want
- **Test iteratively with users early** in the design process

### Fidelity and Progression
- **Start with low-fidelity** for concept exploration and flexibility
- **Progress to high-fidelity** for design refinement and validation
- **Lo-fi focuses on conceptual design**, hi-fi focuses on physical design
- **Each fidelity level serves different purposes** in the design process

### Specialized Prototyping Techniques
- **Storyboards communicate task flows** and user scenarios effectively
- **Video prototypes excel at showing complex interactions** and system context
- **Wizard-of-Oz enables testing advanced functionality** without full implementation
- **Horizontal prototypes show breadth**, vertical prototypes show depth

### Testing and Validation
- **Test multiple prototypes simultaneously** for comparative insights
- **Emphasize conversation and think-aloud** protocols during testing
- **Focus on learning over validation** in early prototype testing
- **Use appropriate fidelity** for the questions you need to answer

# HCI Study Notes 05 - Evaluation Methods

## 1. What is Evaluation?

### Definition
**Evaluation**: Gather data about the usability of a design for a particular activity by a specified group of users within a specified environment.

**Purpose**: Systematic assessment of interactive systems to ensure they meet user needs and design goals.

### Goals of Evaluation
- **Assess extent of system's functionality**
- **Assess effect of interface on user**
- **Identify specific problems with system**

---

## 2. Types of Evaluation

### Formative vs. Summative Evaluation

#### Formative Evaluation
**Definition**: Evaluation conducted as project is forming
**Characteristics**:
- **All through the lifecycle** - continuous process
- **Early, continuous, iterative** - ongoing assessment
- **"Evaluating the design"** - focuses on design process
- Aims to improve and refine the design

#### Summative Evaluation  
**Definition**: Evaluation conducted after a system has been finished
**Characteristics**:
- **Make judgments about final item** - assess completed product
- **"Evaluating the implementation"** - focuses on final product
- Determines if objectives were met

### Multiple Ways to Evaluate

#### Classification by Approach
**Empirical**: Assess with real users through observation and data collection
**Formal**: Models and formulas to calculate measures
**Automated**: Software measures and metrics
**Predictive/Critique**: Expertise and heuristic feedback

---

## 3. Empirical Evaluation

### Definition and Core Concept
**Empirical Evaluation**: Process of assessing a system or interface based on direct observation and data collected from real users.

**Key Characteristic**: Verifiable or provable by means of observation.

### Types of Data
- **Qualitative**: Descriptive, subjective insights
- **Quantitative**: Numerical, measurable data
- **Conducted with real users** - actual target audience

### Application Across Design Process
**Earlier in design process**: Testing paper prototypes in the lab
**Later in design process**: Field studies, out in the wild, usability testing

### Empirical Evaluation Methods

#### Lab Studies
**Environment**: Closed, controlled lab setting
**Data Type**: Quantitative results
**Purpose**: Compare alternatives (e.g., new UI vs. existing UI)

**Pros**:
- **Replicable** - controlled conditions allow for consistent results
- Controlled variables for reliable comparison

**Cons**:
- **Expensive** - requires dedicated facilities and equipment
- **Requires real users and lab** - resource intensive

#### Field Studies
**Environment**: "Real life" setting - natural user environment
**Data Type**: Qualitative results
**Purpose**: Watch process over time in natural context

**Pros**:
- **"Ecologically valid"** - reflects actual usage conditions
- **Cheap, quick, less training required**
- More realistic user behavior

**Cons**:
- **Not reproducible** - environmental variables differ
- **User-specific results** - harder to generalize

### Think Aloud Protocol

#### User Role
**Responsibilities**:
- **Steps to complete the tasks** - verbalize actions
- **Any issues they are facing** - express difficulties
- **Confusion they are encountering** - articulate problems

#### Evaluator Role
**Responsibilities**:
- **Conduct observation of the user** - watch and listen
- **Take notes** - document observations
- **Record video or audio** - capture for later analysis
- **Analyze data later** - systematic review of findings

#### Prompting Techniques
**Useful Prompts**:
- "Tell me what you are thinking."
- "Tell me what you are trying to do."
- "Are you looking for something? What?"
- "What did you expect to happen just now?"
- "What do you mean by that?"

**Critical Rule**: Do not help users to do the tasks or give solutions. Want to understand the problems and issues users are facing.

### User Tasks Design

#### Task Structure
**Components**:
- **Task description** - clear explanation of what needs to be done
- **Input and expected output** - define starting point and goal
- **Information sheet** - reference material for users

#### Measurement Planning
**Key Decisions**:
- **What to measure** - define metrics
- **How to measure** - specify collection methods

**Common Measures**:
- **Time taken to complete the task**
- **Number of errors made**
- **Number of users completing the task successfully**
- **Number of times users had to see information sheet** to complete the task

---

## 4. Predictive Evaluation

### Definition and Core Concept
**Predictive Evaluation**: Involves experts assessing a user interface without involving actual users.

**Method**: Expert reviewers interact with system, find potential problems, and give prescriptive feedback.

### Expert Requirements
**Effective when experts**:
- **Haven't used earlier prototype** - fresh perspective
- **Are familiar with domain or task** - understand context
- **Understand user perspectives** - can simulate user experience

### Predictive Evaluation Methods
1. **Heuristic Evaluation**
2. **Cognitive Walkthrough**

---

## 5. Heuristic Evaluation

### Development and Background
**Developer**: Jakob Nielsen in the early 1990s
**Basis**: Heuristics developed based on broad "rules of thumb"
**Reference**: http://www.nngroup.com/articles/ten-usability-heuristics/

### Methodology
**Evaluator Group**: Small set (3-5) expert usability evaluators
**Process**: Assess system based on simple and general heuristics
**Independence**: Evaluators independently check for compliance with usability principles
**Communication**: Different evaluators find different problems; evaluators only communicate afterwards
**Aggregation**: Findings are then aggregated for comprehensive assessment
**Flexibility**: Can perform on working UI or sketches

### Jakob Nielsen's Ten Usability Heuristics

#### 1. Visibility of System Status
**Principle**: Feedback of system's current state
**Examples**:
- Page is loading indicators
- Error loading page messages
- Something saved or deleted confirmations
- Show completion and what to do next

#### 2. Match Between System and Real World
**Principle**: Follow real world conventions
**Requirements**:
- **Speak the user's language**
- **Familiar categories, language and choices**
- **Familiar components and widgets**

**Counter-Example**: Old Mac Desktop - Dragging disk to trash should delete it, not eject it

#### 3. User Control and Freedom
**Principle**: Freedom to undo, explore and change choices
**Features**:
- **"Exits" for mistaken choices**
- **Exploration of data or options**
- **Multiple methods of doing the same thing**
- **Do tasks the way they like**

#### 4. Consistency and Standards
**Requirements**:
- **Consistent layout** - same structure across interface
- **Standard locations and positions** - predictable placement
- **Same language, placement etc. everywhere**
- **Follow platform conventions**
- **Same terminology is used** throughout
- **Same structure on all webpages**

**Example**: Submit button at the bottom after filling out information

#### 5. Error Prevention
**Strategies**:
- **Prevent data loss** - e.g., Confirmation dialog before deleting an item
- **Prevent bad input** - e.g., restrict to numerals if asked to key in mobile number
- **Prevent misinterpretation of the message** - clear, specific error communication

**Example**: User entered text in mobile number field. System displays errors about compulsory fields not completed, but the actual problem is with the mobile number input format.

#### 6. Recognition Rather Than Recall
**Principle**: Make objects, actions, options, & directions visible/easily retrievable
**Implementation**:
- **Show users previews** - e.g., images, results
- **Do not use codes** - use clear labels
- **Icons to click rather than type the text**

**Counter-Example**: Command line interfaces requiring memorization (% rm –rf *)

#### 7. Flexibility and Efficiency of Use
**Features**:
- **Flexible shortcuts** - accelerators for experts (e.g., gestures, keyboard shortcuts)
- **Allow users to tailor frequent actions** - e.g., macros
- **Defaults with options** - sensible defaults but customizable
- **Recommendations and relevant items** - personalized suggestions

#### 8. Aesthetic and Minimalist Design
**Requirements**:
- **Clean and uncluttered interface**
- **Eliminate redundant information** - only leave what has to be there
- **No irrelevant information in dialogs**
- Focus on essential elements only

#### 9. Help Users Recognize, Diagnose, and Recover from Errors
**Requirements**:
- **Clearly state the problem** - specific error identification
- **Provide a solution** - actionable guidance
- **Show how to address the problem** - clear steps

**Examples**:
- Created password with 8 characters, but system requires at least 1 special character and 1 numeral. Error message should state the requirements, so user can fix the error
- Did not fill all fields while registering for an account. Error message should highlight the fields which have not been filled

#### 10. Help and Documentation
**Requirements**:
- **Provide more information and clarify** - contextual assistance
- **Show steps and what to do next** - procedural guidance
- **Easy to search** - findable help content
- **Focused on the user's task** - task-oriented help
- **List concrete steps to carry out** - actionable instructions

**Examples**:
- Press (?) beside a field, popup tells you what the field is about, and what you should enter
- Help text on social networking websites for users to understand consequences of certain actions – upload photos, change privacy settings, who can see posts

### Heuristic Evaluation Process

#### Evaluators' Process
**1. Step through design several times**
- **Examine details, flow, and architecture**
- **Consult list of usability principles**
- Consider anything else that comes to mind

**2. Evaluate against heuristics**
- **Nielsen's "heuristics"** - standard ten principles
- **Category-specific heuristics** - domain-specific guidelines
- Consider design goals, competitive analysis, existing designs

**3. Use violations to redesign/fix problems**
- Identify specific issues and propose solutions

#### Multiple Evaluators Necessity
**Problem with Single Evaluator**:
- **No evaluator finds everything** - individual blind spots
- **Single evaluator achieves poor results** - limited perspective
- **Only finds 35% of usability problems** - inadequate coverage

**Solution with Multiple Evaluators**:
- **Some find more than others** - complementary strengths
- **5 evaluators find ~75% of problems** - significantly improved coverage

#### Phases of Heuristic Evaluation

**1. Pre-evaluation Training**
- Give evaluators needed **domain knowledge** and information on the scenario
- Ensure common understanding of context and goals

**2. Evaluation**
- **Individuals evaluate** independently 
- **Then aggregate results** - combine findings

**3. Severity Rating**
- **Determine how severe each problem is** (priority)
- Can do first individually and then as a group
- Collaborative severity assessment

**4. Debriefing**
- **Review with design team**
- Discuss findings and implications

#### How to Perform Heuristic Evaluation

**Evaluation Passes**:
- **At least two passes for each evaluator**
- **First pass**: Get feel for flow and scope of system
- **Second pass**: Focus on specific elements

**Assistance Requirements**:
- **If system is walk-up-and-use** or **evaluators are domain experts**: no assistance needed
- **Otherwise**: might supply evaluators with scenarios

**Output Requirements**:
- **Each evaluator produces list of problems**
- **Explain why** with reference to heuristic or other information
- **Be specific & list each problem separately**

### Severity Rating System

#### Rating Process
- **Independently estimate after review** - individual assessment first
- **Allocate resources to fix problems** - prioritization tool
- **Estimate need for more usability efforts** - resource planning

#### Severity Factors
**Severity combines**:
- **Frequency**: How common is this problem?
- **Impact**: How hard is it to overcome?
- **Persistence**: How often must users overcome it?

#### Severity Scale
**0**: Don't agree that this is a usability problem
**1**: Cosmetic problem - fix if extra time available
**2**: Minor usability problem - low priority fix
**3**: Major usability problem; important to fix
**4**: Usability catastrophe; imperative to fix

#### Severity Rating Example
**Example Entry**:
"[H1-4 Consistency] [Severity 3][Fix 0]
The interface used the string 'Save' on the first screen for saving the user's file, but used the string 'Write file' on the second screen. Users may be confused by this different terminology for the same function."

### Debriefing Process
**Participants**: Conduct with evaluators, observers, and development team members
**Activities**:
- **Discuss general characteristics of UI**
- **Suggest potential improvements** to address major usability problems
- **Development team rates effort to fix** - feasibility assessment
- **Brainstorm solutions** - collaborative problem-solving

### Heuristics vs. User Testing Comparison

#### Heuristic Evaluation Advantages
- **Heuristic evaluation often faster** - 1-2 hours for each evaluator
- **Results come pre-interpreted** - expert analysis included
- No need to recruit users

#### User Testing Advantages
- **User testing is more accurate** (by definition) - reflects actual usage
- **Takes into account actual users and tasks** - real-world validity
- Reveals unexpected user behaviors

#### Heuristic Evaluation Limitations
- **May miss problems & find "false positives"** - expert assumptions may be wrong
- May not reflect actual user priorities

#### Complementary Approach
- **Valuable to alternate methods** - each finds different problems
- **Don't waste participants** - use methods strategically

### Shneiderman's 8 Golden Rules
**Alternative Framework**: https://www.cs.umd.edu/users/ben/goldenrules.html

1. **Consistency**
2. **Shortcuts**
3. **Feedback**
4. **Dialog closure**
5. **Simple error handling**
6. **Reversible actions**
7. **Put user in control**
8. **Reduce short-term memory load**

---

## 6. Cognitive Walkthrough

### Definition and Purpose
**Cognitive Walkthrough**: Usability evaluation method in which one or more evaluators work through a series of tasks and ask a set of questions from the perspective of the user.

**Goal**: Assess learnability and usability through simulation of the way users explore and become familiar with interactive system.

### Background and Analogy
**Description**: Essentially a usability "thought experiment"
**Analogy**: Like code walkthrough in software engineering
**Developers**: Polson, Lewis, et al. at UC Boulder (2002)

### Process Overview
**Method**: 
- **Construct carefully designed tasks** from system spec or screen mock-up
- **Walk through (cognitive & operational) activities** required to go from one screen to another
- **Review actions needed for task** - step-by-step analysis
- **Attempt to predict how users would behave** and what problems they'll encounter

### Requirements for Cognitive Walkthrough

#### Essential Information Needed
1. **Description of users and their backgrounds** - user profile
2. **Description of task user is to perform** - specific scenarios
3. **Complete list of the actions required to complete task** - detailed action sequence
4. **Prototype or description of system** - interface representation

### Cognitive Walkthrough Assumptions

#### User Behavior Model
**Assumption 1**: **User has a rough plan** (not always true)
**Assumption 2**: **User explores system, looking for actions** to contribute to performance
**Assumption 3**: **User selects action that seems best** for reaching desired goal
**Assumption 4**: **User interprets response and assesses** whether progress has been made toward completing task

### Cognitive Walkthrough Methodology

#### Step-by-Step Process
**Structure**:
- **Step through action sequence**
  - Action 1 → Response A, B, ...
  - Action 2 → Response A
  - Continue through all actions

**Analysis**: **For each action, ask four questions** and try to construct a believable story

### The Four Cognitive Walkthrough Questions

#### Question 1: Will user be trying to produce effect?
**Focus**: User motivation and goals

**Typical Supporting Evidence**:
- **It is part of their original task** - aligns with user goals
- **They have experience using the system** - familiar pattern
- **The system tells them to do it** - explicit instruction

**No Evidence Response**:
- **Construct a failure scenario** - explain why user might not attempt action
- **Explain, back up opinion** - provide reasoning

#### Question 2: Will user notice the action is available?
**Focus**: Visibility and discoverability

**Typical Supporting Evidence**:
- **Experience** - user knows to look for this type of action
- **Visible device, such as a button** - clear visual indicator
- **Perceivable representation of an action** such as a menu item

#### Question 3: Will user know it's the right action for the desired effect?
**Focus**: Action-goal mapping

**Typical Supporting Evidence**:
- **Experience** - user has learned this connection
- **Interface provides a visual item** (such as prompt) to connect action to result effect
- **All other actions look wrong** - process of elimination

#### Question 4: Will user understand the feedback?
**Focus**: System response comprehension

**Typical Supporting Evidence**:
- **Experience** - user familiar with this type of feedback
- **Recognize a connection** between a system response and what user was trying to do

### Summary of Four Questions
1. **Will users be trying to produce whatever effect the given action has?**
2. **Will users be able to notice that the correct action is available?**
3. **Once found, will they know it's the right action for the desired effect?**
4. **Will users understand feedback after the action?**

---

## 7. DECIDE Evaluation Framework

### Definition and Purpose
**DECIDE**: An evaluation framework providing systematic approach to planning and conducting evaluations.

**Structure**: Six-step process for comprehensive evaluation planning

### DECIDE Steps

#### D - Determine the aims and goals
**Questions**:
- **What are the high level objectives of the evaluation?**
- **Who wants it and why?**

**Impact**: **The goals influence the paradigm for the study**

**Example Goals**:
- Identify the best metaphor to base the design
- Check to ensure that the final interface is consistent
- Investigate how technology affects working practices

#### E - Explore the questions you will ask
**Rationale**: **All evaluations need goals & questions to guide them** so time is not wasted on ill-defined studies

**Process**: **Questions are based on the goals of the study**

**Example**: Goal of finding out how many customers prefer to purchase paper airline tickets rather than e-tickets can be broken down into sub-questions:
- What are the customers' attitudes to these new tickets?
- Are they concerned about security?
- Is the interface for obtaining them poor?

#### C - Choose the evaluation approach/method
**Decision Point**: **An evaluation paradigm is an approach** that is influenced by particular theories and philosophies

**Impact**: **The evaluation paradigm strongly influences the techniques used**, and how the data is analyzed and presented

**Example**: Field studies do not involve testing and modeling

#### I - Identify practical issues
**How to Address**:
- **Select users**
  - Where to find subjects?
  - How to contact them?
  - How many subjects do I need?
- **Stay on budget** - resource management
- **Staying on schedule** - time management
- **Find evaluators** - expert recruitment
- **Select equipment** - technical requirements

#### D - Decide how to deal with ethical issues
**Informed Consent Development**: **Develop an informed consent form**

**Participants' Rights**:
- **Know the goals of the study**
- **What will happen with the findings**
- **Privacy of personal information**
- **Not to be quoted without their agreement**
- **Leave when they wish**
- **Be treated politely**

**Ethics Board Requirements**:
- **Ethics board (Institutional Review Board, IRB)** oversight
- **Need permission from ethics committee**
- **Review documentation, approve** study protocols

#### E - Evaluate, analyze, interpret and present the data collected
**Analysis Considerations**: **How data is analyzed and presented depends on the paradigm and techniques used**

**Quality Factors**:
- **Reliability**: Can the study be replicated?
- **Validity**: Is it measuring what you thought?
- **Biases**: Is the process creating biases?
- **Scope**: Can the findings be generalized?
- **Ecological validity**: Is the environment of the study influencing it?

**Example Bias**: Hawthorne effect - behavior changes due to awareness of being observed

---

## Summary - Key Takeaways

### Evaluation Fundamentals
- **Evaluation gathers data about usability** for specific activities, users, and environments
- **Formative evaluation occurs during design** process for improvement
- **Summative evaluation occurs after completion** to assess final product
- **Multiple evaluation approaches** serve different purposes and contexts

### Empirical Evaluation Methods
- **Lab studies provide controlled, replicable results** but are expensive
- **Field studies offer ecological validity** but are less reproducible
- **Think aloud protocol reveals user thinking** without providing solutions
- **Proper task design and measurement planning** are essential for valid results

### Predictive Evaluation Methods
- **Heuristic evaluation uses expert reviewers** applying established principles
- **Nielsen's 10 heuristics provide comprehensive** usability assessment framework
- **Multiple evaluators find 75% of problems** vs. 35% for single evaluator
- **Severity rating helps prioritize** fixes and allocate resources
- **Cognitive walkthrough simulates user learning** through systematic questioning

### Evaluation Planning
- **DECIDE framework provides systematic approach** to evaluation planning
- **Clear goals and questions guide** effective evaluation studies
- **Ethical considerations and practical issues** must be addressed upfront
- **Choice of method depends on** goals, resources, and stage in design process
- **Data analysis and presentation** should match chosen evaluation paradigm

# HCI Study Notes 06 - Visual Design

## 1. Goals of Visual Design

### Purpose
- **Guide**: Help users navigate, convey structure, importance, and relationships  
- **Pace**: Draw users in, orient them, and create flow  
- **Message**: Establish look and feel, express meaning, style, and personality  

---

## 2. Gestalt Theory

### Definition
**Gestalt Theory**: A psychological framework that explains how humans perceive visual elements as organized patterns or wholes rather than just individual parts.

**Key Idea**: *“The whole is other than the sum of the parts.”* — Kurt Koffka

### Core Principles
- **Proximity**: Elements close together are perceived as a group  
- **Similarity**: Elements that look alike are grouped together  
- **Continuity**: The eye follows paths, lines, and curves  
- **Closure**: The mind fills in gaps to see complete forms  
- **Figure & Background**: Distinguish main objects from background  
- **Symmetry**: Balanced elements are perceived as related  
- **Common Fate**: Elements moving in the same direction are grouped  

---

## 3. Whitespace

### Definition
**Whitespace**: Empty space around elements that enhances clarity and grouping.

### Benefits
- Conveys grouping and relationships  
- Improves balance and readability  
- Guides the eye across the layout  
- Creates ease of reading  

---

## 4. Typography

### Definition
**Typography**: The art and technique of arranging text to be legible, readable, and visually appealing.

### Key Concepts
- **Point**: Font size  
- **Leading**: Space between lines  
- **x-height**: Height of lowercase letters  
- **Ascenders/Descenders**: Parts of letters extending above/below baseline  
- **Weight**: Thickness of strokes  
- **Serifs**: Decorative strokes at character ends  
- **Kerning**: Space between letters  

### Font Choice Guidelines
- Use common fonts for large text blocks  
- Unique fonts suitable for logos or highlights  
- Use contrast in fonts (avoid small incremental changes)  
- Combine serif and sans-serif fonts for balance  
- Typeface sets tone and style  

### User Reading Behavior
- Users scan, not read in detail  
- Typical scanning follows an **F-shaped pattern**  
- Important elements should be placed **above the fold** (initial view)  

---

## 5. Grids and Layout

### Definition
**Grid System**: Framework for aligning and organizing visual elements.

### Benefits
- Enhances readability and scanning  
- Provides visual and structural balance  
- Ensures alignment and reduces clutter  

### Techniques
- **Rule of Thirds**: Divide layout into thirds for aesthetic balance  
- **Grid Layout Tips**:  
  - Align elements with grid boundaries  
  - Allow large elements to span multiple units  
  - Avoid misalignment  
  - Use proximity and scale for emphasis  
  - Left-align text for easier skimming (LTR languages)  

---

## 6. Color Theory

### Definition
**Color Theory**: Guidance on mixing colors and understanding visual effects of color combinations.

### Hue Circle Principles
- Pick non-adjacent colors for contrast  
- Opponent colors (e.g., red-green, blue-yellow) work well together  

### Guidelines
- Avoid highly saturated, extreme colors together  
  - Use pastel tones unless emphasis is needed  
- Follow conventions:  
  - Red = error/stop/alert  
  - Green = success/go/okay  
- Use fewer colors for simplicity  
- Too many colors = clutter and distraction  

---

## 7. Summary - Key Takeaways

- **Gestalt theory**: Visual perception groups elements into meaningful wholes  
- **Whitespace**: Enhances grouping, readability, and balance  
- **Typography**: Typeface choice impacts readability and brand perception  
- **Users scan, not read**: Design for scanning, especially above the fold  
- **Grids and layouts**: Provide structure, alignment, and clarity  
- **Color**: Conveys meaning and must be used carefully with conventions

# HCI Study Notes 08 - Human Abilities

## 1. Human Visual System

### Structure of the Human Eye

#### Key Components:
**Cornea:**
- Transparent front part of the eye
- Covers iris, pupil, and anterior chamber
- Refracts light entering the eye

**Pupil:**
- Opening in the center of the iris
- Controls amount of light entering the eye
- Adjusts size based on light conditions

**Lens:**
- Focuses light onto the retina
- Can change shape for focusing (accommodation)
- Yellows with age, affecting color perception

**Retina:**
- Light-sensitive tissue at back of eye
- Contains photoreceptor cells (rods and cones)
- Converts light into neural signals

---

## The Visual Spectrum

### Electromagnetic Spectrum
**Human Visible Range**: 390 nm to 700 nm
- **Violet/Blue**: ~390-450 nm
- **Green**: ~495-570 nm  
- **Yellow**: ~570-590 nm
- **Orange**: ~590-620 nm
- **Red**: ~620-700 nm

**Key Point**: Typical human eye responds only to this narrow band of the electromagnetic spectrum

---

## Retina and Photoreceptors

### Two Types of Photoreceptors

#### Rods (120 million)
**Characteristics:**
- Sensitive to broad spectrum of light
- Highly sensitive to small amounts of light
- Cannot discriminate between colors
- Sense intensity or shades of gray
- Primarily for night vision and perceiving movement

**Function**: Peripheral vision and low-light conditions

#### Cones (6 million)
**Characteristics:**
- Used to sense color
- Require more light to function
- Three types with different photopigments
- Concentrated in fovea (center of retina)

**Function**: Color vision and high-acuity central vision

---

## Color Perception

### Three Types of Cones
**Photopigments sensitive to different wavelengths:**
1. **Blue cones**: Short wavelengths (~420 nm)
2. **Green cones**: Medium wavelengths (~530 nm)
3. **"Red" cones**: Long wavelengths (~560 nm, actually yellow-green)

### Color Distribution
**Cone Distribution:**
- **Red cones**: 64% of total cones
- **Green cones**: 32% of total cones
- **Blue cones**: Only 4% of total cones

**Key Facts:**
- Not distributed evenly across retina
- Very few blue cones in retina center (high acuity area)
- Causes "disappearance" of small blue objects when fixated on

### Color Sensitivity Characteristics
**Most Sensitive**: Center of spectrum (green-yellow, ~550 nm)
**Less Sensitive**: Blues and reds must be brighter to be perceived as same intensity

**Brightness Perception Formula:**
```
Y = 0.3 Red + 0.59 Green + 0.11 Blue
```
- Brightness mainly determined by green and red cones
- Blue contributes minimally to perceived brightness

### Shape and Edge Detection
**Method**: Find edges using brightness and color differences
**Implication**: Color contrast important for readability and visibility

---

## Age-Related Vision Changes

### Lens Yellowing
**Effect**: Lens yellows with age and absorbs shorter wavelengths
**Impact**: Sensitivity to blue is reduced further
**Design Implication**: Elderly users have more difficulty with blue colors

---

## Color Deficiency (Color Blindness)

### Prevalence
**Affects**: ~9% of population (more common in males)

### Types of Color Deficiency

#### 1. Red-Green Deficiency (Most Common)
**Protanopia:**
- Lack of red photopigment
- Cannot discriminate reds properly

**Deuteranopia:**
- Lack of green photopigment  
- Cannot discriminate greens properly

**Impact**: Cannot distinguish colors dependent on red and green

#### 2. Reduced Color Discrimination
**Characteristics:**
- Different photopigment response
- Reduces capability to discern small color differences
- More common than complete deficiency

---

## Design Implications for Vision

### Critical Guidelines

#### Blue Color Usage
**Don't use blue for:**
- Text content
- Small objects or details
- Critical information

**Reasons:**
- Few blue cones overall
- No blue cones in retina center
- Reduced blue sensitivity with age
- Small blue objects can "disappear" when fixated

#### Peripheral Vision
**Avoid**: Red and green in the periphery
**Reason**: Cone distribution varies across retina

#### Color Contrast
**Blues and reds**: Must be brighter than greens and yellows to be perceived as same intensity
**Design Tip**: Use brightness differences, not just color differences

#### Accessibility for Color Deficiency
**Guidelines:**
- Don't rely solely on color to convey information
- Use color + shape/pattern/text combinations
- Provide high contrast options
- Test designs with color blindness simulators
- Avoid red-green combinations for critical distinctions

### Color as Communication Tool
**Strengths**: Powerful tool for communicating key information
**Risks**: Inappropriate use can severely reduce system performance
**Best Practice**: Combine color with other visual cues

---

## 2. Human Auditory System

### Structure and Function

#### Sound Characteristics

**Frequency:**
- Number of cycles of sound wave per second
- Measured in Hertz (Hz)
- Determines pitch of sound

**Human Hearing Range:**
- **Deep bass**: 20-60 Hz
- **Human speech**: 300-3,400 Hz
- **Bird chirps**: 2,000-8,000 Hz
- **Overall range**: ~20 Hz to 20,000 Hz (young adults)

### Decibel Scale (dB)

**Characteristics:**
- Logarithmic scale
- Doubling of sound pressure = 6 dB increase
- Used worldwide for sound level measurement
- Context-dependent (dB value depends on reference)

**Examples of Sound Intensities:**
- **180 dB**: Rocket at take-off (pain threshold)
- **140 dB**: Jet engine at take-off
- **120 dB**: Rock band (hearing damage risk)
- **110 dB**: Loud thunder
- **90 dB**: City traffic
- **80 dB**: Loud radio
- **60 dB**: Ordinary conversation
- **30 dB**: Soft whisper
- **0 dB**: Softest sound a person can hear

---

## Age-Related Hearing Loss

### Frequency Range Reduction
**Progressive loss with age:**
- **Age 50**: Maximum ~14 kHz
- **Age 70**: Maximum ~10 kHz

### Design Implications

#### For Older Users
**Guideline**: Sounds should not be too high pitched
**Reason**: Older people cannot hear higher frequencies
**Application**: Use mid-range frequencies (300-3,000 Hz) for alerts and feedback

---

## Audio in User Interfaces

### Benefits of Audio Feedback

**1. Richer Environment:**
- Creates more robust experience than graphics alone
- Adds dimension to user interaction

**2. Additional Information Channel:**
- Present information when visual bandwidth exhausted
- Complement visual overload situations

**3. Task Enhancement:**
- Makes tasks easier and more productive
- Provides confirmation without visual attention

**4. Redundancy:**
- Complements graphics and text
- Reinforces concepts through multiple senses
- Increases information retention

### Design Considerations
**Accessibility**: Consider hearing impairments
**Context**: Appropriate volume and frequency ranges
**Redundancy**: Don't rely solely on audio cues

---

## 3. Touch and Haptics

## Human Skin Structure

## 4. Model Human Processor (MHP)

### Origin and Purpose
**Developers**: Card, Moran & Newell (1983)
**Purpose**: Predictive model of human performance in HCI tasks
**Goal**: Understand and predict user behavior with interactive systems

---

## MHP Architecture

### Three Processors

#### 1. Perceptual Processor
**Function**: Processes sensory input
**Inputs**: Visual, auditory, and other sensory information
**Output**: Symbolic representations to cognitive processor
**Cycle Time**: ~100 ms

#### 2. Cognitive Processor  
**Function**: Makes decisions and plans actions
**Inputs**: Information from perceptual processor and memories
**Output**: Commands to motor processor
**Cycle Time**: ~70 ms

#### 3. Motor Processor
**Function**: Executes physical responses
**Input**: Commands from cognitive processor
**Output**: Physical actions (keystrokes, movements)
**Cycle Time**: ~70 ms

### Three Memory Systems

#### 1. Sensory Buffers
**Visual Image Store:**
- Temporary storage of visual information
- Very brief duration (~200 ms)
- High capacity but rapid decay

**Auditory Image Store:**
- Temporary storage of auditory information
- Slightly longer duration (~1,500 ms)
- Preserves sound patterns briefly

#### 2. Working Memory (Short-term)
**Capacity**: 7 ± 2 "chunks" of information
**Access Time**: Rapid (~70 ms)
**Decay Time**: ~200 ms without rehearsal
**Transfer**: Information passes to long-term memory after a few seconds of continued storage

#### 3. Long-Term Memory (LTM)
**Capacity**: Huge (essentially unlimited)
**Access Time**: Slower (~100 ms)
**Decay**: Minimal decay over time
**Content**: Knowledge, skills, experiences, facts

---

## MHP Operation Example: Sending a Text Message

### Step-by-Step Process

#### Stage 1: Perception
**Visual Input**: User looks at smartphone screen and sees messaging app icon
**Processing**: 
- Retina processes visual information
- Transmitted to visual cortex
- Visual image held briefly in Visual Image Store

**Transfer**: Relevant details passed to Working Memory → Cognitive Processor

#### Stage 2: Cognition
**Working Memory**: 
- User remembers intention to send message
- Maintains plan in working memory

**Long-Term Memory Retrieval**:
- Recalls app layout
- Retrieves location of contact list
- Accesses knowledge of how messaging apps work

**Planning**:
- Cognitive system formulates plan to touch messaging app icon
- Determines sequence of actions needed

#### Stage 3: Motor Action
**Motor Planning**: Motor plan sent to muscles controlling fingers
**Execution**: Physical touch on screen

---

## MHP Characteristics

### Serial vs. Parallel Processing

**Serial Processing:**
- One task at a time
- Example: Pressing a key in response to light

**Parallel Processing:**
- Multiple tasks simultaneously
- Example: Driving while reading signs and hearing simultaneously

### Processor Parameters
**Cycle Times**: Approximately 100-200 ms per processor
**Memory Parameters**: 
- Capacity (how much can be stored)
- Decay time (how long it persists)
- Type (format of storage)

---

## MHP Operational Principles

### Recognize-Act Cycle
**Process:**
1. Contents in working memory trigger associations
2. Associations linked to actions in long-term memory
3. Actions modify contents of working memory
4. Cycle repeats

**Implication**: Interface design should leverage existing mental associations

### Discrimination Principle
**Definition**: Retrieval determined by candidates that exist in memory relative to retrieval cues

**Key Factors:**
- **Retrieval cues**: Hints that trigger memory recall
- **Interference**: Strongly activated chunks can interfere with retrieval
- **Multiple cues**: Better cues = better retrieval

---

## Working Memory Characteristics

### Capacity: 7 ± 2 Chunks

**Examples of Chunking:**
```
Without chunking: 6565921189 (10 items - hard to remember)
With chunking: +65 6592-1189 (3 chunks - much easier)

Without chunking: AYECTEPIE (9 letters - difficult)
With chunking: AYE CTE PIE (3 words - much easier)
```

### Temporal Properties
**Rapid Access**: ~70 ms to retrieve item
**Rapid Decay**: ~200 ms without rehearsal
**Transfer to LTM**: Occurs after a few seconds of continued storage

---

## Cognitive Chunking

### Definition
**Process**: Grouping individual pieces of information into larger, manageable units to facilitate better understanding, memory, and retrieval

### Chunking Techniques

#### 1. Visual Chunking
**Method**: Use whitespace to separate and group information
**Purpose**: Create visual distinction between different information groups
**Example**: Spacing between form sections

#### 2. Semantic Chunking
**Method**: Change visual characteristics of groups
**Purpose**: Use color, typography, or style to indicate related information
**Example**: Color-coding categories

#### 3. Visual Progression
**Method**: Use visual and cognitive cues to guide information processing order
**Purpose**: Help users internalize information in logical sequence
**Example**: Numbered steps, visual flow indicators

### Design Implication
**Guideline**: Create cognitive chunks in UI design to reduce memory load and improve usability

---

## Cognitive Load Theory

### Definition
**Cognitive Load**: Universal set of learning principles for efficient instructional environments by leveraging human cognitive processes
**Core Concept**: Used amount of working memory resources

### Total Working Memory Capacity Model

```
Total Working Memory = Intrinsic Load + Extraneous Load + Germane Load + Free Capacity
```

### Types of Cognitive Load (Paas et al. 2004)

#### 1. Intrinsic Load (ICL)
**Definition**: Inherent difficulty of instructional topic
**Characteristic**: Irreducible by instructional design (mostly)
**Examples**:
- Calculating 2 + 2 (low intrinsic load)
- Solving differential equation (high intrinsic load)
**Design Impact**: Choose appropriate complexity for target audience

#### 2. Extraneous Load (ECL)
**Definition**: Load generated by manner of information presentation
**Characteristic**: Reducible by instructional design
**Source**: Poor presentation design
**Examples**: 
- Confusing layouts
- Unclear instructions
- Searching for information
**Design Goal**: Minimize through good interface design

#### 3. Germane Load (GL)
**Definition**: Load devoted to processing, construction, and automation of schemas
**Characteristic**: Increasable by instructional design
**Function**: Productive cognitive effort for learning
**Examples**:
- First-time learning vs. practiced skill
- Deep processing of material
**Design Goal**: Maximize productive learning

#### Free Capacity
**Definition**: Remaining unused working memory capacity
**Factors Reducing Free Capacity**:
- Stress
- Lack of sleep
- Multitasking
- Environmental distractions

---

## Major Cognitive Load Effects

### 1. Split-Attention Effect
**Problem**: Unnecessary splitting of attention across multiple sources
**Cause**: Information spread across disconnected locations
**Impact**: Increases extraneous cognitive load
**Solution**: Integrate related information spatially and temporally

**Example**: 
- **Poor**: Diagram on one page, explanation on another
- **Good**: Labels integrated directly into diagram

### 2. Redundancy Effect
**Problem**: Presenting same information in multiple formats unnecessarily
**Cause**: Both diagrams and accompanying text when one would suffice
**Impact**: Forces processing of redundant information
**Solution**: Remove redundant information sources

**Example**:
- **Poor**: Detailed diagram with full text description of same content
- **Good**: Diagram with brief annotations, or detailed text without diagram

### 3. Element Interactivity
**Definition**: Instructional content composed of component parts (elements) that interact
**High Interactivity**: Elements must be understood in relation to each other
**Low Interactivity**: Elements can be understood independently
**Impact**: Higher interactivity increases intrinsic load

**Design Consideration**: Break complex, high-interactivity content into manageable parts

---

## Memory and Interference

### Interference Problem
**Situation**: Two strong cues in working memory link to different chunks in long-term memory
**Result**: Difficulty retrieving correct information
**Example**: Similar passwords for different accounts

### Design Implications
**Solution**: Use distinctive cues and clear differentiation
**Application**: Make interactive elements visually distinct to avoid confusion

---

## Perceptual Causality

### Definition
**Perceptual Causality**: Two distinct stimuli can fuse if the first event appears to cause the other

### Perceptual Processor Cycle
**Principle**: Stimuli occurring within one cycle of perceptual processor (~100 ms) fuse into single concept

### Design Implication
**Responsiveness**: Create perception of causality by being sufficiently responsive
**Guideline**: System feedback should occur within 100-200 ms of user action
**Application**: 
- Button press feedback
- Click acknowledgment
- Loading indicators for longer operations

---

## Recognition vs. Recall

### Recall
**Definition**: Information reproduced from memory without cues
**Example**: Command-line interfaces requiring typed commands
**Difficulty**: High cognitive load
**Memory Demand**: Must retrieve from long-term memory unaided

**Command Example**: Remember that `ls -la` lists all files with details

### Recognition
**Definition**: Presentation of information provides knowledge it's been seen before
**Example**: GUI menus showing available commands
**Benefit**: Easier because of retrieval cues
**Memory Demand**: Lower - cues aid retrieval

**Menu Example**: See "List Files" option with description in menu

### Retrieval Cues
**Definition**: Anything related to item or situation where learned
**Types**:
- Visual hints
- Icons representing functions
- Descriptive labels
- Menu names and categories
- Contextual information

### Design Principle
**Nielsen's Heuristic**: "Recognition rather than recall"
**Application**: 
- Use menus instead of command-line when possible
- Provide icons and labels
- Show available options
- Use auto-complete and suggestions
- Display recently used items

---

## Summary - Key Takeaways

### Vision
- Understand limitations: blue insensitivity, color blindness
- Design for accessibility: don't rely solely on color
- Consider age-related changes in vision
- Use appropriate contrast and sizing

### Hearing  
- Account for age-related hearing loss
- Use mid-range frequencies for critical audio
- Provide visual alternatives for audio cues
- Don't rely solely on high-frequency sounds

### Touch
- Leverage high-sensitivity areas (hands, lips, tongue)
- Use haptic feedback appropriately
- Design touch targets for finger size
- Consider tactile as additional information channel

### Model Human Processor
- Understand three processors: perceptual, cognitive, motor
- Work within working memory limitations (7±2 chunks)
- Minimize cognitive load through good design
- Use recognition over recall
- Provide timely feedback for perceptual causality
- Leverage chunking to reduce memory burden
- Consider interference and provide distinctive cues

# HCI Study Notes 09 - Usability Experiments

## Overview: The 9 Stages of Usability Experiments

1. Identify your objective
2. Formulate a hypothesis
3. Choose the variables
4. Choose the experimental design
5. Choose the tasks
6. Recruit participants
7. Run the experiment
8. Perform statistical tests on the data
9. Analyze and interpret the results

---

## Stage 1: Identify the Objective

### Purpose
**Determine**: What do you want to know about your interface?
**Goal**: Clear understanding of research question

### Example Objectives

#### Button Size/Positioning
**Question**: Which button size or position leads to highest accuracy?
**Measurement**: Error rate, target acquisition time

#### Color Scheme
**Question**: Which color scheme is clearest or most confusing?
**Measurement**: Task completion time, error rate, subjective ratings

#### Audio/Haptic Feedback
**Question**: Do sounds or vibrations improve subjective enjoyment?
**Measurement**: User satisfaction ratings, engagement metrics

#### Ease of Use
**Question**: Which design is easier to use?
**Measurement**: Learning time, efficiency, user preference

### Key Consideration
**Specificity**: Objective should be specific enough to guide experiment design but broad enough to be meaningful

---

## Stage 2: Formulate a Hypothesis

### Definition
**Hypothesis**: Makes a prediction about the outcome of the experiment
**Requirement**: Must be testable - experiment will show if prediction is correct
**Format**: Should be presented in terms of independent and dependent variables

### Good Hypothesis Examples

**Button Size:**
"Bigger buttons lead to more accurate target selection"
- Clear prediction
- Testable relationship
- Specific variables

**Sounds/Vibrations:**
"Enjoyment of the UI is higher with audio and haptic feedback"
- Measurable outcome
- Clear comparison
- Specific condition

**Autocomplete:**
"An autocomplete functionality to search locations leads to better user satisfaction compared to typing the complete location address"
- Compares two conditions
- Specific outcome measure
- Testable prediction

### What Makes a Hypothesis Bad

#### 1. Vague Hypotheses
**Problem**: Doesn't predict specific outcome
**Example**: "System A leads to better user satisfaction and less stress"
- What is "better"?
- How much improvement?
- Multiple unmeasured outcomes

#### 2. Overly Complex Hypotheses
**Problem**: Can explain any result - not falsifiable
**Example**: "System A's performance is a function of data type, user knowledge, developer settings, random numbers, and pseudo-random numbers"
- Too many variables
- Impossible to isolate effects
- Not practically testable

### Guidelines for Good Hypotheses
- **Specific**: Clear prediction of direction and magnitude
- **Testable**: Can be proven true or false
- **Simple**: Focus on key relationship
- **Measurable**: Variables can be quantified

---

## Stage 3: Choose the Variables

### Types of Variables

#### Independent Variable (IV)
**Definition**: Characteristic that is changed to produce different conditions
**Control**: Manipulated by the researcher
**Purpose**: The presumed cause in cause-effect relationship

**Examples:**
- **Interface design**: Layout, color scheme, icon size
- **Input method**: Touch input vs. mouse input vs. keyboard
- **Feedback type**: With/without audio, with/without haptics
- **Feature presence**: Autocomplete on/off

**Levels**: Different values or conditions of IV
- Example: Button size (small, medium, large) = 3 levels

#### Dependent Variable (DV)
**Definition**: Used to test the hypothesis - what is being measured
**Nature**: Outcome driven by the independent variable
**Purpose**: The presumed effect in cause-effect relationship

**Examples:**
- **Task completion time**: Seconds or milliseconds to finish task
- **Error rate**: Number or percentage of mistakes
- **User satisfaction**: Likert scale ratings (1-5 or 1-7)
- **Accuracy**: Percentage of correct responses
- **Clicks to completion**: Number of interactions needed

#### Control Variables
**Definition**: Variables held constant to ensure experiment validity
**Purpose**: Prevent confounding effects
**Determined by**: Experimental design requirements

**Examples:**
- **Environmental conditions**: Same lighting, noise level, temperature
- **Hardware**: Same device model, screen size, resolution
- **User demographics**: Age range, expertise level, background
- **Time of day**: Testing at consistent times
- **Instructions given**: Standardized script for all participants

#### Confounding Variables
**Definition**: Variables that can alter the experiment outcome
**Problem**: Not controlled, can interfere with results
**Solution**: Identify and control or account for them

**Examples:**
- **User experience**: Varying familiarity with technology
- **Fatigue**: Performance deterioration from tiredness
- **Learning effects**: Improvement from practice
- **Motivation level**: Varying participant engagement
- **Physical abilities**: Eyesight, hearing, motor control

---

## Example: Sound/Vibration Hypothesis

**Hypothesis**: "Having sounds and vibrations on mobile app leads to better user satisfaction compared to no sounds and vibrations"

### Variable Identification

**Independent Variable**: Feedback type
- **Level 1**: No sounds and vibrations
- **Level 2**: Having sounds and vibrations

**Dependent Variable**: User satisfaction
- **Measurement**: 1 to 5 scale on survey question
- **Type**: Ordinal data

**Control Variables**: 
- Type of mobile device (same model for all)
- Noise level in testing environment
- Task performed
- Testing instructions

**Confounding Variables** (to watch for):
- User hearing ability
- Age differences
- Previous experience with similar apps
- Personal preferences for feedback

---

## Stage 4: Choose the Experimental Design

### Purpose of Experimental Design
**Specifies**:
- What independent variables to manipulate and how
- Which dependent variables to measure and how
- How to control confounding variables
- Which variables to control for validity

### Basic Requirement
**Minimum**: At least 2 conditions (depends on levels of IV)
- **Control condition**: Baseline or comparison condition
- **Experimental condition**: Modified or treatment condition

---

## Two Main Design Types

### 1. Between-Subjects Design (Independent Samples)

#### Definition
**Also called**: Independent Design, Independent Samples
**Principle**: Compare one group against another
**Method**: Participants randomly allocated to one of the groups
**Participation**: Each group performs ONE condition only

#### Example: Sound/Vibration Study

**Setup**:
- Recruit 40 participants
- Randomly assign to two groups of 20

**Control Group** (20 participants):
- Use app with no sounds and vibrations
- Subjects: 1, 3, 5, 7... 39

**Experimental Group** (20 participants):
- Use app with sounds and vibrations  
- Subjects: 2, 4, 6, 8... 40

**Measurement**: Compare user satisfaction between groups

#### Strengths of Between-Subjects Design

**1. No Learning Effects:**
- Participants don't carry over experience from one condition to another
- Lower chances of practice effects
- Prevents carryover effects from biasing results
- Each condition is "fresh" for participants

**2. Less Fatigue:**
- Each participant exposed to single treatment only
- Shorter testing sessions per participant
- Reduced participant burden

**3. Multiple Variables Can Be Tested:**
- Can evaluate many systems simultaneously
- Example: Testing 4 different interfaces
  - Divide participants into 4 groups
  - Each group tests one interface
- Efficient for broad comparisons

#### Limitations of Between-Subjects Design

**1. Need Many Participants:**
- More groups = more participants required
- 3 conditions = 3x the participants needed
- Can be costly and time-consuming to recruit

**2. Individual Variability:**
- Differences in abilities and expertise between groups
- Risk of getting "bad group" of participants
- Natural variance in human performance
- One group might be systematically different

**3. Assignment Bias:**
- Control and experimental groups from potentially different populations
- Random assignment doesn't guarantee equivalent groups
- Sample size needs to be large enough to balance out differences

---

### 2. Within-Subjects Design (Repeated Measures)

#### Definition
**Also called**: Repeated Measures, Related Design
**Principle**: Same participants take part in more than one condition
**Method**: Compare each participant against themselves
**Participation**: All participants experience ALL conditions

#### Example: Button Size Study

**Setup**:
- Recruit 20 participants
- All 20 take part in BOTH conditions

**Condition 1**: Small buttons
- All 20 participants complete tasks

**Condition 2**: Large buttons  
- Same 20 participants complete tasks

**Independent Variables**:
- Button size (2 levels)

**Dependent Variables**:
- Time taken to press button
- Where on screen was pressed (accuracy)

**Control Variables**:
- Same phone model for all tests
- Same screen size and resolution
- Same time given to react and press

**Confounding Variables** (to watch for):
- Test for Condition 1 might be easier than Condition 2
- Some participants may have bad eyesight
- Order effects (discussed below)

#### Strengths of Within-Subjects Design

**1. Fewer Participants Needed:**
- Each participant serves as their own control
- Can achieve statistical power with smaller sample
- More cost-effective recruitment

**2. Reduced Variation:**
- Less chance of variation between participants
- Individual differences controlled
- Each person compared to themselves

**3. Reduction in Error Variance:**
- Self-comparison eliminates individual baseline differences
- Higher statistical power
- More sensitive to detecting real effects

**Example Benefit**: 
Testing eyesight impact on button accuracy:
- **Between-subjects**: Risk all people with bad eyesight in one group
- **Within-subjects**: Everyone's eyesight affects both conditions equally
- Result: Can truly isolate button size effect

#### Limitations of Within-Subjects Design

**1. Carryover Effects:**
- **Definition**: Participation in one condition affects performance in others
- **Problem**: Confounding extraneous variable
- **Example**: Learning from first condition helps in second

**2. Fatigue Effects:**
- **Problem**: Participants become tired after first treatment
- **Impact**: Negatively affects performance in later conditions
- **Solution**: Provide adequate rest/breaks between conditions
- **Consider**: Time between conditions, total session length

**3. Practice Effects:**
- **Problem**: Participants become familiar with experiment
- **Impact**: May positively affect performance in later treatments
- **Distinction**: Different from carryover - general skill improvement

**4. Order Effects:**
- **Definition**: Outcome depends on order treatments were performed
- **Impact**: Cannot separate treatment effect from order effect
- **Critical Problem**: Threatens internal validity

---

## Controlling Order Effects: Counterbalancing

### Problem
Performance in Condition B might be influenced by having done Condition A first

### Solution: Counterbalancing
**Method**: Randomize order of treatments across participants

**Example with 2 Conditions:**
```
User 1: Treatment A → Treatment B
User 2: Treatment B → Treatment A
User 3: Treatment A → Treatment B
User 4: Treatment B → Treatment A
```

**Example with 3 Conditions (Button Size):**
- **IV**: Button size with 3 levels
  - Condition A: Small button
  - Condition B: Medium button
  - Condition C: Large button

**Problem Without Counterbalancing:**
By Condition C, participants have had two chances to practice or get tired

**Counterbalancing Solution:**
```
User 1: A → B → C
User 2: B → C → A
User 3: C → A → B
User 4: A → C → B
User 5: B → A → C
User 6: C → B → A
```

**Result**: Order effects distributed across all conditions

---

## Matched Design

### Definition
**Method**: Participants matched into pairs based on specific criteria
**Assignment**: Each member of pair allocated to different condition

### Matching Criteria
**Common factors:**
- Gender
- Expertise level
- Age
- Personal relationship
- Background knowledge
- Physical abilities

### Process
1. Identify matching criteria relevant to study
2. Assess all participants on these criteria
3. Form pairs with similar characteristics
4. Randomly assign one member to each condition

### Advantages
- Controls for individual differences better than pure between-subjects
- More efficient than within-subjects for some designs
- Reduces variance between groups

### Limitations
**1. Matching Quality:**
- Some pairs may have higher expertise than others
- Perfect matching is difficult to achieve

**2. Matching Criteria:**
- Choosing wrong criteria doesn't help
- May not know which factors are important

**3. Practical Issues:**
- Finding good matches can be challenging
- Requires larger initial participant pool

## Experimental Validity Ladder

### 1. Content Validity (Foundation)
**Question**: Does the result reflect a variable of interest?
**Also**: Is the result interesting or just a known fact?
**Importance**: Ensures experiment measures what it claims to measure
**Example**: Testing "ease of use" but only measuring speed

### 2. Construct Validity
**Question**: Does the result align with theoretical concepts?
**Also**: Can we explain the result using known theories?
**Importance**: Connects findings to broader understanding
**Example**: Explaining results using cognitive load theory

### 3. Internal Validity
**Question**: Does the hypothesis hold?
**Also**: Is it valid in the experimental context?
**Importance**: Ensures results due to IV manipulation, not confounds
**Threats**: Confounding variables, poor controls
**Example**: Did button size really cause the difference, or was it screen brightness?

### 4. External Validity
**Question**: Does the outcome hold for other datasets or sample users?
**Also**: Can it be generalized?
**Importance**: Results apply beyond specific test conditions
**Example**: Findings from university students apply to general population?

### 5. Ecological Validity (Highest)
**Question**: Does the result apply to real-life scenarios?
**Importance**: Practical applicability of findings
**Example Problem**: Testing interface developed for blind people with sighted users
**Good Example**: Testing mobile app in realistic mobile contexts (walking, distractions)

## Stage 5: Choose the Tasks

### Purpose
**Need**: Right task to properly test hypothesis and elicit measures
**Already Know**:
- What you want to find out (objective)
- What you think you'll find (hypothesis)
- What you're testing (IV)
- What you're measuring (DV & data)
- The experimental design

### Task Design Principles

#### 1. Constraint
**Guideline**: Tasks should test just the thing you're interested in
**Purpose**: Isolate the variable of interest
**Example**: Testing button size - task should focus on button pressing, not navigation

#### 2. Data Collection
**Guideline**: Collect enough data to analyze
**Principle**: More data reduces influence of outliers (extreme behavior)
**Example**: Each button size targeted 20 times in different positions
**Reasoning**: Average of 20 trials more reliable than single trial

#### 3. Measurement Method
**Consider**:
- How to time conditions?
  - Manual stopwatch
  - Program-based timing
  - Per-trial timing as DV
- What data to collect?
  - Position clicked (x, y coordinates)
  - Time taken (milliseconds)
  - Accuracy (hit/miss)
  - Error patterns

## Stage 8: Perform Statistical Tests

### Purpose
**Goal**: Compare datasets gathered from different conditions
**Question**: Is there a statistically significant difference?

### Hypotheses in Statistical Testing

#### Null Hypothesis (H₀)
**Definition**: Any observed changes in behavior are due to chance
**Assumption**: No real difference between conditions
**Example**: "Button size has no effect on accuracy"

#### Alternate Hypothesis (H₁)
**Definition**: The hypothesis you're trying to demonstrate
**Assumption**: Real difference exists between conditions
**Example**: "Larger buttons lead to higher accuracy"

### Decision Rule
**If test results are significant**: Reject null hypothesis, accept alternate hypothesis
**If test results are not significant**: Fail to reject null hypothesis

---

## Choosing Statistical Tests

### Factors Determining Test Choice

#### 1. Type of Comparison
**Difference**: DV differs between IV levels
- Example: User satisfaction differs with/without sounds

**Correlation**: DV changes systematically with IV
- Example: Errors increase as screen size decreases

#### 2. Type of Data

**Nominal/Categorical:**
- Labels for variables
- No inherent order
- Examples: Male/Female, Colors, Device types

**Ordinal/Scale:**
- Ordered categories
- Clear ranking but unequal intervals
- Examples: 
  - Likert scales (Strongly Disagree to Strongly Agree)
  - Grades (A, B, C, D, F)
  - Sizes (S, M, L, XL)
  - Ratings (Low, Med, High)

**Interval:**
- Ordered with equal spacing
- No true zero point
- Can't do ratios
- Examples:
  - Dates (Nov 9, 2020)
  - Coordinates (latitude/longitude)
  - Time of day (3:30pm)
  - Temperature in Fahrenheit/Celsius

**Ratio:**
- All properties of interval
- Has true zero point
- Can do arithmetic operations
- Examples:
  - Counts and amounts
  - Physical measurements (length, mass)
  - Time duration (20 milliseconds)
  - Accuracy percentages

#### 3. Experimental Design
**Between-subjects**: Independent/unrelated samples
**Within-subjects**: Related/repeated measures

#### 4. Number of Conditions
**One IV with 2 levels**: 2 conditions (most common)
**One IV with 3+ levels**: 3+ conditions
**Multiple IVs**: Multi-factorial design

---

## Parametric Tests

### When to Use
**Requirements (ALL must be met):**

1. **Data is Interval or Ratio**
   - Numeric measurements
   - Frequencies of occurrence

2. **Data is Normally Distributed**
   - Conduct normality test to verify
   - Bell curve distribution
   - Examples: Shapiro-Wilk test, Kolmogorov-Smirnov test

3. **Characterized by Central Tendency Measures**
   - Can meaningfully calculate mean
   - Standard deviation meaningful
   - Standard error calculable

### Common Parametric Tests

#### For 2 Conditions

**Between-Subjects Design:**
- **Test**: Independent t-test (Student's t-test)
- **Purpose**: Compare means of two independent groups
- **Example**: Comparing satisfaction between Group A and Group B

**Within-Subjects Design:**
- **Test**: Paired t-test (Dependent t-test)
- **Purpose**: Compare means of same group in two conditions
- **Example**: Comparing same users' performance with/without feature

#### Procedure
1. Calculate test statistic (t value)
2. Determine degrees of freedom
3. Calculate significance value (p-value)
4. Calculate descriptive statistics (mean, SD, SE)
5. Interpret results

---

## Non-Parametric Tests

### When to Use
**Requirements:**
- Data is ordinal or nominal
- Parametric assumptions not met
- Distribution not normal
- Small sample sizes

**Method**: Uses ranks/order instead of mean comparisons
**Trade-off**: Less statistical power than parametric tests

### Common Non-Parametric Tests

#### For 2 Conditions

**Between-Subjects Design:**
- **Test**: Mann-Whitney U test (Wilcoxon rank-sum)
- **Purpose**: Compare distributions of two independent groups
- **Method**: Ranks all scores, compares rank sums

**Within-Subjects Design:**
- **Test**: Wilcoxon signed-rank test
- **Purpose**: Compare distributions in repeated measures
- **Method**: Ranks differences between paired observations

#### For Categorical Data

**Between Groups:**
- **Test**: Chi-square (χ²) test
- **Purpose**: Compare frequencies across categories

**Within Subjects (2 conditions):**
- **Test**: Binomial Sign test
- **Purpose**: Compare paired categorical data

#### Procedure
1. Rank all observations
2. Calculate differences between ranked positions
3. Calculate test statistic (U, T, or χ²)
4. Map to critical values table
5. Obtain p-value (significance)

---

## Test Selection Flowchart: 2 Conditions

### Step 1: Type of Analysis
**Difference or Correlation?**

→ **Difference** (proceed to Step 2)
→ **Correlation** (use Spearman's ρ for ordinal, Pearson's r for interval)

### Step 2: Data Type
**Categorical, Ordinal, or Interval/Ratio?**

→ **Categorical**: Chi-square (χ²) for unrelated, Binomial Sign for related
→ **Ordinal/Interval with parametric assumptions not met**: Continue to Step 3
→ **Interval/Ratio with parametric assumptions met**: Continue to Step 3

### Step 3: Experimental Design
**Related (Within-Subjects) or Unrelated (Between-Subjects)?**

**Parametric Tests:**
- Related: Paired t-test
- Unrelated: Independent t-test

**Non-Parametric Tests:**
- Related: Wilcoxon signed-rank test
- Unrelated: Mann-Whitney U test

---

## Multiple Conditions (3+) and Multi-Factorial

### One Independent Variable (3+ levels)

**Parametric - Between-Subjects:**
- **Test**: One-way ANOVA (Analysis of Variance)
- **Purpose**: Compare means across 3+ independent groups

**Parametric - Within-Subjects:**
- **Test**: Repeated measures ANOVA
- **Purpose**: Compare means across 3+ conditions in same participants

**Non-Parametric - Between-Subjects:**
- **Test**: Kruskal-Wallis analysis of variance
- **Purpose**: Compare distributions across 3+ independent groups

**Non-Parametric - Within-Subjects:**
- **Test**: Friedman's test
- **Purpose**: Compare distributions across 3+ conditions in same participants

### Multiple Independent Variables

**Parametric Tests:**
- **Factorial unrelated ANOVA**: All IVs between-subjects
- **Factorial repeated measures ANOVA**: All IVs within-subjects
- **Factorial mixed design ANOVA**: Some IVs between, some within

**Non-Parametric:**
- **Multiple regression**: Predicting DV from multiple IVs
- **Loglinear analysis**: Analyzing multi-way frequency tables

## Statistical Significance

### P-Value Interpretation
**Definition**: Probability that observed differences are due to chance

**Lower p-value** = Less likely due to chance = More likely due to IV

### Accepted Significance Levels

**p ≤ 0.05:**
- Minimum accepted level
- 5% chance results due to random variation
- 95% confidence in results

**p ≤ 0.01:**
- Moderate significance
- 1% chance results due to random variation
- 99% confidence in results

**p ≤ 0.001:**
- High significance
- 0.1% chance results due to random variation
- 99.9% confidence in results

### Decision Making

**If p < 0.05:**
- Null hypothesis is rejected
- Results are statistically significant
- Conclude IV had effect on DV

**If p > 0.05:**
- Null hypothesis is NOT rejected
- Results are not statistically significant
- Cannot conclude IV had effect

**Important Notes:**
- "Not significant" ≠ "no difference exists"
- Means "not enough evidence to reject null hypothesis"
- Could be due to:
  - Small sample size
  - High variability in data
  - Weak effect size
  - Measurement issues

---

## Types of Errors

### Type I Error (False Positive)
**Definition**: Incorrectly rejecting a true null hypothesis
**Meaning**: Concluding there's an effect when there isn't
**Probability**: Controlled by significance level (α = 0.05)
**Example**: Concluding button size matters when it actually doesn't

**Impact**: 
- Pursuing ineffective design changes
- Wasted resources
- False conclusions

### Type II Error (False Negative)
**Definition**: Failing to reject a false null hypothesis
**Meaning**: Missing a real effect
**Probability**: Related to statistical power (β)
**Example**: Concluding button size doesn't matter when it actually does

**Impact**:
- Missing valuable improvements
- Concluding "no difference" incorrectly
- Higher risk with non-parametric tests (less power)

### Balancing Errors
**Trade-off**: Reducing Type I error risk increases Type II error risk
**Solution**: Appropriate sample size and effect size considerations

---

## Statistical Power

### Definition
**Power**: Probability of correctly rejecting false null hypothesis
**Goal**: High power (typically 0.80 or 80%)

### Factors Affecting Power

#### 1. Significance Level (α)
**Definition**: Probability of incorrectly rejecting null hypothesis
**Standard**: p < 0.05 (5% Type I error rate)
**Confidence**: 95% confidence in results

**Trade-off**: 
- Lower α = fewer false positives but less power
- Higher α = more power but more false positives

#### 2. Sample Size (n)
**Impact**: Larger sample = higher power
**Reasoning**: More data reduces random variation impact
**Guideline**: Calculate required sample size before study

**General Rules:**
- Small effect: Need large sample
- Large effect: Can use smaller sample
- Within-subjects: Need fewer participants than between-subjects

#### 3. Effect Size
**Definition**: Degree to which phenomenon is present
**Types**:
- Small effect: Subtle differences
- Medium effect: Moderate differences
- Large effect: Obvious differences

**Impact**: Larger effect sizes easier to detect with smaller samples

### Power Analysis
**Purpose**: Determine appropriate sample size before conducting study
**Inputs**: Expected effect size, desired power, significance level
**Output**: Required number of participants

# HCI Study Notes 10 - A/B Testing and Mobile Interaction

## 1. A/B Testing

### What is A/B Testing?

**Definition**: The simplest form of controlled experiment where traffic is randomly split between two or more versions to determine which performs better.

**Basic Concept**:
- Randomly split traffic between versions (independent variable)
- **A (Control)**: Typically existing system
- **B (Treatment)**: Typically new version of webpage/feature
- Collect metrics of interest (dependent variable)
- Analyze results statistically

**Alternative Names**:
- **Flights** (Microsoft)
- **1% Tests** (Google)
- **Bucket tests** (Yahoo!)
- **Field experiments** (Facebook, medicine)
- **Randomized clinical trials (RCTs)** (medicine)

### A/B/n Testing
**Extension**: Compare more than two variants (A/B/C/D)
**Complexity**: More than two independent variables
**Common**: Frequently used in practice

### Scientific Validity
**Best Method**: Most scientific way to prove causality
**Purpose**: Confirm changes in metrics are caused by treatment, not chance
**Requirement**: Must run statistical tests to validate differences

---

## A/B Testing Examples

### Example 1: Office Online Feedback

**Goal**: Increase feedback response rate after users read help topics

#### Version A (Original)
**Design**:
- Everything placed together
- Rating and reason for rating combined
- No semantic meaning for stars
- Single question follows rating

#### Version B (Redesigned)
**Design**:
- Stars annotated with "not helpful" to "very helpful"
- Stars are colored for clarity
- Better visual hierarchy

**Result**: **Version B gets more than double the response rate**

#### Version C (Further Iteration)
**Comparison**: B vs. C tested
**Result**: **Version C is better than B by a factor of 3.5**

**Key Lesson**: Incremental improvements through iteration can yield dramatic results

---

### Example 2: Amazon Recommendations

**Innovator**: Greg Linden
**Idea**: Show recommendations based on shopping cart items instead of just cart contents

**Evaluation Considerations**:

**Pros**:
- Cross-sell more items
- Increase average basket size
- Enhanced user experience

**Cons**:
- Might distract people from checking out
- Could reduce conversion rate

**Result**: Simple experiment run, **wildly successful**
**Impact**: Now standard practice across e-commerce

---

### Example 3: Zalora Checkout Rate

**Question**: Does free delivery and return policy increase checkout rate?

**Tested Variations**:
- **Control**: Standard delivery and return terms
- **Variation 1**: Free delivery messaging
- **Variation 2**: Free delivery and returns messaging

**Purpose**: Determine impact of shipping policies on conversion

## Overall Evaluation Criterion (OEC)

### Definition
**OEC**: A long-term metric that the company really cares about
**Purpose**: Determines whether to launch new treatment
**Goal**: Optimize for customer lifetime value

### Common OEC Examples

**Time-Based Metrics**:
- Time on site (per week or month)
- Visit frequency
- Session duration

**Engagement Metrics**:
- Click-through rates
- Conversion rates
- Feature usage

**Business Metrics**:
- Revenue per user
- Customer retention
- Lifetime value

### OEC Characteristics

**Should Be**:
- Defined using short-term metrics that predict long-term value
- Hard to game or manipulate
- Aligned with business objectives
- Measurable and actionable

### When to Dig Deeper

**If Experiment is Flat or Negative**:
- Look at many metrics beyond OEC
- Slice and dice by segments (browser, country, device)
- Analyze subgroups and edge cases
- Consider long-term vs. short-term effects

## A/A Testing

### Purpose
**Goal**: Validate testing infrastructure and statistical methods
**Method**: Run test where A = B (no actual difference in treatment)

### Why A/A Tests Matter

**Common Mistake**: Making conclusions based on random variations
**Prevention**: Ensures differences are real, not statistical artifacts
**Validation**: Confirms testing system works correctly

### Statistical Requirements

**Compute**:
- 95% confidence intervals on metrics
- Determine if differences are due to chance or statistically significant
- Statistical power of tests

**Practice**: Continuously run A/A tests in parallel with other A/B tests

---

## Experimental Design Best Practices

### Run Experiments at 50/50%

**Why Not 1% Experiments?**
- Need to expose sufficient users to detect effects
- Based on power calculations
- Sample size requirements

**Fastest Approach**: Equal-probability variants (50/50% for A/B)
- Minimizes time to statistical significance
- Maximizes learning rate

**Risk Management**: Don't start at 50/50% from beginning - ramp up

---

## Ramp-Up and Auto-Abort

### Ramp-Up Strategy

**Phase 1: Initial Testing (0.1%)**
- Start experiment at very small percentage
- Perform simple analyses
- Ensure no obvious problems detected

**Phase 2: Gradual Increase**
- Ramp up to larger percentage incrementally
- Repeat analysis at each stage
- Continue until reaching 50%

**Phase 3: Full Deployment**
- Maintain 50/50% split for sufficient duration
- Collect data for statistical significance

### Detection Sensitivity

**Large Differences (10%)**:
- Easy to detect with small sample
- Requires minimal exposure
- Serious problems caught during ramp-up

**Small Differences (0.1%)**:
- Extremely hard to detect
- May require 50% for two weeks or more
- Need larger sample size (quadratic relationship)

### Auto-Abort Conditions

**Trigger Abort If**:
- Treatment significantly worse on OEC
- Key metrics show severe degradation
- Critical errors or crashes detected
- User complaints spike

**Purpose**: Minimize negative impact on users and business

---

## Randomization and User Assignment

### Critical Requirements

#### 1. Good Randomization
**Importance**: Foundation of valid experimental results
**Method**: True random assignment to variants
**Verification**: Check distribution across segments

#### 2. Consistent Assignment
**Rule**: User should see same variant on successive visits
**Implementation**: Cookie or user ID-based assignment
**Benefit**: Prevents confusion and maintains experiment integrity

#### 3. Independent Assignment
**Rule**: Assignment to one experiment should not affect assignment to others
**Purpose**: Allows multiple concurrent experiments
**Consideration**: Watch for interaction effects

#### 4. Monotonic Ramp-Up
**Rule**: Users exposed to treatments during ramp-up must stay in those treatments
**Reason**: Prevents bias from switching between variants
**Exception**: May need to handle users who clear cookies

## A/B Testing Advantages

### 1. Test for Causal Relationships
**Strength**: Goes beyond correlation to establish causation
**Benefit**: Know what effects are created by specific changes
**Confidence**: Statistical validity of results

### 2. Reduce External Factors
**Control**: History and seasonality impact both A and B equally
**Isolation**: Can attribute differences to treatment
**Reliability**: Minimizes confounding variables

### 3. Ease of Test Design and Scalability
**Simplicity**: Decide versions to test and split traffic evenly
**Flexibility**: Possible to test range of alternatives
**Scalability**: Can run many experiments simultaneously

### 4. Measures Actual User Behavior
**Real Users**: Actual customers are the testers
**Authentic Data**: Behavior in natural environment
**Solid Evidence**: Data supports ideas and design choices
**Business Value**: Direct impact on metrics that matter

### 5. Ease of Implementation
**Tools Available**: Software packages support simple split tests
**Example**: Google Web Analytics (https://www.google.com/analytics/web/)
**Integration**: Can work with existing infrastructure
**Accessibility**: Available to organizations of all sizes

---

## A/B Testing Disadvantages

### 1. Agreement on OEC Required
**Challenge**: Company must agree on evaluation criteria
**Prerequisite**: Clear goals and objectives needed
**Variables**: Must define independent and dependent variables
**Alignment**: Stakeholders must agree on success metrics

### 2. Problem with Quantitative Metrics
**Limitation**: Doesn't explain **why** A is better than B
**Missing Context**: Lacks user reasoning and motivation
**Solution Needed**: Combine with subjective/qualitative measures
**Designer Value**: Helps identify and understand real issues

### 3. Primacy Effect
**Problem**: Changing design may degrade user experience temporarily
**Reason**: Takes time for users to adapt to new design
**Impact**: New design may perform worse initially even if better long-term
**Solution**: Run experiments for sufficient duration to overcome adaptation period

### 4. Consistency and Contamination
**Cookie-Based Assignment**:
- Users may use multiple machines
- Users may erase cookies
- Same user may see different variants

**Result**: Contamination of experimental groups
**Mitigation**: Use user ID when available, accept some noise

### 5. Multiple Experiments
**Issue**: Running many experiments simultaneously
**Effect**: Statistical variance increases
**Impact**: Harder to get statistically significant results
**Solution**: Careful experimental design and power calculations

### 6. Outlier Detection
**Problem**: 5-40% of traffic generated by non-human sources
**Sources**:
- Crawlers
- Bots
- Robot scripts
- Automated testing

**Impact**: Skewed results and false conclusions
**Solution**: Identify and remove such data from analysis

### 7. Ethical Considerations
**Example**: Facebook emotional contagion experiment
**Concerns**:
- Informed consent
- Potential harm to users
- Manipulation without disclosure
- Privacy implications

**Best Practice**:
- Consider ethical implications
- Follow company policies and regulations
- Avoid experiments that could harm users
- Be transparent when appropriate

---

## Statistical Significance and Power

### Sample Size Calculation
**Before Starting**: Calculate required sample size
**Factors**:
- Expected effect size
- Desired statistical power (typically 80%)
- Significance level (typically 0.05)
- Baseline metric variance

### Running Duration
**Consideration**: How long to run experiment
**Factors**:
- Traffic volume
- Expected effect size
- Desired confidence level
- Weekly/seasonal patterns

**Recommendation**: Run for at least one full week to capture weekly patterns

## Best Practices Summary

### Planning Phase
1. Define clear OEC and success metrics
2. Calculate required sample size
3. Plan ramp-up schedule
4. Consider ethical implications

### Execution Phase

2. Examine multiple metrics, not just OEC

4. Look for unexpected effects
5. Combine with qualitative feedback

### Decision Phase
1. If positive and significant: launch treatment
2. If flat or negative: investigate why
3. Consider long-term vs. short-term effects
4. Document learnings for future experiments

## Mobile Design Guidelines

### Core Principles

#### 1. Design for Simplicity
**Guideline**: Keep interfaces clean and uncluttered
**Reason**: Limited screen space and attention
**Benefit**: Reduces cognitive load

#### 2. Minimize User Input
**Guideline**: Reduce typing and data entry requirements
**Methods**:
- Autofill options
- Smart defaults
- Autocomplete
- Voice input alternatives

#### 3. Minimize Vertical Scrolling, Avoid Horizontal Scrolling
**Vertical Scrolling**: Keep to minimum when possible
**Horizontal Scrolling**: Avoid completely - poor UX
**"Above the Fold"**: Critical information should be immediately visible

#### 4. Prioritize Information on Each Screen
**Focus**: Most important content first
**Hierarchy**: Clear visual hierarchy
**Progressive Disclosure**: Reveal details as needed

#### 5. Useful Error Messages and Feedback
**Clarity**: Clear explanation of what went wrong
**Actionability**: Suggest how to fix the problem
**Timing**: Immediate feedback for user actions

#### 6. Fast System Response Time
**Expectation**: Mobile users expect instant response
**Target**: Sub-second response times
**Loading**: Provide loading indicators for longer operations

## Text Input Efficiency

### Progressive User Interfaces

**Concept**: Transition from recognition (ease) to recall (efficiency)
**Example**: Marking menus (Kurtenbach and Buxton, 1990s)

**Trade-off**: Ease vs. Efficiency
- **Recognition-Based**: Look and select, feedback-driven, controlled
- **Recall-Based**: Memory-driven, automatic, open-loop

**Goal**: Easy to learn, quick when expert

### Swipe Keyboards

**Modern Innovation**: Gesture-based typing
**Benefit**: Faster than tap typing
**Implementation**: Spatial + Language models

#### Basic Keyboard Model
```
User Input Signal (s) 
↓
Spatial Model: P(s/word_i)
+
Language Model: P(word_i/context)
↓
Decoding: w = arg max P(word_i/s)
↓
Text Output (w)
```

**Examples**: SwiftKey, Gboard, Swype

# HCI Study Notes 11 - Motor Behavior Models

## Overview: Models in HCI

### Purpose of Models

**Used to Simplify Reality**:
- Make complex systems understandable
- Create manageable representations

**Applications**:
- Understanding systems
- Designing interfaces
- Evaluating designs

**Focus**: How the interface will perform tasks and how efficient it is

---

## Two Types of Models

### Predictive Models
**Definition**: Provides a mathematical prediction of human performance

**Characteristics**:
- Allows metrics to be determined analytically
- No need for experimental measurement
- Quantitative predictions without building system

**Purpose**: Forecast what will happen without carrying out research

### Descriptive Models
**Definition**: Provides a framework or context for thinking about a problem

**Characteristics**:
- Generally does not yield empirical or quantitative measure
- Qualitative understanding
- Conceptual framework

**Purpose**: Understand and describe system behavior

---

## Predictive/Performance Models

### Key Advantages

**Allow Mathematical Prediction**:
- Human performance without experimental measurement
- No need for working system
- Metrics determined analytically

**Save Resources**:
- Avoid time-consuming user studies
- Eliminate resource-intensive experiments
- Allow design scenarios to be explored hypothetically

### What Can Be Predicted

**Reaction Times**:
- Interface response time
- User reaction time

**Movement Times**:
- Time to move mouse
- Time to press a button

**Task Completion**:
- Overall time to complete tasks
- Efficiency comparisons

---

## Three Main Predictive Models

1. **GOMS** (Goals, Operators, Methods, Selection Rules)
2. **Keystroke-Level Model** (KLM)
3. **Fitts' Law** (Pointing)

---

## 1. GOMS Model

### Four Components

#### Goals (G)
**Definition**: The state the user wants to achieve
**Example**: Find a website
**Nature**: High-level objectives

#### Operators (O)
**Definition**: The cognitive processes and physical actions needed to attain goals
**Example**: Decide which search engine to use
**Types**: Mental and physical actions

#### Methods (M)
**Definition**: The procedures for accomplishing the goals
**Example**: 
- Drag mouse over search field
- Type in keywords
- Press the Go button

**Nature**: Step-by-step sequences

#### Selection Rules (S)
**Definition**: Decide which method to select when there is more than one
**Example**: Choose between typing URL directly or using search engine
**Purpose**: Handle multiple pathways to same goal

---

### GOMS Benefits

**Pseudocode Modeling**:
- Model system systematically
- Understand bottlenecks
- Identify inefficiencies

**Decision-Making Support**:
- Combine various views of system
- Compare alternative designs
- Evaluate trade-offs

**Learning Analysis**:
- Understand learning sequences
- Identify training needs
- Optimize for learnability

**Cognitive Load**:
- Understand cognitive load on user
- Identify mentally demanding steps
- Simplify complex procedures

**Cost-Effective**:
- Saves time and money (no user study needed)
- Quick to prepare, repeat, and analyze
- Precise to interpret and easy to convey

---

### GOMS Limitations

**Novel Interactions**:
- Difficult to model novel multimodal interaction techniques
- Limited for innovative interfaces

**Specialized Users**:
- Hard to model for specific user groups (e.g., interface for blind users)
- Assumes typical user capabilities

**Variable Parameters**:
- User expertise varies
- Context changes behavior
- Individual differences significant

---

## 2. Keystroke-Level Model (KLM)

### Overview

**Focus**: How long it takes users to actually use the HCI via hardware
**Method**: Perform tasks using input devices (interaction)
**Approach**: 
- Measurements of experts performing low-level actions (operators)
- Use measurements to predict time required to complete task

---

### KLM Operators and Timing

#### K - Keystroke/Button Press
**Range**: 0.08s - 1.20s
**Mean**: 0.40s
**Depends On**: Motor skills of the user
**Variability**: Expert typists faster than novices

#### P - Pointing with Mouse
**Time**: 1.10s
**Factors**: 
- Distance to target
- Size of target
**Note**: Relates to Fitts' Law

#### H - Homing
**Time**: 1.00s
**Definition**: Moving hand between mouse and keyboard
**Includes**: 
- Movement between any two devices
- Fine positioning of hand

#### D - Drawing
**Formula**: D(n_D, l_D) cm
**Variables**:
- n_D = number of line segments drawn
- l_D = total length of line segments
**Usage**: Graphic/drawing operations

#### M - Mental Activity
**Time**: 1.35s
**Definition**: Mental preparation for next action
**Purpose**: Thinking or decision-making time
**When**: Between physical actions

#### R - Response Time
**Time**: Variable
**Depends On**:
- The system
- The command
- Context of command
**Nature**: System-dependent, not user-dependent

**Source**: Card, S. K., Moran, T. P., & Newell, A. (1980). The keystroke-level model for user performance time with interactive systems.

---

### KLM Example: Delete File to Recycle Bin

**Goal**: Put a file into Recycle Bin without using shortcut key

#### Step-by-Step Breakdown

| Step | Action | Operator | Time (s) |
|------|--------|----------|----------|
| 1 | Initiate the deletion | M | 1.35 |
| 2 | Find the file icon | M | 1.35 |
| 3 | Point to file icon | P | 1.10 |
| 4 | Press and hold mouse button | K | 0.10 |
| 5 | Drag file icon to recycle bin | P | 1.10 |
| 6 | Release mouse button | K | 0.10 |
| 7 | Point to original window | P | 1.10 |

**Total Time Calculation**:
```
T_EXECUTE = 2t_K + 3t_P + 2t_M
          = 2(0.10) + 3(1.10) + 2(1.35)
          = 0.20 + 3.30 + 2.70
          = 6.2 seconds
```

**Comparison**: Can calculate time for shortcut key method and compare to find most efficient approach

---

### KLM Applications

**Menu Performance**:
- Predicting user performance with hierarchical menus
- Comparing menu depths and structures

**Editor Usage**:
- Predicting usage patterns in text editors
- Optimizing command sequences

**Input Reduction**:
- Assignments to reduce typing keystrokes
- Autocomplete effectiveness

**Accessibility**:
- Predicting text entry performance for physically challenged users
- Word prediction system evaluation

---

### KLM Strengths

**Quick and Easy**:
- Design systems without deep knowledge of memory cognition
- Simple calculation method
- No prototype needed

**Cost-Effective**:
- Predict task times without building prototype
- No need to recruit and test users
- Saves time and money

**Objective**:
- Mathematical foundation
- Repeatable results
- Comparable across designs

---

### KLM Limitations

**Single Dimension**:
- Measures only one aspect of performance (task completion time)
- Doesn't measure time to learn
- Ignores error rates

**Shallow Cognitive Model**:
- Deeper representation of user's mental operations not considered
- Doesn't account for problem-solving complexity
- Limited cognitive modeling

**Individual Differences**:
- Users differ in knowledge and experience
- Motor skills vary significantly
- Technical ability differences not fully captured

**Expert Focus**:
- Based on expert performance
- May not reflect novice behavior
- Learning curve not modeled

## 3. Fitts' Law

### Overview

**Developer**: Paul Fitts (1954)
**Application**: Predicts time to point at object using a device

**Prediction Based On**:
- Distance from target object
- Target object's width (size)

**Also Called**: Psychomotor behavior modeling
**Purpose**: Models target acquisition actions

---

### Fitts' Law Formula

```
MT = a + b log₂(D/W + 1)
```

**Where**:
- **MT** = Movement Time
- **a** = Empirically determined constant (device-dependent)
- **b** = Empirically determined constant (device-dependent)
- **D** = Distance (amplitude) from start to center of target
- **W** = Width of target

### Index of Difficulty (ID)

```
ID = log₂(D/W + 1)
```

**Definition**: Standardized measure of task difficulty
**Unit**: Bits
**Interpretation**: Higher ID = more difficult task

### Index of Performance (IP)

```
IP = ID/MT
```

**Also Called**: Throughput or Bandwidth
**Definition**: Standardized measure of performance
**Unit**: Bits per second
**Use**: Compare targeting effectiveness of different devices

---

### Key Principles of Fitts' Law

**Movement Time Increases Linearly with ID**:
- More difficult tasks take longer
- Predictable relationship

**Distance Effect**:
- Targets further away take longer to reach
- Linear relationship with log(distance)

**Size Effect**:
- Smaller targets take longer to hit
- Linear relationship with log(1/width)

**Speed-Accuracy Tradeoff**:
- Moving fast makes you less accurate
- Must slow down for precision

**One of the Few "Laws" of HCI**: Consistently validated across studies and contexts

---

### Device Performance Comparison

**Fitts' First HCI Application**: Card (1978) testing input devices at Xerox

#### Index of Performance by Device

| Device | IP (bits/s) |
|--------|-------------|
| Eye Tracker | 13.7 |
| Hand | 10.6 |
| Mouse | 10.4 |
| Joystick | 5.0 |
| Trackball | 2.9 |
| Touchpad | 1.6 |

**Interpretation**: Higher IP = more efficient device for pointing tasks

---

### Two Components of Targeting

#### Open-Loop Impulse Phase
**Characteristics**:
- Rapid ballistic movement towards target
- Fast, pre-programmed motion
- Little feedback control

#### Closed-Loop Correction Phase
**Characteristics**:
- Slower corrective movements
- Fine-tuning to hit target
- Feedback-driven adjustments

**Velocity Profile**:
```
Velocity
   ↑     /\
   |    /  \___
   |   /       \___
   |  /            \___
   | /                 \___
   +----------------------→ Time
     Impulse  Correction
```

## Improving Pointing and Targeting

### Three Main Strategies

#### 1. Increase W (Make Targets Bigger)
**Method**: Increase size of clickable/tappable areas
**Example**: macOS Dock with expanding icons
**Benefit**: Easier to hit, faster selection
**Trade-off**: Takes more screen space

#### 2. Reduce D (Bring Targets Closer)
**Method**: Minimize distances between related controls
**Example**: Context menus appear at cursor
**Benefit**: Less movement time
**Implementation**: Group related functions

#### 3. Support Both Phases
**Ballistic Phase**: Provide large initial target area
**Corrective Phase**: Offer visual feedback for fine adjustments

---

### Screen Edges and Corners

#### Infinite Targets at Edges
**Principle**: Cannot overshoot screen edges
**Effect**: Edges act as infinitely large targets
**Examples**:
- Windows Start button (bottom-left corner)
- macOS Menu bar (top edge)
- Close button (top corner)

**Why**: Physical barrier prevents overshooting

#### Corners Are Even Better
**Advantage**: Infinite in two dimensions
**Fastest Access**: Screen corners easiest to hit
**Implementation**: Place important functions at corners
**Examples**: 
- Start menu (Windows)
- Activity corner (macOS)
- Mobile home buttons at bottom

#### Use Physical Constraints
**Design Principle**: Leverage edges and corners to improve interaction
**Result**: Faster, more reliable selection

## Fitts' Law Design Conclusions

### Proximity of Components

**Key Finding**: Placing key components far apart increases time for sequential tasks

**Design Implications**:
- Group common/similar interface items together
- Shorter distances between related buttons
- Easier to use and faster completion

### Menu Design Efficiency

**Menu Type Efficiency** (from least to most efficient):
1. **Linear Menus**: Least efficient
   - Long average distance from handle to elements
   - Must travel length of menu

2. **Rectangular Menus**: More efficient
   - Shorter average distances
   - Compact arrangement

3. **Pie Menus**: Most efficient
   - Equal distance to all menu items
   - Gesture-based selection
   - Faster average movement time

**Linear Menu Optimization**:
- Align handle with middle of menu
- Reduces average distance to items
- Improves efficiency

---

### Mobile Application Examples

#### Gmail for iOS (Poor Design)
**Problem**: 
- Options in bottom sheet
- Far away from menu handle (ellipsis)
- Long finger travel distance

**Impact**: Slower, more tiring interaction

#### Mail for iOS (Good Design)
**Solution**:
- Contextual menu appears next to icon
- Minimal movement required
- Faster interaction

**Lesson**: Keep actions near their triggers

---

#### Form Button Placement

**Sephora for iPhone (Poor Design)**:
- Save button in top-right corner
- Long distance from last form field
- Difficult thumb reach
- Increased completion time

**Taxa 4x35 Taxi App (Good Design)**:
- Call-to-action at bottom of form
- Close to last form field
- Easy thumb reach
- Faster completion

**Lesson**: Position primary actions near where user's attention/cursor will be

### Prime Pixel Concept

**Definition**: The single point of space that input device's cursor is currently on

**Application**: Reference point for contextual actions

**Example - Windows Right-Click**:
- Right-click brings up contextual menu
- Menu origin at prime pixel
- Close to user's current focus
- Minimal mouse movement needed

**Farthest Target**: Items distant from prime pixel take longest to reach

### Button Size Optimization

#### Not Always "Bigger is Better"

**Considerations**:
- Interface consistency matters
- Diminishing returns for large buttons
- Screen space is limited

**Size Increase Effects**:

**Small Objects**:
- 20% size increase = significantly easier to click
- Large improvement in usability
- Worth the space trade-off

**Large Objects**:
- 20% size increase = minimal improvement
- Not worth the space
- May cause other problems

#### Additional Concerns

**Making Sign-In Button Larger**:
- Won't make it easier to click (already large)
- May create inconsistency
- Could blind out other options
- Takes excessive space

**Balance**: Optimize size without sacrificing other design principles

- **Index of Difficulty**: Standard measure of task difficulty
- **Index of Performance**: Compare input devices
- Enables quantitative comparison

### Design Applications
- Improve interaction by increasing W or reducing D
- Leverage screen edges and corners
- Consider prime pixel in interface design
- Optimize button sizes appropriately

### Validation
- One of few true "laws" in HCI
- Consistently validated across studies
- Applicable to wide range of interfaces

## 4. Key-Action Model (KAM)

### Purpose

**Focus**: How users interact with keyboards
**Analysis**: What shortcuts users can use for tasks

**Reveals**:
- What user expects computer to do
- What computer actually does
- Gaps between expectation and reality

---

### Keyboard Key Categories

#### Symbol Keys
**Function**: Deliver graphic symbols
**Examples**: 
- Letters (a-z, A-Z)
- Numbers (0-9)
- Punctuation (., !, ?, etc.)

**Use Case**: Typing in text editor like Notepad

#### Executive Keys
**Function**: Invoke actions in the application
**Examples**:
- ENTER (submit, new line)
- F1 (help)
- ESC (cancel)
- TAB (navigate)
- DELETE

**Purpose**: Command and control

#### Modifier Keys
**Function**: Set up condition to modify effect of subsequently pressed key
**Examples**:
- SHIFT (capitalize, alternate symbols)
- CTRL (command modifier)
- ALT (alternate actions)
- CMD (Mac command key)

**Do Not**: Generate symbols or invoke actions alone

**Example**: 
- SHIFT + 1 = !
- Without SHIFT: 1

---

### KAM Example: Gaming

**Goal**: Understand keyboard operation while playing a game

#### Arrow Keys
**Function**: Change directions and perform actions
**Usage**: Direct movement control
**Benefit**: Intuitive directional mapping

#### Alphabet Keys (W-A-S-D)
**Function**: Alternative to arrow keys
**Usage**: 
- W = Forward
- A = Left
- S = Backward
- D = Right

**Benefit**: 
- Frees right hand for mouse
- Additional keys nearby for more actions
- Standard in PC gaming

---

### KAM Benefits

**Design Evaluation**:
- Suggests aspects of keyboard operation to consider
- Particularly useful for new designs
- Identifies potential improvements

**Critical Analysis**:
- Formulate arguments on potential
- Understand capabilities
- Recognize limitations
- Focus on keyboard interaction domain

**Expectation Management**:
- Identify gaps between user expectations and actual behavior
- Understand mental models
- Improve feedback and consistency

## 5. Buxton's Three-State Model

### Overview

**Purpose**: Simple expression of computer pointing device operation

**Focus**: State transitions
**Application**: 
- Characterize device properties
- Understand interaction techniques
- Determine ease of use

**Source**: Buxton, W. A. S. (1990). A three-state model of graphical input.

---

### The Three States

#### State 0: Out of Range (OOR)
**Definition**: Device not detected by system
**Mouse Example**: Clutching or repositioning mouse on pad
**Touch Example**: Finger not in contact with screen
**Effect**: Movement has no effect on system

#### State 1: Tracking
**Definition**: Device detected but not engaged
**Mouse Example**: Moving cursor around display
**Touch Example**: Finger makes contact with tablet (if hovering supported)
**Effect**: Tracking symbol (cursor) moves

#### State 2: Dragging
**Definition**: Device engaged for action
**Mouse Example**: Button pressed while moving
**Touch Example**: Finger touching and moving
**Uses**:
- Moving icons on desktop
- Selecting range of text
- Drawing
- Resizing windows

---

### Mouse State Transitions

#### State 1 → State 2
**Trigger**: Depress mouse button over an icon
**Result**: Enables dragging when mouse moves
**Example**: Click and hold on file icon

#### State 2 → State 1
**Trigger**: Release mouse button
**Result**: Return to tracking state
**Example**: Drop file icon in new location

#### State 1 ↔ State 0
**Mouse**: Lift mouse to reposition (clutching)
**Purpose**: Reset position without cursor movement

---

### Touchscreen Example

**Scenario**: Touch tablet with only touch/no-touch sensing

#### State 0: Out of Range
**Condition**: Finger not in contact with tablet
**Effect**: No system response to finger movement

#### State 0 → State 1
**Trigger**: Finger comes in contact with tablet
**Result**: System begins tracking

#### Limited Capability
**Problem**: Cannot distinguish State 1 from State 2
**Reason**: No pressure sensitivity, only touch/no-touch
**Implication**: 
- Touching = immediate dragging
- No hover state
- No separate tracking

**Contrast with**: Modern tablets often have hover detection (State 1 distinct from State 2)

---

### Model Benefits

**Conceptualization**:
- Useful framework for understanding input devices
- Clarifies device properties
- Explains interaction techniques

**Design Guidance**:
- Interface must be responsive to all input methods
- Consider mouse, touchpad, keyboard, touch
- Users have preferences

**Usability Requirement**:
- System must be equally responsive for all input devices
- Ensures broad accessibility
- Accommodates user preferences

## Overall Summary: Motor Behavior Models

### Predictive Models

**GOMS**:
- Composed of Goals, Operators, Methods, Selection rules
- Used to achieve specific goals
- Hierarchical decomposition

**Keystroke-Level Model**:
- Identifies low-level actions (K, P, H, D, M, R)
- Predicts task completion time
- Based on expert performance

**Fitts' Law**:
- Predicts pointing time based on distance and size
- MT = a + b log₂(D/W + 1)
- One of few HCI "laws"

### Descriptive Models

**Key-Action Model**:
- Describes keyboard interaction
- Three key categories
- Reveals expectation gaps

**Buxton's Three-State Model**:
- Three states: OOR, Tracking, Dragging
- Conceptualizes input devices
- Useful for design

### When to Use Each

**Predictive Models**:
- Early design phase
- Comparing design alternatives
- No prototype available
- Need quantitative predictions

**Descriptive Models**:
- Understanding existing systems
- Communicating concepts
- Identifying design issues
- Qualitative analysis

### Value of Models

**Design Process**:
- Simplify complexity
- Enable systematic analysis
- Support evidence-based decisions
- Reduce need for costly user studies (predictive)
- Provide frameworks for thinking (descriptive)

**Limitations**:
- Models are simplifications
- May not capture all factors
- Individual differences matter
- Context affects validity
- Should complement, not replace, user testing
