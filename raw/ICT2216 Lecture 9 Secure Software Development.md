### Opening Discussion

**Will you ask an LLM to generate random numbers? Why or why not?**

This is a critical security question. LLMs are deterministic language models — they do not have access to a hardware entropy source or a cryptographically secure pseudo-random number generator (CSPRNG). Numbers that look random when generated by an LLM may be:
- Statistically biased (patterns in training data)
- Predictable (reproducible given the same prompt)
- Not suitable as cryptographic secrets, session tokens, salts, or nonces

> **Rule:** Always use the cryptographically secure random number facilities of your runtime environment (e.g., `secrets` module in Python, `java.security.SecureRandom` in Java, `/dev/urandom` on Linux) — never an LLM.

### Opening Case Studies

**ChatGPT Vulnerabilities — Indirect Prompt Injection (GPT-4o and GPT-5)**

Researchers at Tenable discovered seven vulnerabilities and attack techniques in OpenAI's GPT-4o and GPT-5 models. OpenAI has since addressed some of them.

The vulnerabilities enable **indirect prompt injection attacks** — an attacker manipulates the expected behaviour of a large language model by embedding malicious instructions in content that the LLM processes (e.g., a document, a webpage, a tool result), tricking it into performing unintended or malicious actions.

Key observations from a separate jailbreak attempt on "Fable-5":
- Most attempts failed — the model uses **layered defences**: both input-side and output-side safety checks
- Refusals are not just keyword-based — the model shows **semantic/intent detection** across languages and encodings
- At least **3 classifiers** were observed: input classifier (covering conversation history and system prompt), a live output classifier that interrupts the model mid-generation if it detects policy violations
- Techniques attempted by attackers: Unicode/homoglyph substitution, long-context tracking, fiction framing, and exploiting intent-classification inconsistencies

> **Implication for secure software:** AI-assisted development tools themselves are attack surfaces. Input from external sources processed by LLM-integrated systems must be treated as untrusted.

**15-Year-Old Arrested for AI-Assisted Cyberattack on Bandai Channel**

A 15-year-old student from Saitama Prefecture, Japan, was arrested on 4 July 2025 for launching a cyberattack on Bandai Channel (operated by Bandai Namco Filmworks):

- The student allegedly used a program **created with the assistance of ChatGPT** to exploit a vulnerability in the company's system
- Between 5:00 PM and 8:45 PM on 4 November, the attack caused the unauthorised **cancellation of 46,812 subscription accounts**
- The attack partially disrupted operations until December, when full service was restored after repairs
- The student allegedly discovered the vulnerability in the company's system and exploited it to fraudulently obtain account information

> **Takeaways:**
> 1. LLMs significantly lower the barrier to entry for cyberattacks — script kiddies can now generate functional exploit code with minimal technical knowledge
> 2. Subscription/account management systems must have robust rate limiting, anomaly detection, and authorisation checks to prevent mass account manipulation
> 3. This is precisely why secure software development skills are essential — to build systems that resist even AI-assisted attacks

**Phone Number Encryption — A Design Discussion**

A MongoDB database was shown containing bank customer records with `phone` fields stored in plaintext. 

> **Design question:** Should phone numbers be encrypted in your database?

Considerations:
- Phone numbers are **PII** under PDPA — they must be protected
- If the database is breached, unencrypted phone numbers are immediately usable by attackers for SIM swapping, phishing, or social engineering
- However, encryption creates operational complexity: you cannot search encrypted fields without decrypting first (or using deterministic encryption / format-preserving encryption)
- **Risk-based decision:** For a financial application, phone numbers used for MFA should be stored encrypted at rest. Assess the sensitivity of each field individually.

## Part 1 — Software Assurance and Secure Testing

### Secure Testing for Software Assurance

**Testing** verifies that a program runs correctly on a given set of inputs.

| Aspect | Detail |
|---|---|
| **Benefit** | Concrete failures prove issues and aid in fixing them |
| **Drawbacks** | Expensive, difficult, hard to cover all code paths, and provides no guarantee about untested paths |

**Some errors are particularly hard to find through testing alone:**
- Errors that arise in **unusual circumstances or uncommon execution paths** (e.g., buffer overflows, unvalidated input, unhandled exceptions)
- Errors involving **non-determinism** (e.g., race conditions — the same inputs may or may not trigger the bug depending on thread scheduling)

> In these cases, **static analysis can provide a major improvement** — it analyses all paths simultaneously without needing to execute the program.

---

### Types of Security Testing

**1. Dependency Testing**

Verifies whether third-party modules, libraries, or components introduce vulnerabilities:
- Does the application use components with known vulnerabilities (CVEs)?
- Do security service modules (e.g., authentication libraries) fail under edge cases?
- Are there vulnerabilities in the file system or registry interactions of dependencies?

**2. Client-Side Testing**

The tester works with the user interface exclusively, attempting to enter:
- Escape characters
- Excessively long strings (buffer overflow probing)
- Code fragments in various programming languages
- Incorrect or boundary input values
- Inputs designed to trigger error handling failures
- Cross-Site Scripting (XSS) payloads
- SQL Injection payloads

---

### Quality Assurance at Microsoft — Evolution

Microsoft's QA history illustrates why automated analysis became necessary:

**Original process:** Manual code inspection
- Effective when the team and system were small
- As the system grew, too many paths and interactions existed for humans to reason about manually

**Early 1990s:** Added massive system and unit testing
- Tests took **weeks to run** due to different platforms, configurations, and huge test volumes
- Still detected issues slowly and missed subtle security bugs

**Inefficient detection:** Security holes like the infamous **Blue Screen of Death (BSOD)** in Windows 98 demonstrated that manual and test-based QA alone was insufficient

**2000s:** Static analysis introduced
- Most errors were found in **3rd party device drivers**
- Microsoft introduced the **Static Driver Verification (SDV) framework** — a static analysis tool to detect errors in device drivers
- Significantly improved the quality of Windows device drivers
- Marked the mainstream adoption of static analysis in industrial-scale software development

---

### Code Inspections (Security Auditing)

**Code inspection / security audit** involves convincing someone else that your source code is correct, with the intent of discovering:
- Bugs
- Security breaches
- Violations of programming conventions

**Key principle:** Should be done by a **third party** (not the original developer) — the author is too close to the code to spot their own assumptions and blind spots.

| Aspect | Detail |
|---|---|
| **Benefit** | Humans can generalise beyond single runs; experienced reviewers recognise patterns from past vulnerabilities |
| **Drawbacks** | Expensive, time-consuming, requires skilled reviewers, and provides no guarantees of completeness |

**Code review workflow (e.g., Gerrit):**
- **Submitter** → submits code for review
- **Code Reviewer** → reviews the change, may approve or request changes
- **Verifier** → may run automated checks
- **Approver** → final approval gate before merge
- **Committer** → merges approved changes

**Reference:** Trail of Bits — Auditing Source Code: https://trailofbits.github.io/ctf/vulnerabilities/source.html

---

### Code Management — Git Branching Strategy

A secure development workflow uses **branching** to isolate features from the main codebase:

```
main    ●────────────────────────────────────────────●
        │                                            ↑
develop ●──────────────────────────────────────────●
        │                                          ↑
feature ●───────●                    ●──────────●
feature          ●──────────────────●
```

- **main/master** — production code only; changes via pull requests after review
- **develop** — integration branch for completed features
- **feature branches** — isolated development; merged only after code review and CI/CD checks pass

This workflow ensures that **no unreviewed or untested code reaches production**.

## Part 3 — Introduction to Static Code Analysis

### The Motivation

When you have **millions of lines of code** and **thousands of classes**, manual review cannot scale. A malicious adversary will try to exploit anything you miss — and they can spend weeks searching through your code while you had only limited time to review it.

**Static Code Analysis** automates part of what a human reviewer does — but at far greater scale and coverage.

---

### What is Static Analysis?

**Definition (narrow sense):** Systematic examination of an abstraction of a program's state space — analysing the program without running it.

**Definition (broad sense):** Any analysis of a program without executing it, including simpler syntactic checks (e.g., detecting `=` used instead of `==` in a condition).

**When does static analysis happen?**

| Timing | Examples |
|---|---|
| **Before compile-time** | IDE warnings about undeclared variables, syntax highlighting |
| **At compile-time** | Type checking, compiler warnings |
| **After compile-time** | Load-time analysis of Java bytecode; separate static analysis tools run in CI/CD |

**The key insight:** Static analysis asks a computer to do what a human would do during code review — but with much higher coverage:
- Reason about **many possible runs** of the program simultaneously
- Sometimes reason about **all possible runs**, providing a formal guarantee
- Reason about **incomplete programs** (e.g., libraries, modules) without needing a complete executable

---

### Benefits and Drawbacks of Static Analysis

| Benefits | Drawbacks |
|---|---|
| Much higher code coverage than testing | Can only analyse limited properties |
| Finds bugs in uncommon paths not exercised by tests | May produce **false positives** (complains about non-errors) |
| Can reason about all paths simultaneously | May produce **false negatives** (misses real errors) |
| Can analyse incomplete programs (libraries) | Can be time-consuming to run on large codebases |
| Automates what human reviewers look for | Cannot detect logical errors requiring human judgment |
| People make the same mistakes repeatedly — automation catches them | The heap (dynamic memory) is a major challenge for static analysis |

---

### What Can Static Analysis Detect?

Classic security vulnerabilities and bugs that static analysis tools commonly find:

- **Buffer overflows** and unvalidated inputs
- **Memory errors** — null dereferences, uninitialised data, use-after-free
- **Memory or resource leaks** — allocated memory/handles never released
- **Violation of API or framework rules** — incorrect usage of security APIs
- **Bad programming practices** — suspicious patterns, anti-patterns
- **Broken encapsulation** — private data exposed incorrectly
- **Race conditions** — unsafe access to shared resources
- **Unused variables** and **dead/unreachable code**
- **Missing initialisation** of variables
- **Hardcoded credentials** — API keys, passwords in source code

---

### Classifying Static Analysis

Static analyses can be classified by:

**1. Expressiveness / Power** — which category of properties can they check?

**2. Technique used** — how do they work?

**3. Quality measures:**
- **False positive rate** — how often does the tool complain about a non-error? (High false positives cause developers to ignore the tool)
- **False negative rate** — how often does the tool miss a real error? (Lower is better, but reducing false negatives often increases false positives)

**Classification by approach:**

| Type | Description |
|---|---|
| **Purely syntactic** | e.g., `grep`, `cmd` — pattern matching on text |
| **Control flow aware** | Understands which code paths are reachable |
| **Data flow aware** | Tracks how data moves through the program |
| **Type system based** | Uses type information to detect misuse |
| **Semantically aware** | Understands program meaning, not just structure |

**The spectrum from simple to powerful:**

```
Type Checking ←──────────── Middle Ground ────────────→ Program Verification
(simple, practical)   (static analysis tools)         (powerful, less practical)
e.g., compiler            e.g., Coverity,                 e.g., ESC/Java 2,
type errors               Fortify, Checkmarx              formal proof systems
```

---

### Overview of Static Analysis Pipeline

A typical static analysis tool processes source code through several intermediate representations:

```
Source Code
    ↓
Lexical Analysis → Token Stream
    ↓
Parsing → Abstract Syntax Tree (AST)
    ↓
Semantic Analysis → Names Database / Symbol Table
    ↓
CFG Construction → Control Flow Graph (CFG)
    ↓
Call Graph Construction → Call Graph
    ↓
Analysis Engine → Results / Warnings
```

Each representation enables different types of analysis:
- **AST** — syntactic checks, pattern matching
- **Symbol Table** — name resolution, type checking, scope analysis
- **CFG** — control flow analysis, reachability, dead code detection
- **Call Graph** — inter-procedural analysis, taint tracking across function boundaries

## Part 4 — Techniques Used in Static Analysis

### 1. Simple Pattern Matching

**Pattern matching** checks a sequence of tokens for the presence of specific patterns.

**What patterns are useful?**
- A static string of 24 characters that looks like an API key
- Obviously suspicious strings or magic numbers (hardcoded credentials, default passwords)
- Known dangerous function calls (e.g., `gets()`, `strcpy()` in C — vulnerable to buffer overflows)

**Example — detecting hardcoded credentials:**

```python
# Mimic potential occurrence of API keys in source code
credential = 'WwIZp6ihFqaHV841eb2BxbRt50iAj1EZx1laj'
api_key_github = 'a3$ad59e97...'
api_key = '3000520000LIeTc/4aesbeydadovey5...'
aws_key = '294D78743194D244AF48C6757A7FF1E71CC51'
gcp_key = 'C142940787431940244AF46C67A7FFIE8ICCD'
np_key = '9a3b106041776d6567e13128091013136'
```

A static analysis tool using pattern matching would flag all of these as potential hardcoded secrets — triggering a finding even before the code is executed.

**Real-world example — Cloudflare ReDoS outage (3 July 2019):**

A single regex rule deployed globally caused CPU to spike to **100%** on Cloudflare machines worldwide, dropping traffic by **82%** at peak. The regex contained catastrophic backtracking (an Evil Regex pattern as discussed in Lecture 7). The rule was deployed globally in one go, bypassing progressive rollout.

> "That cloudflare outage was caused by a single regex rule deployed globally in one go 😅" — @mjos_crypto

Static analysis tools with regex analysis capabilities can detect **Evil Regex patterns** (grouping with repetition, alternating with overlapping — see Lecture 7) before deployment.

**How to ensure your regex is correct?** Use static analysis tools that simulate catastrophic backtracking, or use linear-time regex engines (e.g., RE2).

### 2. Data Flow Analysis

**Data flow analysis** collects run-time (dynamic) information about data in software while the software is in a static state.

Three key concepts:

| Term | Definition |
|---|---|
| **Basic Block** | A sequence of consecutive instructions where control enters at the beginning, leaves at the end, and the block cannot branch internally |
| **Control Flow Analysis** | Tracks the flow of control (which block executes next) |
| **Control Flow Path** | The path that execution takes through the blocks |

**Example — Basic Blocks:**

```php
$a = 0;
$b = 1;

if ($a == $b) {      # Block 1 starts
    echo "a and b are the same";
}                    # Block 1 ends
else {               # Block 2 starts
    echo "a and b are different";
}                    # Block 2 ends
```

**Data flow analysis for security — Taint Analysis:**

Taint analysis tracks untrusted input (e.g., HTTP request parameters) from its **definition point** (where it enters the program) through all **reference points** (where it is used) to **evaluation points** (where it is executed or output). If tainted data reaches an evaluation point without sanitisation, it is flagged as a potential injection vulnerability.

```
Definition Point  →  Reference Point  →  Evaluation Point
(user input)         (variable use)        (SQL query / HTML output)
```

**Example — Missing Initialisation (data flow):**

```
# Initialised:
if (b) { c = 5; } else { c = 6; }    ← both branches assign c

# NOT initialised:
if (b) { c = 5; } else { d = 6; }    ← c unset on the else branch
```

Data flow analysis tracks whether `c` has been assigned on all paths to its first use.

---

### 3. Control Flow Analysis

**Control flow analysis** creates an abstract graph representation of the program:
- **Nodes** represent basic blocks
- **Directed edges** represent jumps (branches) from one block to another
- An **entry block** has only an exit edge (the first block executed)
- An **exit block** has only an entry edge (the last block executed)

**Example — Detecting Interrupt Handling Bugs (Linux kernel):**

```c
/* From Linux 2.3.99 drivers/block/raid5.c */
static struct buffer_head *
get_free_buffer(struct stripe_head *sh, int b_size) {
    struct buffer_head *bh;
    unsigned long flags;

    save_flags(flags);
    cli();             /* ← disables interrupts */

    if ((bh = sh->buffer_pool) == NULL)
        return NULL;   /* ← returns with interrupts DISABLED (bug!) */

    sh->buffer_pool = bh->b_next;
    bh->b_size = b_size;
    restore_flags(flags);  /* ← re-enables interrupts */
    return bh;
}
```

**The bug:** The early `return NULL` exits the function with interrupts disabled. Control flow analysis can detect this by:
1. Tracking interrupt state as a boolean: `b = {enabled, disabled}`
2. Checking that on **all paths** to function exit, `b = enabled`
3. The early return path has `b = disabled` → flagged as a bug

**Complications:** Loops and jumps create potentially infinite paths. Static analysis handles this by **abstracting the program state** (e.g., PC, interrupt_state) and checking reachability of the error state.

**Can static analysis always get this right?** No — it may **overestimate** possible execution paths:

```c
if (…) { cli(); }     /* disables interrupts on one path */
…
if (…) { restore_flags(flags); }  /* re-enables on another path */
```

The analysis may not know whether the two `if` conditions are always correlated — it may conservatively assume they can be independent, generating a **false positive**.

**Example — Uninitialised variable in control flow:**

```c
int i;
if (i > 1 && i < 10) {
    print("correct!");
}
```

`i` is declared but never initialised. Control flow analysis detects that `i` is read before any assignment on all paths → **uninitialised variable warning**.

### 4. Abstract Interpretation

**Abstract interpretation** is a theory of sound approximation of the semantics of computer programs. It performs a **partial execution** of the program, gaining information about semantics (control-flow, data-flow) without performing all calculations.

**Key property — soundness:** The analysis may overestimate the set of possible program behaviours, but it never underestimates them. This means:
- If the tool says "no error of type X," there genuinely are none (no false negatives for the checked property)
- If the tool says "possible error," it might be a false positive

**Main applications:**
- Inside compilers — deciding whether optimisations or transformations are safe
- For debugging or certification — checking programs against classes of bugs

**Example — Division by zero:**

```python
def f(x, y):
    return x / y
```

- Abstract interpretation might conclude: "A division by zero **may occur** here" (if `y` could be 0 on any path)
- This is conservative — it could be a **false positive** if the calling context always passes `y ≠ 0`
- But it is **sound** — if the tool says "no division by zero," it truly cannot occur on any execution path

### 5. Model Checking

**Model checking** verifies whether a model satisfies a desired property.

- Not limited to software — applies to hardware, protocols, and state machines
- Can use both static and dynamic techniques
- Particularly powerful because it can express **complex temporal properties** using formal logic

**Example — Class model and call hierarchy:**

```
P:Program
  ├── A:Node — A:Method
  │   └── A1:Node, A2:Node
  ├── B:Node — B:Method (calledBy A:Method)
  │   └── B1:Node, B2:Node
  └── C:Node — C:Method (calledBy B:Method)
      └── C1:Node, C2:Node
```

Model checking can verify properties like:
- "Method A never calls Method C directly" (enforcing architectural layers)
- "Every method that acquires a lock eventually releases it" (liveness property)
- "No path through the call graph leads to privilege escalation" (security property)

Different **logics** are used for model checking:
- **Temporal logic** — properties about sequences of states over time
- **Hoare logic** — preconditions and postconditions for individual functions
- Mathematical logic borrowed from linguistics and built specifically for software verification

---

### 6. Theorem Proving

**Theorem proving** provides a "powerful" version of runtime assertions:
- Based on the behaviour and runtime requirements of the program
- Uses **specially formatted comments or annotations** in the native language (e.g., JML for Java, Dafny for general programs)
- The tool mathematically **proves** that the annotated properties hold

**Characteristics:**
- **Labor-intensive** — requires significant effort to write and maintain formal specifications
- **Limited use** in practice — primarily used in highly **safety-critical applications** (avionics, medical devices, cryptographic protocol implementations, kernels)

### Practical Examples of Static Analysis — Simple to Complex

#### Style Checking (Simplest)
Enforcing naming conventions and coding guidelines without any program abstraction:
- Java methods must start with a **lower case** letter
- C# methods must start with an **upper case** letter
- Constants must be written in **ALL_CAPS**
- Company-specific naming conventions

#### Unused Variables and Dead Code
```python
def calculate():
    x = 5       # x is assigned but never used → warning
    y = 10
    return y    # x is dead code after this point
```

#### Missing Initialisation (Control Flow)

```c
# Correctly initialised on all paths:
if (b) { c = 5; } else { c = 6; }    # c always set

# NOT correctly initialised:
if (b) { c = 5; } else { d = 6; }    # c unset on else path → warning
```

#### Data Flow — Missing Initialisation

```c
# Correct:
d = 5;
c = d;    # d is set before c references it

# Incorrect:
c = d;    # c assigned from uninitialized d → warning
d = 5;
```

#### Circular Static Initialisation (Abstract Interpretation)

```java
class A { static int a = B.b + 1; }
class B { static int b = A.a + 1; }
```

Class `A` depends on `B.b` and class `B` depends on `A.a`. This creates a circular dependency in static initialisation — the abstract interpretation uses a domain that distinguishes **undefined** values from defined ones, detecting that one of these will be undefined at initialisation time.

### Criteria for a Successful Static Analysis Tool

**Must-haves:**

1. **Acceptable false positive rate** — if the tool generates too many warnings, developers will ignore or suppress them without investigation ("alert fatigue")
2. **Not too many warnings** — overwhelming output drives users away from the tool
3. **Good error reporting** — each finding must include context and a trace of the error so developers can understand and fix it
4. **Bugs should be easy to fix** — the tool should guide the developer to the root cause, not just flag a symptom
5. **Teachable** — the tool should allow developers to:
   - **Suppress false positives** with justification annotations
   - **Add design intent** via assertions to help the tool reason more precisely

---

### Limitations of Static Analysis

**The heap challenge:**
- The heap is a **dynamic structure** that evolves at runtime
- It is extremely difficult to model the heap precisely at compile time
- Many static analyses **disregard the heap completely**, leading to:
  - **False positives** — tool flags code as unsafe that is actually safe at runtime
  - **False negatives** — tool misses real heap-based vulnerabilities (e.g., use-after-free, null pointer dereference through dynamically allocated objects)

**Other limitations:**
- Cannot reason about **external inputs** or runtime environment state
- Cannot detect **logical flaws** that require business context to understand
- **Cannot detect humans making stupid decisions** (no automated tool catches everything)
