## Running Case: An Online Service

The running case: an online service. Load balancer, three API servers behind one queue, a single database instance, and two storage nodes. One transaction makes 1 API request, 4 database queries and 2 storage accesses; 2% of transactions also trigger a report query.

- dataset: `service_request_log_2026.csv`, synthetic, generated by simulating this network

# 01 — Multi-Server Queues

## Multi-Server Queues

So far each queue has had exactly one server. Many systems place several identical servers behind a single queue.

- **M/M/c queue:** a single queue feeding c identical servers
- arrivals follow a Poisson process with rate λ, and each server has service rate μ
- the traffic intensity per server is ρ = λ / (c × μ)
- the system is stable only if ρ < 1, i.e. λ < c × μ

Examples: the running case's API tier (three servers behind one load-balancer queue), a thread pool with c worker threads, c GPUs serving one request queue.

Unlike M/M/1, the M/M/c waiting time needs a multi-server calculation (the Erlang C formula). We use the model conceptually here rather than derive it.

---

## One Fast Server or Many Slow Servers

Suppose a fixed budget buys either one server of rate c × μ, or c servers of rate μ behind one queue. Which gives the better response time?

- with equal aggregate capacity, the single fast server wins on latency: an individual job receives the full rate c × μ
- the gap is largest at low load and narrows at high load, but it does not reverse
- real systems still use many servers: one device cannot be scaled up indefinitely, and redundancy matters (one failed server removes 1/c of the capacity, not all of it)

So the case for many servers is operational: cost, fault tolerance and scaling limits, not a queueing advantage.

---

## Multi-Server Queues: The API Tier

The running case's API tier: λ ≈ 8 transactions per second, S ≈ 148 ms per request, c = 3 servers behind one queue.

- per-server ρ = λ × S / c = 8 × 0.148 / 3 ≈ 0.40
- measured mean wait at the API queue: about 7 ms, essentially nothing
- if one server goes down, c = 2: ρ = 8 × 0.148 / 2 ≈ 0.60
- we will see exactly this happen in the dataset, and what it does to the wait

The photolithography station in the capstone case is exactly this shape too: three tools behind one queue. Watch for the echo.

# 02 — Operational Laws

## Systems of Queues: Visit Counts

A single transaction can visit several devices, some of them more than once. The running case has exactly this structure:

```
                                        ┌──► SQL queries ──► Database
transactions ──► API tier (3 servers) ──┤
                                        └──► storage access ──► Storage (2 nodes)
```

---

## Forced Flow Law

The visit count Vₖ is the average number of times one transaction visits device k.

- **Forced Flow Law:** Xₖ = Vₖ × X
- X is the system throughput and Xₖ is the throughput of device k
- the flows through all devices are forced into fixed proportion by the visit counts

In the running case, measured V(db) = 4.02 (the extra 0.02 is the report queries). At the measured X = 8.06 transactions per second, the database sustains 4.02 × 8.06 ≈ 32.4 queries per second: exactly what the log shows.

---

## Service Demand Law

The service demand Dₖ is the total service time one transaction requires at device k, summed across all of its visits.

- **Service demand:** Dₖ = Vₖ × Sₖ
- **Service Demand Law:** Uₖ = X × Dₖ
- this is the Utilisation Law from Lecture 03, restated per device using demands
- Dₖ can also be measured without tracing visits: Dₖ = Uₖ / X

Demands are the key quantity in the rest of this lecture: they determine which device saturates first.

---

## Operational Laws: Measured Demands

Measured from the BEFORE window of the running case, per transaction:

- API tier: V = 1.00, S = 148 ms, so D = 148 ms
- database: V = 4.02, S = 19.4 ms, so D = 78 ms
- storage: V = 2.00, S = 8.0 ms, so D = 16 ms

At the measured X = 8.06 transactions per second, the Service Demand Law gives:

- U(api) = 8.06 × 0.148 / 3 servers ≈ 0.40 per server
- U(db) = 8.06 × 0.078 ≈ 0.63
- U(sto) = 8.06 × 0.016 / 2 nodes ≈ 0.06 per node

All three match the dashboards. Nothing is saturated.

# 03 — Bottleneck Analysis

## The Bottleneck Device

As throughput X rises, every device utilisation Uₖ = X × Dₖ rises in proportion to its demand.

- the device with the largest demand reaches 100% utilisation first: this device is the bottleneck
- beyond that point, the system cannot process transactions any faster
- maximum throughput: X ≤ 1 / Dmax

With c servers at a device, the ceiling becomes X ≤ c / D. The bottleneck is therefore the device with the lowest ceiling, which is not always the one with the largest demand.

**Two terms, used throughout this lecture:**

- **capacity bottleneck:** the device with the lowest ceiling, the one that would cap throughput first
- **congestion hotspot:** the device where queueing actually accumulates. Often the same device, but not always: a station can be the first without ever binding, while queueing piles up for reasons capacity analysis cannot see

---

## Response Time Bounds

- a transaction needs at least its total demand: R ≥ D₁ + D₂ + … + Dₙ
- this minimum is reached when there is no queuing anywhere, i.e. at very low load
- as load rises, queuing at the bottleneck dominates, and response time grows without bound as X approaches 1 / Dmax

Together these give a quick feasibility check: the sum of the demands bounds the best possible response time, and the largest demand bounds the best possible throughput. Both come from simple measurements, before any detailed model is built.

---

## Bottleneck Analysis: Largest Demand vs Lowest Ceiling

Using the measured demands: API 148 ms, database 78 ms, storage 16 ms. The API tier has the largest demand. Is it the bottleneck?

- API ceiling: 3 servers / 0.148 ≈ 20.3 transactions per second
- database ceiling: 1 / 0.078 ≈ 12.8 transactions per second: the lowest
- storage ceiling: 2 nodes / 0.016 ≈ 125 transactions per second
- minimum response time: R ≥ 148 + 78 + 16 = 242 ms

The largest demand does not decide it; the lowest ceiling does. The single-instance database is the capacity bottleneck, and a requirement of 20 transactions per second is infeasible without changing it.

---

## Improving the Bottleneck

Only changes at the bottleneck raise the throughput ceiling. The demand D = V × S gives two levers:

- **reduce V:** cache query results so fewer SQL queries reach the database (halving the visits from 4 to 2 halves the demand)
- **reduce S:** add an index so that each query completes faster
- **add capacity:** replicas or a faster device reduce the demand per unit of capacity

After the fix, recompute the demands: another device becomes the new bottleneck, with a new ceiling. Optimisation is iterative.

---

## Running Case: An API Server Goes Down

Two days in, API-02 goes down. The DEGRADED window catches it.

- per-server ρ at the API tier: 0.40 → 0.60, exactly the M/M/c arithmetic from earlier
- measured mean wait at the API queue: 7 ms → 58 ms, roughly 8 times worse
- API ceiling falls: 3 / 0.148 ≈ 20.3 → 2 / 0.148 ≈ 13.5 transactions per second
- the database ceiling is 12.8: the database remains the capacity bottleneck, but only just

And the puzzle: p95 was already 3.5 seconds before this failure, at ρ(db) = 0.63 with spare capacity everywhere. Losing a server made things worse, but it did not cause the problem. **Not saturated does not mean no queueing problem:** hold that thought until the variability section.

# 04 — Interactive Systems

## Closed Systems and Think Time

Our running online service is modelled as an **open system**: requests arrive from an external population. Interactive systems are different: they are **closed**, with a fixed number of users cycling between thinking and waiting.

- N: the number of active users
- Z: the average think time, the pause between receiving a response and submitting the next request
- each user is always in one of two states: thinking (for Z on average) or waiting for the system (for R on average)

Load testing tools work exactly this way: they simulate N virtual users, each with a configured think time. We keep this section separate from the running case and return to it in the practice questions.

---

## Interactive Response Time Law

Apply Little's Law to the whole system, users included:

- N = X × (R + Z): the user population equals the throughput times the duration of one full cycle
- **Interactive Response Time Law:** R = N / X − Z

This is how load test results are read: the tool fixes N and Z, measures X, and the law gives the response time that users experience.

---

## Interactive Systems: Worked Example

A system supports N = 100 concurrent users with an average think time of Z = 5 seconds. The measured throughput is X = 15 transactions per second.

- R = N / X − Z
- R = 100 / 15 − 5
- R = 6.67 − 5 = 1.67 seconds

If the population doubles to N = 200 while throughput stays capped at the bottleneck ceiling, the additional users appear entirely as added response time.

# 05 — Variability and the Kingman Formula

## Coefficient of Variation

The M/M/1 results depend on arrivals and service being random in a specific (Markov) way. Real workloads differ, and the difference is captured by variability.

- **coefficient of variation:** C = standard deviation / mean
- Cₐ measures the variability of interarrival times, Cₛ measures the variability of service times
- C = 0 is perfectly regular, C = 1 matches the Markov assumption of M/M/1, C > 1 is bursty or highly mixed

Example: an API serving 20 ms lookups and occasional 5 second reports has a very high Cₛ, even though the average service time looks moderate.

---

## The Kingman Formula

For a single server queue with general arrivals and service times (G/G/1), the average wait in queue is approximately:

**W ≈ [ρ / (1 − ρ)] × [(Ca² + Cs²) / 2] × S**

- a utilisation term: the same steep growth as the M/M/1 curve
- a variability term: scales the whole curve up or down
- a time term: the average service time

With Ca = Cs = 1 this reduces to the M/M/1 result. The formula is approximate, but very useful for first-order capacity and latency reasoning.

Kingman covers a single server only. Stations with c servers use the same three-factor structure with a modified utilisation term; the capstone case shows the multi-server form.

---

## Kingman Formula: Worked Comparison

Three systems with identical utilisation ρ = 0.8 and service time S = 100 ms. Only the variability differs.

- **regular arrivals and service** (Ca² = Cs² = 0): W ≈ 0, essentially no waiting, provided arrivals are evenly spaced relative to capacity
- **Markov** (Ca² = Cs² = 1): W ≈ 4 × 1 × 100 = 400 ms
- **mixed workload** (Ca² = 1, Cs² = 4): W ≈ 4 × 2.5 × 100 = 1,000 ms

Same hardware, same load, same average service time: a 2.5 times difference in waiting, caused entirely by variance.

---

## Running Case: Diagnosis — Service Time Variability

The database service time distribution is the tell: two populations, two orders of magnitude apart, in one queue.

- measured Cs² ≈ 34 at the database: extreme, and it comes from the mix, not from noise
- a report query is roughly 75 standard queries' worth of work: 4 quick queries routinely wait behind one report
- note the split: service is wild, arrivals are smooth. The capstone case will show the mirror image

Averages hide this completely. Mean DB service time is 19.4 ms; almost no query takes 19.4 ms.

---

## Running Case: Intervention — Split the Queues

Day 8: API-02 is restored, and the fix ships: report queries move to a read replica, DB-RPT. Standard queries keep DB-01.

- DB-01: ρ falls to 0.38 and Cs² collapses; mean wait per query 165 ms → 5 ms
- DB-RPT: ρ = 0.23; reports wait about 0.27 s, invisible on a 1.5 s operation
- transaction p95: 3.48 s before, 0.44 s after, an 8-fold improvement
- comparing BEFORE and AFTER (both have 3 API servers) isolates the effect of the split

Segregating heavy from light traffic is the variance lever, executed: attack the variance, not the load. Same lesson as continuous batching in LLM inference. Not every system gets this option: the capstone case shows one that could only diagnose its variability, not remove it.

---

## Running Case: Validating the Model

Did the theory predict the new state? The split-out report queue is a textbook G/G/1: one server, independent arrivals, so Kingman applies as stated.

- measured inputs at DB-RPT: ρ = 0.23, Ca² = 1.0, Cs² = 0.26, S = 1.43 s
- predicted: W ≈ 0.23/0.77 × (1.0 + 0.26)/2 × 1.43 ≈ 0.30 s
- measured from the log: W = 0.27 s, within 8%

One honest caveat: the same check on the busy shared DB-01 in the BEFORE window over-predicts by 2 to 3 times, because in a network the arrivals feed back on themselves and stop being independent. Kingman is a tool for stations that meet its assumptions, and a mechanism-teacher everywhere else.

---

## Why Variability Matters in Practice

- **mixed workloads:** a few long requests queued in front of short ones inflate the wait for everyone. Separating heavy and light traffic into different queues reduces Cₛ
- **bursty arrivals:** retry storms and on-the-hour scheduled jobs raise Cₐ. Jittered retries and request smoothing attack variance rather than load
- **headroom:** the common rule of running below 70 to 80% utilisation is a variability allowance. Uniform batch jobs can run higher, interactive systems cannot
- **LLM inference:** the number of tokens per request varies widely, so Cₛ is large. Continuous batching and separating prefill from decode are variance reduction techniques

Three levers act on latency: utilisation, service time and variability. Standard dashboards show only the first two.

# 06 — Capstone Case: The Wafer Fab

## Case Study: A Wafer Fab

The capstone dataset: `fab_cycle_time_2026H1.csv`, structured like a semiconductor fab's lot tracking data. One system that exercises every tool in this lecture at once.

- 525 lots, each passing through 6 process steps: deposition, photolithography, etch, ion implant, CMP, metrology
- about 3 lots arrive per day, January to June 2026
- every row is one processing step for one lot, with three timestamps: arrival, process start, process end
- queue time and process time per step come directly from the timestamps

**The problem:** average lot cycle time rose from 1.8 days in January to 2.2 days in June. Nothing about the process recipes changed. The next three slides run the full diagnostic loop: demands, capacity, then variability.

The dataset is synthetic, generated for this module to reproduce realistic queueing behaviour. Real fabs differ in scale: a lot visits litho 30 to 60 times (once per mask layer) for one to two hours per visit, and full cycle times run to weeks. Here the visits are collapsed and the timescale compressed, but the queueing structure is faithful.

---

## Case Study: Demands in the Fab

Mean service time per step, with visit counts adjusted for rework (V = 1 + rework rate, assuming at most one additional visit per reworked lot):

| Step | S | V | D |
|---|---|---|---|
| Deposition | 6.3 h | 1.06 | 6.7 h |
| Photolithography | 8.3 h | 1.03 | 8.6 h |
| Etch | 5.2 h | 1.04 | 5.4 h |
| Ion implant | 3.1 h | 1.03 | 3.2 h |
| CMP | 2.5 h | 1.03 | 2.6 h |
| Metrology | 1.5 h | 1.04 | 1.6 h |

Total demand per lot: 28 hours. Measured cycle time in January, the healthy period, was 43 hours. So even before anything broke, roughly one third of a lot's life was queue time. Photolithography carries the largest demand.

---

## Case Study: The LITHO-02 Failure

Photolithography is the M/M/c station promised in the multi-server section: three tools sharing one queue (c = 3).

- from April, LITHO-02 collapses: 30 lots per month down to 8
- the station effectively drops from c = 3 to c = 2
- ceiling with 3 tools: X ≤ 3 / 8.6 h ≈ 8.4 lots per day
- ceiling with 2 tools: X ≤ 2 / 8.6 h ≈ 5.6 lots per day
- arrivals: about 3.05 lots per day

Apply the two terms from the bottleneck section: at 3.05 lots per day, no ceiling binds anywhere, so this fab has no operative capacity bottleneck. What litho became is a **congestion hotspot**: the damage is queueing, not lost throughput. The next section explains why.

---

## Case Study: Reading the Queue at a Multi-Server Station

How can queue time triple when the station still has spare capacity? Litho process time stayed flat at about 8.3 hours while its queue tripled.

- per-tool ρ rose from about 0.36 (3 tools) to about 0.54 (2 tools)
- arrivals are bursty, Ca ≈ 1.5, while service is very regular, Cs ≈ 0.2: the mirror image of the online service's database
- priority discipline: Hot lots average 3.2 h in queue, Normal lots 8.0 h

Kingman is a single-server (G/G/1) result, so it does not apply here. The multi-server counterpart, **Sakasegawa's G/G/c approximation**, keeps the same three factors with a modified utilisation term:

**W ≈ [(Ca² + Cs²) / 2] × [ρ^(√(2(c+1))−1) / (c(1−ρ))] × S**

Both factors that grew are in this formula: the utilisation term jumped when c fell from 3 to 2, and arrival variability was high throughout. We use it to read the mechanism, not as a point predictor: within-day burstiness here exceeds what a single stationary Ca captures.

---

## Four Sources of Performance Problems

Everything in this lecture and the last traces a performance problem to one of four places:

- **Demand:** how much work each transaction brings. D = V × S
- **Capacity:** the ceiling the largest demand imposes. X ≤ 1 / Dmax, or c / D with c servers
- **Variability:** how unevenly work arrives and runs. W ≈ ρ/(1−ρ) × (Ca²+Cs²)/2 × S
- **Population:** how many users the system must cycle. N = X × (R + Z)

Diagnosis means working out which of the four is binding. In the fab: demand unchanged, capacity reduced but never binding, variability amplified. That is why cycle time rose.

## Assignment E.4.1: Forced Flow Law

Each web transaction issues 4 SQL queries on average. The web server completes 25 transactions per second. What throughput must the database sustain?

**Solution:**
V(db) = 4 and X = 25, so X(db) = V(db) × X = 4 × 25 = 100 queries per second.

## Assignment E.4.2: Service Demand Law

The database from the previous question takes 5 ms to serve each query on average. What is the database demand per transaction, and what is the database utilisation at 30 transactions per second?

**Solution:**
D(db) = V × S = 4 × 5 = 20 ms per transaction.
U(db) = X × D = 30 × 0.020 = 0.6, i.e. 60%.

## Assignment E.4.3: Bottleneck Analysis

A fab processes lots through six steps with the following demands per lot: deposition 6.7 h, photolithography 8.6 h, etch 5.4 h, ion implant 3.2 h, CMP 2.6 h, metrology 1.6 h. Each step has a single tool. Which step is the capacity bottleneck, and what is the maximum throughput in lots per day?

**Solution:**
Photolithography has the largest demand (8.6 h), so it is the bottleneck.
X ≤ 1 / 8.6 lots per hour = 24 / 8.6 ≈ 2.8 lots per day.

---

## Assignment E.4.4: Bottleneck Analysis

The fab installs three photolithography tools behind one queue, leaving the other steps unchanged. What is the new maximum throughput? If one litho tool fails and lots arrive at 3.05 per day, does the fab saturate?

**Solution:**
With c = 3, the litho ceiling is 3 / 8.6 ≈ 0.35 lots per hour ≈ 8.4 lots per day. Deposition (6.7 h) becomes the next constraint at 24 / 6.7 ≈ 3.6 lots per day, so the system ceiling is 3.6 lots per day.

With one litho tool down, the litho ceiling is 2 / 8.6 ≈ 5.6 lots per day, still above both 3.6 and the arrival rate of 3.05. The fab does not saturate: the rising queue times are a variability effect, not a capacity shortfall.

---

## Assignment E.4.5: Interactive Response Time Law

A closed system has 200 users with an average think time of 10 seconds. The measured throughput is 18 transactions per second. What is the average response time?

**Solution:**
R = N / X − Z = 200 / 18 − 10 = 11.11 − 10 = 1.11 seconds.

## Assignment E.4.6: Kingman Formula

A server runs at ρ = 0.9 with an average service time of 50 ms. Estimate the average wait in queue when Ca² = Cs² = 1, and when the service variability rises to Cs² = 9 with Ca² = 1.

**Solution:**
Utilisation term: ρ / (1 − ρ) = 0.9 / 0.1 = 9.
Ca² = Cs² = 1: W ≈ 9 × 1 × 50 = 450 ms.
Ca² = 1, Cs² = 9: W ≈ 9 × 5 × 50 = 2,250 ms.
The same server at the same utilisation waits five times longer, purely because of service time variance.
